### Q1092 — 排序标题跟着优先级表走：优先级表一改，库里那一列就旧了

- **裁决（第五轮收口，2026-09-23）：** **岔** —— 实现走的就是条目建议的那条；追认：维持现状（2026-09-23 拿主意的人整批追认）。

- **来自：** 票 `gui-looks-like-the-design/11`（`Q802` 裁成物化一列之后引进来的新账，拿主意的人点名要记）
- **类别：** 记
- **在哪：** `crates/core/src/title.rs` 的 `write_sort_keys`；`crates/core/src/catalog/browse.rs` 的 `row_sort_key!`
- **这是什么账：** `work.sort_title` 装的是 `title::choose(set, priorities)` 交出来的
  `Chosen::sort`，而 `choose` **要读优先级表**（它先挑显示标题，排序标题跟着显示标题走）。
  于是优先级表一改，库里那一列还是上一轮的——**得再折一趟标题**才对得上。
- **怎么处置的：** 只在**折标题那一趟**写这一列（`title::run_task`，它本来就拿着
  `Priorities`）。**`title::refold` 不动这一列**——那一条是别人顺手把集合折回来的
  （`scrape::zh::judge` 否掉一条中文名之后就地重折的那一下），手上没有优先级表。
  于是那种就地重折之后，排序键可能比标题集合旧一轮。
- **为什么不顺手给 `refold` 穿一份优先级表：** 它要从 `judge` 往上穿，而 `judge` 的调用方
  （命令行，以及挂单 `Q39` 说迟早要接上的界面那一侧）都得跟着改签名；而这件事的后果是
  「排序键旧一轮」，不是「排错了」——下一趟折标题就对上了。
- **另一条路：** 让 `refold` 把这一列**抹成 `NULL`**（宁可退回作品名，也不留一个旧键）。
  站得住，但那样人在详情面板上否掉一个中文名，整份库的排序会当场退回按作品名排——
  一个更大的、更看不懂的跳变。
- **建议留：** 现在这样。真要收紧的话，该做的是让库屏工序段那一行也说「排序键是哪一轮的」。
- **谁来裁：** 收尾

### Q1096 — 排序标题折大写：Rust 那一层与 SQL 那一层口径不完全一样

- **裁决（第五轮收口，2026-09-23）：** **记** —— 认下并写进文档；追平是票级且无人要。已落地：crates/core/src/catalog/browse.rs row_sort_title! 文档

- **来自：** 票 `gui-looks-like-the-design/11` 的 `/code-review`（Standards 与 Spec 两轴都抓到了）
- **类别：** 记
- **在哪：** `crates/core/src/catalog/browse.rs` 的 `row_sort_title!`
- **这是什么账：** 那一列有三层退路，第一层 `work.sort_title` 是 Rust 的
  `title::sort_title()` 折的——`to_uppercase()` 认 Unicode（`é→É`、西里尔也折），
  还把中间的空白压成一个；第二、三层退路在 SQL 里折，走 SQLite 的 `UPPER()`，
  **只认 ASCII**、也不压空白。
- **什么时候看得出来：** 同一份库里同时有「折过标题的作品」与「退路那两层」（还没折过的库、
  或者没认出作品的那些行），而名字里带重音拉丁或西里尔。那时两批的相对位置是错的。
- **怎么处置的：** **认下来、写进 `row_sort_title!` 的文档**，并把原先那句「所以两侧
  答得一样」改成如实说明。**没去追平**：ASCII 拉丁与 CJK 上两侧本来就一致，而那是这个库
  里绝大多数行；这一票的验收也没要求这一条。
- **另一条路：** 给 SQLite 注册一个自定义的折大写函数（与 Rust 那一处同一份实现），
  或者干脆让第二、三层也落库。前者要给每一处开库的地方都挂上那个函数（漏一处就是
  「这条查询跑不起来」），后者等于把作品名也物化一列。
- **建议留：** 现在这样。真要收紧，第一条路更对——**折大写是一条判据**，两处各写一份
  正是 ADR-0024 要防的事。
- **谁来裁：** 收尾

- **类别：** 岔

- **撞上什么：** 这一票把「默认那一种排法」变成了一处**有后果**的判断
