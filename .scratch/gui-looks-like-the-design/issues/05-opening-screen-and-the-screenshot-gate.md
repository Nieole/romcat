## 截图门：定下来的几件事（拿主意的人 2026-09-14）

- **出基线的机器：** 维护者本机，Apple M1，wgpu 走 Metal。比对也在这台机器上跑；本机重复出图逐像素一致。
- **阈值：** `egui_kittest` 0.36.1 的缺省——一个像素的 YIQ 色距过 0.6 算坏，坏 **0** 个像素才算过（`tests/snapshot.rs` 的 `比对`）。
- **CI 上为什么跳过：** GitHub Actions 的 runner 上没有能用的显卡，wgpu 拿不到适配器，这几条会炸成红，而那不是界面的错。
  `tests/snapshot.rs` 的 `该跳过` 认出 `GITHUB_ACTIONS=true` 就跳过，并印一行说清为什么、在哪儿守。
  **像素层由合并之前在本机跑的门禁守**，`gate.yml` 一行没改。
  **不按「找不找得到显卡」跳**：本机哪天显卡驱动坏了，这几条该红给人看，不该悄悄变绿。
- **Windows 那台验证机（ADR-0018）：** 基线不出自它，渲染后端也不同，会不会红没有量过（挂单 `Q766`）。
- **基线在哪、怎么重批：** 放在 `crates/gui/tests/snapshots/<屏>/<那一态>-<主题>.png`。
  重批跑 `UPDATE_SNAPSHOTS=1 cargo test -p romcat-gui --all-features --test snapshot`。
  对不上时基线旁边会落 `.new.png` / `.diff.png` / `.old.png`，`.gitignore` 挡着不入库；`.gitattributes` 把 `*.png` 标成 `binary`。

## 什么时候该重批基线，什么时候是回归

截图门红了，先看旁边那张 `.diff.png`，再问一句：**这次改动本来就是要改这一屏的样子吗？**

**重批**：新基线与改动放进**同一个提交**，提交说明写清哪几张变了、为什么变；新图照样由拿主意的人看过再合。
- 改动本来就冲着这一屏的样子去：令牌（`tokens.toml`）、字体子集、`look.rs` 里的控件画法、开场或向导的版式与文案。
- 抬了 `egui` / `egui_kittest` / `wgpu` 的版本：抗锯齿与字形栅格化会让整屏细细地变。
- 换了出基线的机器：在新机器上整批重出，一次提交，并改上面那一节和 `snapshot.rs` 开头那几行说明。
- 下面这几张票改了屏上的字与数：`no-mute-spots-opening-a-catalog/04`（空态多一句）、`/05`（开场改按上次扫描倒排）、
  `one-criterion-per-thing/01`（容量）、`/06`（那几档计数）、`queue-followups/09`（台账数字）。
  ⚠️ **截图喂的是合成数据**（`Screen::listed`）：核心库排序或计数的算法变了，**像素不变**；
  只有屏上那句话怎么说、那个数怎么印变了（措辞、格式、单位、多一行字）才会红。
  红在字上、而那张票本来就要改那句话，就是该重批的那种。

**回归**：修代码，基线不动。
- 改动**不是**冲着这一屏去的，截图却红了。比如改的是子库屏，或者改了一个共用控件的内部实现，开场的间距、换行、对齐、颜色跟着变了。
- diff 图上是东西挪了位置、字被截掉、折行变了，或者颜色串了主题，而没有哪张票要这样。
- 只有一种主题红：另一套主题的颜色接错了。

**拿不准就当回归**：把 `.diff.png` 连同改动交给拿主意的人。**不许为了让门禁变绿而重批。**
