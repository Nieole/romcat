# 34 — 作品详情页补齐核心库还答不出的四处：版本、媒体尺寸与时长、所在子库、导出时刻

**What to build:** 作品详情页（票 15）照稿有四处核心库给不出数：「版本」那一行、媒体格上的「尺寸 · 时长」、状态块的「子库」「导出」两行。拿主意的人 2026-09-15 定「另开票让核心库补齐再画」，票 15 先不画这四处（媒体格先只写「来源 · 大小」）。这张票让核心库交出这几样，详情页照稿补上。

**Blocked by:** 15

**Status:** done

⚠️ **这张票是看票 15 的岔路口（4c–e）时拿主意的人定出来的**，不是规格切出来的。

⚠️ 判断只在核心库一处（ADR-0024）：界面不自己数、不自己判。读媒体尺寸只读媒体目录里的文件，主库一个字节都不碰（ADR-0004）。

⚠️ **票面这一行写错**（做的时候发现，收尾照原样报回）：媒体格那一行照设计稿是**四段**「来源 · 尺寸[ · 时长] · 大小」（`prototype.html` 的 `mediaOf`：`${x.src} · ${x.dim} · ${x.size}`，视频的 `dim` 本身就是 `640 × 480 · 0:30`）。票面把它说成「尺寸 · 时长」两格，漏了这一行本来已经画着的来源与大小。实做照稿走。

⚠️ **「版本」那条根因票面也说反了**：核心库不是给不出，而是**已经知道三份互不相干的版本**，缺的是一条正名与一处判断——文件名剥出来的（`filename::Parsed::version`，剥离规则表里 `rev #` / `v#*` 都在，只进候选的依据字符串、不落库）、裁决记下的（`verdict::Facts::version`，沉淀库有列、`triage::Overrides::version` 有覆盖入口，**没有读回通道**）、卡带头里读出来的（`cart::Facts::version`，躺在 `content_cart.facts` 的 JSON 里）。而 DAT 条目名里的修订标记是**刻意不认**的（`identify::naming::is_language_list` 的注释与 `语言标记组认得出来而修订号认不出来`）。这正是 ADR-0024 那个形状。

⚠️ **票面那句「从清单推」在导出这条线上无物可推**：词表**清单**是**子库同步**那一份（`sublibrary_manifest`），`romcat export` 不产清单；它留下的逐份痕迹只有**底本**（`frontend_snapshot`，按**文件**不按条目）。真正的三档是「整库一个时刻 / 按底本按文件推 / 新开一张按作品记的纯加表」。

- [x] 「版本」：核心库给每个变体一个版本值。从哪来（DAT 条目名里的修订标记、数据源字段……）是新的领域判断——先列岔路口，词表补条目后再做
  - **拿主意的人 2026-09-20 裁：两层，一条回退链**——裁决 > DAT 条目名里的修订标记 > 说不出（屏上「—」）。**稿上那个 `1.0` 照实写「—」**：没有修订标记就是没有，不编（这一处与设计稿不同，是 2026-09-20 定的）。
  - 词表补了条目 **第几版**（`CONTEXT.md`，紧挨**汉化组**；`_Avoid_: 版本、Version、修订号`。屏上那一格照稿仍写「版本」，按**待确认队列**那类「屏上照稿写某某」的先例记了一笔）。
  - 发行版那一层：`identify::naming::parse` 加一项 `revision`（`Rev 1` / `Rev A` / `v1.1`），落 `release.revision`，**走补列办法、结构版本一动不动**（仍是 7）。`is_language_list` 那条「修订号不当语言」的口径一个字没改——变的只是它挡下来之后有人接手了。
  - 变体那一层：`identification.edition` 补一列，唯一写者是裁决落成结论那条路（`identify::Projector::project` 读 `verdict::Facts::version`）。**不与 `release.revision` 合成一列**：那一行按「作品 + 平台 + 地区 + 序列号 + 语言」去重、几个变体共用，合进去会让头一个落库的版本盖住其余几个。
  - **挑哪一层只在一处判**：`catalog::detail::VariantDetail::edition`（ADR-0024）；界面只把它印出来。
  - 证据：`crates/core/src/identify/naming.rs` 三条新单元测试（`条目名尾巴上的修订标记读得出来` / `没有修订标记就是没有_不拿初版去补` / `语言组地区与年份都不许被当成修订`）；`crates/core/tests/works.rs::第几版两层一条回退链_裁决压过发行版的修订_都没有就说不出`（三个变体各走一档）。
- [x] 媒体格「尺寸 · 时长」：图片记像素宽高、视频记时长，媒体落盘时读一次记进中立库（走现有补列办法，不升结构版本）；读不出时长（没有 ffmpeg）时只写「来源 · 大小」，不报错
  - `media` 表补 `width` / `height` / `duration_ms` 三列（`catalog::scrape::add_columns`，`SCHEMA_VERSION` 仍是 7）。**不回填**：回填要逐张开池里那 440 张图、逐段拉一百多个进程，而那一趟跑在开库那条路上。
  - 量尺全仓只有一处：`scrape::pool::adopt_into`——**两条进池的路共用的那一段收尾**（主库那份边读边算、在线那份整块下回来）。图片走 `image` **只读文件头**，视频走**外部 ffmpeg**（`ffmpeg -i` 读它写给人看的那两行；**不引第二个程序**，那样「它在不在」只有一个答案）。解析那一段是纯函数、直接钉了测试。
  - 量不出来不是错误：这一版不解的格式、半截文件、没有 ffmpeg、老库里入过池的——四种都留空，屏上退回「来源 · 大小」。
  - 证据：`crates/core/src/scrape/measure.rs` 五条单元测试（含 `视频流那一行里的四字码不许被读成宽高`——`(avc1 / 0x31637661)` 松一点就会被读成 `0 × 31637661`；`量不出来的时候交回空的一份而不是报错` 走 `preview::NO_SUCH_PROGRAM`，**不靠这台机器装没装 ffmpeg**）；`crates/core/tests/preview.rs::入池那一刻量一次尺寸_图片读得出宽高而视频那一格留空`、`::量不出来的那几格空着_后来量到了补得上_而且不许被再量不出来的抹掉`；界面那一侧 `crates/gui/tests/work.rs::媒体那一面_没有ffmpeg时视频占位并说明原因_播放交给系统播放器` 断的是四段那一整句。
- [x] 状态块「子库」：核心库答出这部作品落在哪几个子库的选择集里，列子库名
  - `sublibrary::holding(catalog, keys)`：**复用 `select`**——与子库屏、容量条、差量预览、真正同步那一趟同一个函数（ADR-0024），于是「详情页说它在这个子库里」与「同步时真会搬它」不可能分岔；例外照样优先于规则（ADR-0016）。
  - 为它开了一条**按变体折事实**的缝 `sublibrary::facts_of`：全库那一趟在真库上是 46,444 个变体 / 343 毫秒（挂账 D156），而详情页开在画帧线程上（一帧预算 16 毫秒）。两条路共用 `fold_one`，于是「一个变体在选择集眼里长什么样」仍旧只有一处定义。
  - 证据：`crates/core/tests/sublibrary.rs::按键折出来的事实与全库折出来的那一份逐字一样`（含收藏、刮削值、库里没有的键）、`::一个变体落在哪几个子库里由求值那一处答_例外照样优先于规则`（规则命中 → 手工排除 → 手工收入 → 多变体取并集）。
- [x] 状态块「导出」：核心库答出这部作品上次写进前端格式的时刻（现在 `exported_at` 是整库一个）；按作品记还是从清单推，列岔路口
  - **拿主意的人 2026-09-20 裁：按作品记**。新增**纯加表** `export_entry(anchor, subject, platform, format, at)`（`catalog::export`），`SCHEMA_VERSION` 一动不动；先例写进了注释（刮削五表、标题集合、底本、子库三表）。
  - 与 `mark_exported` **同一处、同一个时刻戳、同一道打戳闸**：`dry_run`、按停、撞上外面有人动过那三趟照旧不记。每趟导出**整份重写那个格式的那一批**（别的格式不动）——留着上一趟的行会让已经从库里消失的作品永远说着「已导出」。
  - 收敛那一趟顺手交出名单（`Converged::written`，与 `entries` 那个计数**同一个循环里攒**）。
  - **实测（票面原为预测）**：28,529 行（真库条目数，`docs/library-facts.md`）一个事务写完，**头一趟 113.5 毫秒、重写一趟（先整份删掉再写）162.3 毫秒**——`crates/core/tests/stage.rs::逐条记下导出去的是谁_真库量级上那一笔写库的代价量得出来` 打印（`cargo test … -- --nocapture`）。一趟真机导出是 2.7 秒，这一笔在那一趟里量级上不显眼。
    ⚠️ **这两个数带保留**：**debug 构建 + 内存库（`Catalog::open_in_memory`）**量的。release 构建上应当更快，而**落盘的库要真走一次 fsync**——两样都**没量过**，别拿这两个数去回答「真机上要多久」。那条测试也**不断言任何时间上限**：挂钟在忙机器上不稳，钉一个数就是钉一条会随机变红的测试；它断的是行为（整批写完、读得回来、整份重写不累积、别的格式那批不动）。
  - **那一行的时刻带年**（`2026-09-18 11:08`），而设计稿上写的是 `09-03 15:41`——**这一处与稿差一个年份**，2026-09-20 拿主意的人定维持带年：屏上只留一种时刻写法（`report::human_time`，库屏工序段、任务历史、根那几行印的都是它），而这一行答的是「多久以前」，跨年的库上不带年会骗人。
  - 证据：`crates/core/tests/pegasus.rs::导出逐条记下写出去的是谁_之后扫进来的作品照实说还没导出`（走真的 `export_task`，断「整库说导过了而上次导出之后才扫进来的作品说还没」——那正是整库那个时刻答不了的那一种）、`::只排计划那一趟一条逐条的账都不记`；`stage.rs` 那一条另断「整份重写不累积」与「换个格式导一趟，上一个格式那批一条不少」。
