# 23 — 从浏览加入子库与挑选模式

**What to build:** 维护者在浏览里筛到满意，把这一批加进某台设备的子库：可以作为一条

**例外**加入。一个子库通常要分几次加——挑选模式让他换一个平台、点一下就加一条。

### Q1180 — 判「这条规则已经有了」比树不比原文，**与稿不同**

- **裁决（第五轮收口，2026-09-23）：** **记** —— 编排者已裁并落地。已落地：crates/core/src/sublibrary/rule.rs Rule::same_as

- **来自：** 票 `gui-looks-like-the-design/23`（票面第 3 条「已经存在的同一条规则被拦下」）
- **类别：** 与稿不同（**编排者 2026-09-22 裁，已落地**）
- **背景：** 全核心库搜过，从前**没有**这条判据——`Catalog::add_rule` 只发号插入、不查重。
  可用的现成料只有两样：`Rule` 派生的 `PartialEq`（**连 `text` 一起比，实际是「原文一字不差」**）
  与 `StoredRule::text` 的字符串比。两者等价，而且都是**比原文**。
- **稿怎么做的：** `prototype.html` 的 `renderAS` 比字符串：`sub.rules.some(x=>x.text===r.text)`。
- **落地怎么做的：** `Rule::same_as`（只比 `root` 那棵树）与 `Rule::same_one_in`
  （在一批 `StoredRule` 里找同一棵树的那条，交回序号）。**全仓判重只走这一处**（ADR-0024）。
- **为什么与稿不同：** **同一棵树可以有多种原文。** 实测确认了三种写法，
  折出来都是同一棵树、却是三串不同的字：
  - `平台=GB  且  中文=汉化`（中间多打一个空格——人手打出来最常见的那种）
  - `平台=GB 且 中文= 汉化`（值前面多个空格）
  - `(平台=GB 且 中文=汉化)`（整条套一对括号，从别处粘过来的那种）

  拿原文判重的话，同一条规则加得进去两遍，而子库那一侧照样取并集：
  **屏上多一条、选出来的一个不多**——人只会以为哪里坏了。
  同一个教训票 13 栽过一次（改名必须走树，不许 `text.replace`）。
- **要改回照稿比字符串的话动哪一处：** `crates/core/src/sublibrary/rule.rs` 的
  `Rule::same_as`——把 `self.root == other.root` 换成 `self.text == other.text` 即可，
  调用方一处都不用动。钉着它的是 `crates/core/tests/sublibrary.rs::同一棵树两种原文也算同一条规则`。
- **读不回来的那几条一律当作不同**：读不懂的规则本来就没参与求值，拿它去挡一条读得懂的会挡错。
- **谁裁的：** 编排者（2026-09-22）

### Q1181 — 「加入子库」那一层的预估要等一趟 343 毫秒的活，屏上写「正在算…」

- **裁决（第五轮收口，2026-09-23）：** **记** —— 编排者已裁并落地。已落地：票 gui-looks-like-the-design/23（排任务台、「正在算…」）

- **来自：** 票 `gui-looks-like-the-design/23`（验收第 1 条「预估新增多少变体、与已有规则重复多少、加入后多大」）
- **类别：** 取舍（**编排者 2026-09-22 裁，已落地**）；**与稿不同**
- **是什么：** 稿上 `renderAS` 那几个数是**当场**跟着「加入方式 / 目标子库」变的。
  实现做不到：算它们要 `sublibrary::facts()` 走一遍全库，**真机实测 343 毫秒**
  （挂账 D156），再加一趟 `fit`（走排计划那半条线）。**摆不上画帧线**
  ——这一屏每秒画几十帧。
- **落地怎么做的：**
  - 那一趟排**任务台**，只在**开弹层**与**换目标 / 换加入方式**时各算一趟
    （`sublibrary_estimated_for` 记着上一趟是照哪一档算的）；
  - 算着的时候屏上写「**正在算…**」，**不写 0**；
  - 算不出（卡不在手边，核心库交回 `Fit::Unknown`）写「**算不出 · 目标不在位**」，
    **也不写 0**（`Q591` 与 `Q1103` 同一条规矩）。
- **两处守卫特意没挂在这条慢路上**（这是这一条最要紧的一半）：
  - 「按不动」的理由（已经有同一条规则了）由 `Device::duplicate` **当场**答
    ——它只要读一遍那台的规则；
  - 屏上那行「已经有这条规则了」的红字同理，原先摆在预估块里，**挪出来了**。

  理由：守卫挂在慢路上，屏上就会有一段时间**既不说为什么、按钮却已经按不动**
  ——那正是 ADR-0005 拦的「说不出为什么的灰」。
- **要改回照稿当场变的话**：得让那几个数算得起每帧一次，也就是把 `facts()` 缓起来
  并跟着库的变动失效。那是另一张票的量。
- **谁裁的：** 编排者（2026-09-22）

### Q1184 — `replace_rules` 把名字抹成 `NULL`，「改选择」那条回程会连别的规则一起清掉

### Q1185 — 「只加入勾选的」在「全选筛选结果」那一档按得动，稿上是禁的

- **裁决（第五轮收口，2026-09-23）：** **活** —— 无家可归（全仓没有一张开着的票占这片地），进 `/grill-with-docs`，束「界面照稿还差的尾巴」。

- **来自：** 票 `gui-looks-like-the-design/23` 的 `/code-review`（Spec 轴）
- **类别：** 与稿不同（**要人裁**）
- **是什么：** 稿上 `pk=S.pickAll?0:S.picked.size`——**全选那一档 `pk=0`**，
  「只加入勾选的」那一档 `aria-disabled`。实现里 `facts.picked` 走
  `Picked::count(total)`，全选那一档交回「筛出的行数 − 点掉的」，于是那一档**按得动**，
  一下把整批筛选结果写成手动例外。
- **为什么要紧：** 例外是「**人一条条点出来的永久决定**」（ADR-0016），
  不随筛选变。把一万多条筛选结果一次写成例外，等于把一次筛选的结果冻成永久决定
  ——而那正是「作为规则加入」那一档要干的事，两档就没区别了。
- **两条路：** ①照稿禁掉（全选时那一档灰着，理由写明「全选请用『作为规则加入』」）；
  ②留着，但按之前弹一层确认写清要写多少条例外。
- **谁来裁：** 拿主意的人
