## 试跑证据

工具链 `rustfmt 1.9.0-stable (48a229ceae 2026-09-01)`。试跑方法：`git archive HEAD | tar -x` 出一份
丢弃副本，在副本上跑，工作区不碰。

### 先纠一条前提：`rustfmt` 按**显示列宽**算，不按字符数算

票正文第 7 行写的「中文字算一列、实际占两列」**说反了**。判据：同一段结构，参数是 70 个汉字
（70 个字符 / 140 列）时**被拆开**，即使把 `fn_call_width` 顶到 100；换成 70 个 ASCII 字符
（70 字符 / 70 列）则原样留在一行。也就是说它用的是 unicode-width。详见挂单 `Q181`。

这条把整张票的结论掉了个个儿：`max_width = 100` 就是人眼看到的一百列，与人手写排版同一把尺。
实测这个仓库的代码行显示列宽 p50=28、p90=65、p99=92、超过 100 列的只有 103 行 / 112,908 行。
**所以默认值本来就合身**，不需要为中文另调宽度。

### 唯一真被打乱的对齐表格：7 张，全在一个文件里

`crates/cli/tests/triage.rs` 的命令行参数表：

```diff
-        "triage", "batches", "--library", "小库", "--workspace", &工作目录,
+        "triage",
+        "batches",
+        "--library",
+        "小库",
+        "--workspace",
+        &工作目录,
```

数组要保住紧凑排法，规则是**表里每一个元素都不超过 `short_array_element_width_threshold`**
（默认 10 个字符）。这里栽在 `"--workspace"`（13 个字符）上。

数的口径写出来免得复现不了：`grep -rP '^\s*("[^"]*",\s*){2,}' crates --include='*.rs'`
（行首连排两个以上「字面量 + 逗号」的行），HEAD 上 29 行、格式化后 22 行；口径收紧到
`{3,}` 是 27 → 20。**两种口径丢掉的都正好是那 7 行，且都全在 `crates/cli/tests/triage.rs`**
——分母随口径变，结论不变。

三条路都量过，交给票 `11` 挑：

| 路 | 全仓库代价 | 那 7 张表 |
|---|---|---|
| 接受摊开 | 77 个文件 / 2,252 行 | 摊平 |
| `short_array_element_width_threshold = 15` | 85 个文件 / 2,404 行 | **7 张全保住** |
| 逐处 `#[rustfmt::skip]` | 77 个文件 / 2,252 行 + 7 处属性 | **7 张全保住** |

阈值那条要多花 8 个文件 / 152 行，因为它反过来**把别处人手写成一行一个的短元素数组并成紧凑表**
（删除侧 768 → 943 行）。`#[rustfmt::skip]` 是就地显式的，仓库里已有先例
（`crates/gui/src/layout.rs` 的 `ALL`）。本票不替票 `11` 拿这个主意，只把三个数摆出来。
另外注意：阈值救不回带长元素的那一类（`&workspace.path().to_string_lossy()` 是 35 个字符，
调到 60 也没用），那一类只有 `#[rustfmt::skip]` 一条路。
