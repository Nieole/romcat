# 05 — 显示标题不被低置信别名压过

**What to build:** 一条中文条目的中文名其实是拉丁串时，一个**低置信的中文别名**会压过它当上**显示标题**——因为排序键把「语言 + 类型」排在置信度前面。这一票让显示标题回到最可信的那个叫法。

顺带把三处用户看得见的文案里夹着的一长串空格去掉（规则那一层、浏览屏、库浏览各一处）。

**中文名与别名进标题集合这件事一个字都不改**——用户搜哪个叫法都还得搜得到。改的只是"谁当显示标题"。

**Blocked by:** 无 —— 可立即开工

### Q24 — 「别名永远轮不到当显示标题」只在条目的中文名真是中文时成立

- **来自：** 票 `offline-chinese-fields/03`（`/code-review` 的产出）
- **类别：** 路过发现，不在范围内（票 01 的 Q2 / Q7 第 4 条没盖住的那一角）
- **在哪：** `crates/core/src/title.rs:388` 的 `rank`、`:704` 那段注释、
  `crates/core/src/scrape/priorities.toml` 里标题那一节的 ⚠️
- **为什么没停线：** 这张票的硬约束里明写着「别名在变体锚点上、低置信、不当显示标题，
  别顺手动它」。
- **这张票实际做了什么：** 没碰它，只记准。`rank` 的桶是 `(语言, 类型)`，**排在置信度
  前面**：`(中文, 别名) = 3`、`(中文, 汉化组自取) = 4`、`(英文, 官方名) = 5`，
  而「别名 + 非中文」落到 `_ => 7`。中文数据源里对西方游戏常有 `name_cn` 就是一串拉丁字
  （`name_cn = "Minecraft"`）的条目——那时中文名那一路进 7 桶，而别名里那个中文叫法
  （`我的世界`）进 3 桶，于是**低置信的别名成了显示标题**，还压过 4 桶的汉化名。
  `title.rs:709` 与优先级表里那两段都断言这不会发生。两条出路：把判据改成「别名那一路
  一律垫到汉化组自取之下」，或者把这条限制如实写进那两处注释。
- **谁来裁：** 拿主意的人
- **状态：** settled —— **两条出路都没走，走的是第三条。** 票给的那条「别名那一路一律
  垫到汉化组自取之下」按两种读法各改一遍、各跑一遍标题那两组测试量过：互换 3 / 4 档
  测试全绿但**根本解不了**（正名还在第 7 桶，别名从第 3 桶挪到第 4 桶照样赢）；
  把中文别名整档垫进「其余」那一桶解得了，代价是**破三条测试**
  （`显示标题按中文英文日文文件名回退`、`排序标题独立生成而不是拿中文标题去排`、
  `中文名带置信度低的那些进得了队列`），它们钉的是「中文优先」这条回退链本身，
  受连累的是库里那 16,420 个只有文件名的变体——全库最大的一档。
  于是**另立判据**：`rank` 里裁决之后、档位之前插一层，按来源认出这一路整路垫底，
  只动这一路，别的比较逐条不变。四处断言这不会发生的注释全部改成了现在这套说法
  （`title::choose` 的回退链与七层说明、`title::classify` 里那段、`priorities.toml`
  标题那一节、`fuzzy::ALIAS_SOURCE` 的文档）。这条判据认的是一个**具体的来源名字**，
  代价记在挂单 `Q140`。
- **收尾裁决：** **由本票接着做** —— 它就是从这条挂单立起来的。

### Q140 — 票 05 给的第一条路（别名整档垫到汉化名之下）两种读法都不成立，改走「另立判据」

- **来自：** 票 `queue-followups/05`（Q24 的裁决落地）
- **类别：** 票写错了（给的两条出路里，第一条解不了它要解的那条）
- **在哪：** `crates/core/src/title.rs` 的 `rank`（排序键）
- **为什么没停线：** 票自己写着「选哪条要看它对已有那批显示标题影响多大」，那就是让人
  去量；量完两条读法都被现有测试判死，第三条路不动任何已有结论。
- **这张票实际做了什么：** 把票给的那条路按两种读法各改一遍、各跑一遍标题那两组测试：
  - **读法一（`中文·别名` 与 `中文·汉化组自取` 互换名次，3 ↔ 4）**：测试全绿，
    但**根本解不了这条缺陷**——`name_cn` 是拉丁串时正名落在第 7 桶，中文别名从第 3 桶
    挪到第 4 桶照样赢。
  - **读法二（`中文·别名` 不再享有语言优先，落进「其余」那一桶）**：解得了，代价是
    **破三条测试**（`显示标题按中文英文日文文件名回退`、`排序标题独立生成而不是拿中文
    标题去排`、`中文名带置信度低的那些进得了队列`），它们钉的是「中文优先」这条回退链
    本身，而受连累的是**库里那 16,420 个只有文件名的变体**（`TitleKind::Alias` 的文档
    原话：「库里那些中文文件名多半是这一档」）——那是全库最大的一档。
  于是走**另立判据**那条路：在 `rank` 的排序键里，**裁决之后、语言与类型的档位之前**
  插一层，按来源认出 `中文离线源·别名` 这一路（`fuzzy::ALIAS_SOURCE`）整路垫底。
  这一层只动那一路，别的比较**逐条不变**（对所有别的来源它恒为 0），全量门禁
  58 / 1,537 / 0，只多了本票新增的那一条测试。断言这道闸管用的**四处**注释
  （`title::choose` 的回退链、`title::classify` 里那段、`priorities.toml` 标题那一节的
  ⚠️、`fuzzy::ALIAS_SOURCE` 的文档）全部改成了现在这套说法。
  **代价记在这儿**：`rank` 从此认得一个具体的**来源名字**，而它原来只按
  (语言, 类型, 置信度, 表里名次) 这些通用的面排序。同一路要是将来多出第二个源
  （比如别的数据源也给「那条条目还叫什么」），得记着回来加。真要做干净，得给
  `TitleRow` 添一列「这个名字说的是不是手上这个东西」，那是中立库的结构版本要动的活。
- **谁来裁：** 拿主意的人（认下这个按源名认的判据，还是排一张票把它升成 `TitleRow` 的一列）
