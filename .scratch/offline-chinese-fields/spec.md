# 规格：中文离线源取全字段

**Status:** ready-for-agent

## Problem Statement

刮削报告现在告诉用户：**「离线档补不上简介、类型与开发商——换 `--profile 在线` 跑一趟才补得上」**。

这句话是错的，而且错得有代价。

**中文离线源**那份本机数据里，实测（`dump-2026-09-01`，用户机器上已取回）：

| | 条数 | 覆盖率 |
|---|---|---|
| 游戏条目 | 112,562 | — |
| 带**中文简介**的 | 105,981 | **94.2%**（中位 338 字） |
| infobox 带 `游戏类型` | 112,184 | **99.7%** |
| infobox 带 `发行日期` | 112,413 | 99.9% |
| infobox 带 `开发` | 94,351 | **83.8%** |
| infobox 带 `发行` | 88,339 | **78.5%** |
| infobox 带 `别名` | 111,923 | 99.4% |

**这些字段一条都没被取出来过。** 存储只落了条目号、原名、中文名、别名、年份、平台六样；中文离线源在刮削里也只产出一个字段——中文名。那份 435 MB 的数据被当成「撞名字的索引」在用。

调研文档的原话是「dump 完全**不含图片**」，同一段还写着「有中文译名、**有中文简介**」「中文名/中文简介质量最高」。两个离线数据源各缺一样（这一份缺图、另一份缺简介），在报告里被并成了一句「离线档补不上简介」。

后果有三层：

1. **用户被推去烧在线配额换更差的东西。** 在线源给的是英文简介，还要赌上账号与 IP（ADR-0007）；中文简介就躺在本地，免费、离线、是中文的。
2. **导出的库达不到用户自己手写的成色。** 用户手上那份维护多年的前端元数据（193 条样本）每条都有 `description`（中位 1354 字）、`developer`、`publisher`、`genre`。工具现在导出来这四格全是空的，除非跑在线档。
3. **报告在说假话。** 「缺口那一节不是装饰」是这份报告存在的理由，而它点名的缺口有三个是假的。

## Solution

**中文离线源从「撞名字的索引」变成一份完整的离线中文刮削源。**

撞上一个中文条目之后，用户一次拿到：中文名、别名、**简介**、**类型**、**开发商**、**发行商**、年份。全部离线，**一个网络请求都不发，一份配额都不扣**。

在线源的定位随之收窄成它唯一不可替代的那件事：**图**。刮削报告的缺口那一节要照着改——不再说「离线档补不上简介、类型与开发商」，而是如实说「离线档补不上**图**」。

用户看得见的变化：跑一趟 `romcat scrape`（默认离线档），前端里的简介、类型、开发商、发行商从空白变成中文内容，**而这一趟的网络请求数仍然是 0**。

## User Stories

1. 作为库主，我想让离线刮削补上中文简介，这样前端里每个条目点进去有话可读，而不是一片空白。
2. 作为库主，我想让离线刮削补上游戏类型，这样我能在前端里按类型筛。
3. 作为库主，我想让离线刮削补上开发商与发行商，这样我导出的库和我手写那份成色一致。
4. 作为库主，我想让这一切**不发任何网络请求**，这样我不必为了文字内容赌上账号与 IP。
5. 作为库主，我想让刮削报告如实说「离线档补不上的是**图**」，这样我不会为了简介白跑一趟在线档。
6. 作为库主，我想在报告里看见「这一趟从中文离线源补上了多少条简介、多少条类型」，这样我知道这一层到底值多少。
7. 作为库主，我想让简介、年份、开发商、发行商挂在**作品**这一层，这样同一部作品的几个变体不会各存一份重复的简介。
8. 作为库主，我想让中文名与别名继续挂在**变体**这一层，这样依据说得清「是这个文件的正题撞上的」。
9. 作为库主，我想让每一条新字段都带**依据**（条目号、撞上的是哪个名字、两道校验的结果），这样半年后我查得回去。
10. 作为库主，我想让别名进**标题集合**，这样一部作品的多个叫法我都搜得到。
11. 作为库主，我想让中文离线源来的字段和 DAT、文件名那几个源走同一套**字段级优先级**，这样我能用一个源的标题配另一个源的年份。
12. 作为库主，我想让这批字段的置信度如实标注，这样模糊匹配来的东西不会被当成确凿结论。
13. 作为库主，我想让撞不上中文条目的那些变体**什么都不产出**，而不是产出一条像模像样但其实是猜的简介。
14. 作为库主，我想在报告里按平台看见中文离线源的覆盖，这样我知道 N64、DC 这些老平台为什么补不上（数据源本身就浅，不是匹配算法的锅）。
15. 作为库主，我想让改过匹配参数之后重跑能真的重采，这样调门槛不会被输入指纹的缓存吞掉。
16. 作为库主，我想让存储结构升级时自己从本地那份原件重建，这样我不必重新下载 435 MB。
17. 作为库主，我想让 `romcat zh sync` 之后就能看出这一版索引带了哪些字段，这样我知道要不要重刮。
18. 作为库主，我想让简介里的换行、全角空格、以及数据源自带的排版原样保留，这样导出到前端里不会变成一坨。
19. 作为库主，我想让超长的简介（实测最长 9,962 字）不撑爆前端也不撑爆界面表格，这样列表还能滚得动。
20. 作为库主，我想让 infobox 里一个键有多个值时（`开发= A、B`）拆成多条，这样「开发商」这一格不是一串带顿号的长字符串。
21. 作为库主，我想让 infobox 里缺键的条目照常产出它有的那些字段，而不是整条跳过。
22. 作为库主，我想让这一层的产出照样进**待确认队列**，这样模糊匹配撞错了我改得掉。
23. 作为库主，我想让我在队列里对中文名下的**裁决**也管住同一条目来的其余字段，这样我不必对同一次误撞裁决五遍。
24. 作为库主，我想让导出侧一行都不改，这样这次改动的风险只落在刮削那一侧。
25. 作为维护者，我想让「哪些字段来自哪个数据源」在优先级表里写得出来，这样将来加第二家中文数据源时不必改代码。

## Implementation Decisions

### 匹配在变体层做，字段挂在它该挂的那一层

这是这份规格最重要的一条决定，两半各有各的道理：

- **撞在变体层。** 高信号只有一处——文件名剥出来的**正题**是中文的，撞中文条目的中文名与别名。作品层手里只有 DAT 给的名字（多为英文/罗马字），而实测 Bangumi 条目里**只有 15.4% 带纯拉丁别名**，作品层自己撞，撞得上的不到六分之一。
- **简介、年份、开发商、发行商挂作品层。** 那是这些字段的定义（`AnchorKind::Work`：「跨平台跨地区都成立的东西挂这一层」）。挂到变体上就是同一部作品的每个变体各存一份相同的简介。
- **中文名与别名留在变体层**，与现在一致——依据说的是「这个文件的正题撞上的」。

因此中文离线源**在两层都参加**：变体层照旧撞、出中文名与别名，并把撞上的**条目号**作为结论的一部分；作品层不自己撞，读「这个作品下的变体撞到了哪些条目号」，取其中最多数的那一个，出作品级字段。

这要求作品层的刮削主体带上它名下变体的中文条目匹配结果，并且**变体层必须先于作品层采集**。具体怎么把这件事接进计划的构建，交给实现；规格只钉住「撞在哪、挂在哪、谁先跑」。

### 存储要多存几样

中文离线索引现在只落六样。要多落：**简介**、**类型**、**开发商**、**发行商**，以及 infobox 里那些为了拆值必须先解出来的东西。

这份存储是**可再生**的（同 DAT 库）：结构版本一变就从本地那份原件整份重建，不走顺序迁移，也不需要重新下载。结构版本要跟着这次改动往上走一格，让老索引自动重建而不是被将就着用。

### infobox 是一种自定义格式，按格式解

infobox 是 wiki 风格的键值块，值有两种形状：单值（`|游戏类型= ACT`）与多值块（`|别名={ [x] [y] }`）。多值要拆成多条，单值里的顿号分隔也要拆。缺键就是没有，不是错误——照常产出它有的那些字段。

### 报告那一节照实改

刮削报告的缺口一节不再说「离线档补不上简介、类型与开发商」。离线档补不上的只有**图**。同时报告要新增：这一趟中文离线源补上了哪几个字段、各多少条、按平台的覆盖，好让「老平台补不上是数据源浅」这件事看得见（挂账 D125 说的正是这个）。

### 置信与队列不放松

模糊匹配来的东西是**中置信**，不自动通过，照旧进**待确认队列**（挂账 D128 的口径不变）。新字段跟着同一条匹配走，所以它们与中文名同生共死：**对中文名下的裁决同时管住同一次匹配带来的其余字段**，不让用户对一次误撞裁决五遍。

### 输入指纹要盖住新东西

指纹现在盖了正题、平台、索引版本、匹配参数、DAT 条目名。新增的字段解析要跟着进指纹——否则改了解析逻辑重跑，缓存会一口咬定「输入没变」而整条跳过。`--refresh` 是兜底出口，但不该是常态。

### 导出侧不动

前端适配器已经在取 `Developer / Publisher / Genre / Description` 四个字段。刮削这边一产出，一路到导出都不用改。**这次改动的风险面因此只在刮削那一侧。**

### 长简介要有闸

实测最长 9,962 字。规格不定具体数值，但要求：存储与导出都不因为超长条目变得不可用，界面上的列表仍然滚得动。

## Testing Decisions

**好测试测外部行为。** 这份规格的外部行为是：「装一份带简介与 infobox 的中文离线索引，跑一趟离线刮削，那几个字段以中文离线源为源落到对的锚点上」。测的不是解析函数怎么写的。

### 主接缝（一个）：刮削的集成测试

沿用已有的那条路——`建现场 → 识别 → 刮削 → 值(现场, 锚点, 主体, 字段, 源)`。要钉住的行为：

- 简介、类型、开发商、发行商、年份**落在作品锚点上**
- 中文名与别名**落在变体锚点上**
- 这一趟**网络请求数为 0**（离线档只用本地源，已有测试 `离线档只用本地数据源` 是现成的对照）
- 撞不上中文条目的变体**一个字段都不产出**
- 字段级优先级仍然成立：中文离线源的标题配得上另一个源的年份（已有测试 `字段级优先级用一个源的标题配另一个源的年份` 是现成的形状）
- 同一部作品的两个变体撞到同一个条目时，作品锚点上**只有一份**简介
- 改了匹配参数之后重跑**真的重采**

这个接缝同时盖住解析、落库、产出、锚点归属、优先级五件事。**这是最高的那个接缝，主要行为全在这里钉。**

### 次接缝：infobox 解析的内联单元测试

沿用仓库已有的惯例（DAT 名字里那个汉化组抽取就是这么测的）。infobox 边界够多，值得在解析处单独钉：单值、多值块、顿号分隔、缺键、空值、键名里带空格。

### 不加第三个接缝

导出侧一行不改，再补一条到前端文件的端到端只是重测已有行为。

### 真机验收

规格要求实现方在用户那份真索引上跑一趟并报数：撞上的变体数、补上简介/类型/开发商/发行商各多少条、按平台的覆盖表、这一趟的网络请求数（应为 0）。**这些数字进 `docs/library-facts.md`**，与其他事实同一个格式。

## Out of Scope

- **图。** 数据源本身不含图片，这一条不在这份规格里，也不该被任何措辞暗示成能补上。
- **第二家中文数据源。** 挂账 D125 说的「只认一家」不由这份规格解决；但优先级表要留得下第二家的名字。
- **老平台的数据深度。** N64 仅 98 条、DC 仅 38 条是数据源本身的问题，不是匹配算法的问题。规格要求把它在报告里说清楚，不要求把它补上。
- **匹配算法本身。** 正题怎么剥、模糊匹配怎么打分、门槛定在哪，全部沿用现状。这份规格只改「撞上之后取什么」。
- **繁简折叠、罗马数字**（挂账 D121、D120）——同属匹配算法，不在这里。
- **导出侧的任何改动。**
- **在线源的任何改动**，除了报告里对它的描述要跟着改准。

## Further Notes

### 这件事是怎么被发现的

用户手上有一份维护多年的前端元数据（另一块盘上，10TB 主库里一份都没有）。抽出 193 条的样本一看：`description` 中位 1354 字、130 条超过 800 字、红/绿/蓝三条几乎逐句同构——**那是模型生成的**，可再生。`developer`/`publisher`/`genre` 各 193 条，刮削能做。`game:` 有 92.7% 逐字等于文件名去掉扩展名。**汉化组一条都没有。**

也就是说，用户想要的成色，正是这份规格要交付的东西——而且其中最大的一块（中文简介）本来就躺在本机，只是没人去取。

### 与「主库合并」那条线的关系

用户打算把两个主库按平台打散合流。那条线自有它的票，与这份规格**没有依赖**：这里改的是刮削从本地数据源取什么，与文件躺在哪块盘上无关。

先做这一份的理由是：合并之后要给 46,444 个变体从零造元数据，而这份规格决定了那批元数据的成色下限。

### 一句提醒

规格里所有覆盖率都来自 `dump-2026-09-01` 这一版的实测。数据源每周三更新，实现时若重新取过，数字会略有出入——**以实现时跑出来的数为准，别抄这里的**。
