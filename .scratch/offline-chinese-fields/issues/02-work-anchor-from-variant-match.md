# 02 — 作品层拿得到变体撞出来的中文条目

**What to build:** 游戏**类型**出现在**作品**这一层。同一部作品的两个变体撞到同一个中文条目时，作品锚点上**只有一份**类型，不是两份。

这一票立的是整份规格的骨架：**撞在变体层、挂在作品层**。

- 撞只能在变体层做——高信号只有一处，就是文件名剥出来的**正题**（中文的），拿它撞中文条目的中文名与别名。作品层手里只有 DAT 给的名字（多为英文/罗马字），而实测数据源里只有 **15.4%** 的条目带纯拉丁别名，作品层自己撞连六分之一都撞不上。
- 但简介、年份、开发商、发行商属于作品——那是作品锚点的定义（跨平台跨地区都成立的东西挂这一层）。挂到变体上就是同一部作品的每个变体各存一份重复内容。

于是中文离线源**在两层都参加**：变体层照旧撞、出中文名与别名，并把撞上的**条目号**留作结论的一部分；作品层不自己撞，读「这个作品名下的变体撞到了哪些条目号」，取其中最多数的那一个，产出作品级字段。

**这是整份规格里唯一牵动刮削主体形状的一条**：作品层的主体要带上它名下变体的匹配结果，且**变体层必须先于作品层采集**。用最简单的单值字段（`游戏类型`，覆盖率 99.7%）把这条路跑通。

### Q9 — 「变体层必须先于作品层采集」这条我没做成一条采集顺序约束

- **来自：** 票 `offline-chinese-fields/02`
- **类别：** 票没想到的第三种情况
- **在哪：** `crates/core/src/scrape.rs` 的 `WorkVariant`（新增）与 `Plan::build`、
  `crates/core/src/scrape/zh.rs` 的 `ChineseSource::work_hit` / `work_probe`
- **为什么没停线：** 票与规格钉的是「撞在哪、挂在哪、谁先跑」，而规格自己写了
  「具体怎么把这件事接进计划的构建，交给实现」。照字面做成「引擎先跑完变体锚点、
  作品锚点读变体撞完的结果」会**在第二趟静默毁数据**：第一趟采完之后变体那一层整片
  命中输入指纹（`known.get(source.name()) == Some(&input)` 那一支），`collect` 一次
  都不跑，作品锚点手里就是空的——引擎于是把上一趟好好的类型当成「这个源改主意了」
  清掉（`forget_scraped` 那一支）。
- **这张票实际做了什么：** 作品锚点带的是**够撞一次的那几样输入**（`WorkVariant`：
  变体键、主文件键、平台、DAT 条目）而不是撞完的结果，作品层自己现撞一遍。于是这一层
  **与采集顺序和缓存状态都无关**，同一份库跑几趟结果一样；作品层的输入指纹
  （`work_probe`）盖住名下每个变体的那几样，名下多一个变体、换个平台、多撞出一条 DAT
  条目都会重采。**代价说清楚**：已确认的变体一趟里撞两遍（自己一遍、它所属的作品一遍），
  那是一次内存里的倒排查表，而且第二趟起两边都被指纹跳过。计划里变体仍旧排在作品前面
  （`Plan::build` 的两个循环），只是**没有任何东西依赖这个次序**了。
  **另一笔代价是票 03 的复审量出来的**：`Plan::build` 给每个已确认变体的 DAT 条目在
  `WorkVariant` 里再 clone 一份，与 `slot.entries` 并存——真库 30,024 个已确认变体，
  这一层内存大致翻倍。不是错误（计划本来就整份在内存里），但真库上值得量一次。
  集成测试 `类型落在作品锚点上而且同一条条目只留一份` 第七条钉着「再跑一趟类型还在、
  `forgotten` 是 0」。
- **谁来裁：** 拿主意的人
- **状态：** open
- **收尾裁决：** **settled** —— 这条的决定已经落进代码，并有测试钉着。

### Q14 — 新建的中文索引不写 `schema_version`，下次升版会在下完 435 MB 之后硬报错

- **来自：** 票 `offline-chinese-fields/02`（`/code-review` 的产出）
- **类别：** 路过发现，不在范围内（是票 01 引进来的）
- **在哪：** `crates/core/src/zh/store.rs` 的 `prepare`（那句 `_ => {}`，约 295 行）；
  对照 `crates/core/src/catalog.rs:377` 那一侧的 `None` 分支是写版本号的
- **为什么没停线：** 它在**这张票一个字都没动过的文件**里——票 01 的 Q7 第 1 条把
  `prepare` 改成「打开一份旧索引什么都不毁」时，顺带删掉了原来
  `None => put_meta("schema_version", …)` 那一支（`git show 841a067^:…/store.rs` 的 181 行
  还有它），现在版本号只在 `replace` 末尾落盘。这张票的风险面按规格只该在刮削那一侧，
  而票的收尾指示是「只提交这张票动过的文件」。
- **这张票实际做了什么：** 没碰它，只把它记准：**症状**是「文件已建好、`replace` 还没跑过」
  的那一档（第一次 `romcat zh sync` 中途断网，或先跑了 `romcat zh find`）留下的库里
  `meta` 没有 `schema_version` 这一行；等 `SCHEMA_VERSION` 升到 3，`prepare` 读到 `None`
  → 既不走 `TooNew` 也不置 `rebuilding` → `CREATE TABLE IF NOT EXISTS` 对已存在的 v2 表
  一个字不改 → `reshape` 因为 `rebuilding.is_none()` 直接返回 → `replace` 在
  `INSERT INTO subject(… 新列 …)` 上硬报 `no column named`，而这一下**发生在下完
  435 MB 之后**——恰是票 01 的 Q4 想避免的那个失败。
  **改法就一行**：`_ => {}` 那一支里，`found` 为 `None` 时在 `execute_batch(SCHEMA)`
  之后补一句 `self.put_meta("schema_version", &SCHEMA_VERSION.to_string())?`。
