# 规格：界面重构为五屏，主库变成一组根

**Status:** ready-for-agent

**设计稿：** `.scratch/gui-redesign/prototype.html`（可点原型 + 交互 PRD，用户 2026-09-04 确认）

## Problem Statement

界面现在有三屏——**待确认队列**（默认开这屏）、**库浏览**、**子库**。用户的原话：

> 子库页面的操作逻辑看不懂，请系统性的整理过后再改进
> 待确认列表的操作交互方式根本看不懂，也不会操作

**三屏里两屏用不了。** 而且用户要的两件事——**在界面上加扫描目录**、**对筛出来的一批做刮削**——根本没有屏。

根因不在单屏交互，在信息架构：**这三屏是照命令行的命令结构切的**（queue / variants / sublibraries），于是它们成了**三种互不相通的选东西的办法**。用户在库浏览里筛好的东西没法变成子库；待确认队列里那个「点一行就是一条覆盖几百条的选择器」是个看不见的抽象；子库屏一屏塞了八样东西（子库列表、名字/路径/格式/容量/类别表单、规则增删、例外记撤、差量步骤表、容量账、同步、删除确认）且没有明显的先后顺序。

底下还压着三个更硬的问题：

1. **一份中立库锁死一个主库根。** 扫描时会主动拒绝换根（顶层条目重合度不够就报错）。用户手上有两块盘（一块 10 TB 无元数据、一块约 3 TB 有元数据），想统一管理，现在做不到。
2. **界面没有任何后台任务机制。** 扫一趟真库 **37.1 分钟**；点一下「排差量预览」窗口就僵住几秒，期间连「停下」都没有。
3. **待确认有 18,241 个变体。** 按 5 秒一条算是 **25 小时**，逐条处理不是可行路径。

## Solution

**五屏，各管一种活；选东西只有一个地方。**

| 屏 | 一句话 | 它不做什么 |
|---|---|---|
| **库** | 这个库由什么构成：**根** + **数据源** | 不浏览内容 |
| **浏览** | 找到这一批，然后对它施加操作 | 不管设备、不管任务 |
| **待确认** | 过完这一堆 | 不做自由浏览 |
| **子库** | 管住这几台设备 | **不选内容**——改选择跳回浏览屏 |
| **任务** | 排队、进度、可停、历史 | 不发起操作，只承接 |

三处结构性改变：

- **主库变成一组根。** 几块盘、几个目录加进同一个主库，扫完收进同一份中立库。变体的键变成「根名 + 相对路径」。
- **主列表按作品收敛**：10,978 行而不是 46,428 行。变体在详情面板里选。
- **待确认批优先**：按**依据形状**（源 / DAT / 置信度 / 哈希口径）自动分批，前 5 批盖住 14,657 条单候选里的 **12,223 条（83%）**。

以及一条贯穿全局的约定：**主列表的筛选就是子库的规则**，同一套语言。筛到满意按「存成子库」；子库屏点「改选择」跳回浏览屏、规则预填进筛选器。

## User Stories

**库屏 · 根**

1. 作为库主，我想在界面上添加一个扫描目录，这样我不必去命令行。

## Implementation Decisions

### 一、主库变成一组根

**这是唯一动到数据模型的改动，也是唯一要求重扫的改动。**

- 中立库从记录**一个** `library_root` 改为记录**一组根**，每个根有名字、路径、上次扫描的时刻与结果。
- **变体的键**从「相对根 + 路径」变成「**根名 + 相对根 + 路径**」。因此**路径锚**全部失效，**内容锚**不受影响。
- 扫描时那道「换根就拒绝」的闸改为**按根生效**：同一个根换了挂载点仍然要拦（那是防指错盘的），不同根之间互不干涉。
- 新加的根**不许落在已有根的内部**，也不许把中立库所在的工作目录圈进去。
- **主库只读**（ADR-0004）在这一层照旧：加根、扫描、移除根，一个字节都不写主库。
- 路径归一仍按 ADR-0020：键用 NFC，读盘用磁盘上的原始形态。

**为什么现在做**：真库里眼下 **0 条裁决、0 条人工纠正、1 个子库**。路径锚是空的，这是这个改动最便宜的一刻；等用户开始逐条裁决，代价就变成「赔上攒下来的判断」。

### 二、领域逻辑留在核心库

界面只画和转发（仓库现有的线）。这次要在核心库里长出来的能力：

- **作品级的浏览查询**：按作品分页取行，带上它的变体数、总容量、平台集合、元数据齐不齐、最高置信度。这是新的查询面，不是把变体表在界面里聚合。
- **规则语言扩展**：新增 `^以…开始`、`$以…结束` 两个运算符；子句从平铺的「且」改为**可嵌套的组**，每组有「全部满足 / 任一满足 / 都不满足」三种连接。旧的平铺规则要能原样解析（它等价于一个「全部满足」的顶层组）。
- **搜索排序**：一个内置的匹配质量排序（以搜索词开头 > 含有 > 别名命中 > 简介命中），权重不暴露给用户。它只作用于搜索框，不作用于**规则**——子库要的是集合不是顺序。
- **待确认的批分组**：一级按「源 × DAT × 置信度 × 哈希口径 × 候选数」，二级按目录或命名规律。既有的三个轴（按目录 / 按候选作品 / 按命名规律）保留为二级的可选分法。
- **刮削计划的估算**：给定一批锚点、一组字段、一组源、一种采法，算得出会发多少网络请求、大概多久。这是刮削计划本来就有的信息，只是没往外交。
- **收藏与合集**：同一套成员关系。成员落**沉淀库**，锚用**内容锚**；拿不到内容锚的退**路径锚**并如实标注。中立库里的合集是它的投影，重扫后照沉淀库重建。

### 三、长任务要能报进度、能停

核心库里几个长入口（扫描、识别、刮削、同步、排差量）统一接受一个**进度与取消的把手**：定期报进度、被要求停下时在**干净的地方**停（下次能接着跑，不留半截状态）。

界面侧的任务台只是这个把手的消费者：排队、显示、取消、留历史。**任务在核心库之外的线程跑，画帧那条线程一次都不阻塞**——这条正是挂账 D156 说的那件事。

### 四、裁决的撤销必须干净

批量优先的设计成立的前提是撤销可信。**`triage undo` 现在不回滚中立库那一半**（挂账 D102），必须补上：撤销一批之后，中立库与沉淀库两边都回到批量通过之前的样子。

### 五、刮削的语义如实呈现

刮削结果按「锚点 × 字段 × 源」三元组**并存**，没有覆盖。因此界面上：

- **采法**（补缺 / 重采）管的是跑多久、花多少配额。
- **优先级**管的是显示哪个值，**改它不需要重采**。
- **裁决与手工维护的元数据永远排在全部数据源之前**（`priorities.toml` 的第一条规则、ADR-0001），刮削面板上要把这句话常驻写出来。

### 六、媒体预览

- 图片（jpg / png）在详情面板里内嵌显示。
- 视频抽首帧当封面加一个播放标，点击交给**系统默认播放器**。抽帧走外部 ffmpeg，**找不到就退化成占位图标**——不当硬依赖，不新增 Rust 依赖，Windows 上不需要额外构建。
- 抽出来的首帧按内容哈希缓存在**媒体池**里，不重复抽。

### 七、界面骨架

- 五屏由左栏切换；窗口标题写明当前开的是哪一份库与哪一屏。
- 面板边界可拖，位置持久化在工作目录里（不是中立库——那是可再生的）。
- 置信度色条（行左边缘）与置信度标签在五屏里含义一致：高 / 中 / 低 / 还没识别。
- 不指定库时**如实报错**并给出三种给法，不退到合成数据（本轮已落地，保持）。

### 八、不动的东西

- **剥离规则**与**平台清单**继续走命令行。它们是规则编辑器，各自都是一块不小的界面，而且不是常改的东西。
- 命令行的全部能力保持可用。界面与命令行共用同一套核心库结论——命令行裁的界面看得见，反过来也一样。

## Testing Decisions

**好测试测外部行为。** 这份规格的外部行为分两层，各有一条**现成**的接缝，**不新增第三条**。

### 接缝一：核心库的集成测试

领域能力全在这一条上钉。要钉住的行为：

- 一份中立库装两个根，两边的变体互不覆盖；同一个根换挂载点仍然被拦；新根落在旧根内部被拒绝。
- 作品级查询：给定筛选，返回的作品行数、变体数、容量合计对得上；分页稳定。
- 规则语言：嵌套组的三种连接各自成立；`^` `$` 各自成立；**旧的平铺规则原样解析**。
- 搜索排序：以词开头的排在含有的前面；排序只作用于搜索，不作用于规则。
- 待确认分批：一级分组的批数与各批条数对得上真实数据；二级下钻的条数加起来等于一级；换样本每次不同但都在批内。
- 撤销：批量通过再撤销之后，中立库与沉淀库两边都回到原样。
- 收藏：落沉淀库、锚在内容上；删掉中立库重扫之后还在；文件改名之后还认得出；拿不到内容锚的如实标注。
- 刮削估算：给定一批锚点与一组源，算出的请求数与实际发出的一致；**只勾本地源时估算为 0**。
- 长任务：报得出进度；被要求停下时在干净的地方停，下次接着跑不重做已完成的部分。

### 接缝二：GUI 的 headless 测试

沿用已有的那条无窗口跑一帧的路。要钉住的是**状态转换**，不是像素：

- 五屏切换；不指定库时如实报错。
- 选中语义：选中作品行之后，批量操作作用于它全部变体；详情面板里选中变体之后，变体级操作只作用于它。
- 屏间跳转：子库屏点「改选择」之后，浏览屏的筛选器里预填的是那个子库的规则；「更新到子库」之后规则原样回去。
- 任务台：任务跑着时其余屏仍然响应；取消之后状态是干净的。
- 置信度色条：四档各自渲染出对应的标记。
- ffmpeg 不在时，视频位显示占位图标而不是报错。

### 真机验收

在用户那份真库上跑一遍并报数：两个根都扫得进同一份中立库、作品级列表的行数、待确认的一级分批数与前五批条数、一次刮削估算与实际的偏差、扫描任务中途取消再续跑的结果。**这些数字进 `docs/library-facts.md`**，与其他事实同一个格式、带日期。

## Out of Scope

- **剥离规则与平台清单的界面。** 继续走命令行。
- **在窗口内解码播放视频。** 要 ffmpeg 绑定，依赖涨一大截且 Windows 构建麻烦；抽首帧 + 系统播放器已经满足需求。
- **排序权重让用户自己配。** 搜索的匹配质量排序是内置的。
- **两个主库的物理合并。** 主库只读，工具不搬文件。加成两个根之后本来也不必搬。
- **跨库重复拷贝的普查。** 值得做，但不在这份规格里——它是一份独立的报告能力。
- **中文离线源取全字段**（`.scratch/offline-chinese-fields/`）。那 6 张票改的是刮削从本地数据源取什么，与界面无关，**可并行推进**。
- **在线源的任何改动。**
- **合成数据与实测开关。** 本轮已挪进默认关闭的 `demo` feature，保持。

## Further Notes

### 这套设计是怎么来的

一轮 `/grill-with-docs`，13 条决策，全部有真库数字支撑：

| 数字 | 它定死了什么 |
|---|---|
| 46,428 变体 → 10,978 作品 | 主列表按作品收敛，4.2 倍压缩 |
| 六成作品挂着不止一个变体 | 变体必须在详情面板里选得到 |
| 待确认 18,241 变体、25 小时 | 批优先，逐条只是兜底 |
| 其中 80.4% 只有一个候选 | 那不是「选哪个」是「对不对」，可以按批回答 |
| 前 5 批盖住 12,223 条（83%） | 二级分组的一级按依据形状分 |
| 扫一趟 37.1 分钟 | 任务台是基础设施不是一屏 |
| 裁决 0 条、人工纠正 0 条 | 换键形状现在几乎免费，晚做就贵 |
| 媒体池 9.5 GB：342 jpg / 98 png / **178 mp4** | 视频预览是真需求，不是可有可无 |

### 顺带收掉的挂账

- **D74** 合集没有任何建的办法 —— 收藏与合集同机制
- **D102** `triage undo` 不回滚中立库 —— 批量优先的前提
- **D154** 五个筛选之间只能「且」 —— 规则语言取代
- **D156** 差量预览僵住画帧线程 —— 任务台取代
- **D160** 媒体列得出但不显示图 —— 详情面板媒体区

### 一句提醒

设计稿 `.scratch/gui-redesign/prototype.html` 是**静态原型**，交互只演示导航、批展开与刮削面板。凡是原型与本规格文字冲突的地方，**以文字为准**——原型是为了让人看得见，不是实现的依据。
