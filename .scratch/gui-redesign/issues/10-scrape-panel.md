# 10 — 刮削面板与估算

**What to build:** 在浏览屏筛出一批，按「刮削选中…」，面板上四个旋钮定清楚要干什么，**按下去之前就看得见会发多少网络请求、大概多久**。

四个旋钮，两条轴分得清清楚楚：

| 旋钮 | 答的是 |
|---|---|
| **范围** | 对谁 —— 筛出来的这批，带条数，不可就地编辑（要改回筛选器改） |
| **字段** | **我要什么** —— 简介 / 类型 / 开发商 / 发行商 / 年份 / 媒体 |
| **源** | **花多少代价** —— 默认只勾本地源；勾联网源弹配额提醒 |
| **采法** | 跑多久 —— **补缺**（只采一个源都没给过值的）/ **重采**（绕过输入指纹全部重来） |

面板底部实时估算**请求数与耗时**，并常驻一句：**裁决与你手工维护的元数据不会被动。**

**要纠正的心智模型：** 刮削结果按「锚点 × 字段 × 源」三元组**并存**，没有「覆盖」这回事。「有值了但我想换一个」**不该靠重刮**——那是**优先级**的事，改一次排序、零成本、不重跑。面板上要让这件事说得出口。

### Q93 — `clear_scraped` 原先连**裁决**一起删，而 `--refresh` 现在压根不走它

- **来自：** 票 `gui-redesign/10`
- **类别：** 撞上的既有缺陷
- **在哪：** `crates/core/src/catalog/scrape.rs::clear_scraped`
- **为什么没停线：** 这一票的验收点名「裁决与手工维护的元数据不会被动，**行为上也要成立**」，
  修它正是这张票的正题。
- **这张票实际做了什么：** 裁决与刮削结论住在同一张 `scrape_value` 表里
  （源名是 `裁决`，`priorities.toml` 的第一条规则让它排在每条链最前）。而
  `clear_scraped` 是一句光秃秃的 `DELETE FROM scrape_value`——于是
  `romcat scrape --refresh` 会把用户在浏览屏上一个字一个字敲进去的元数据**一起删掉**，
  而那是重跑重建不出来的。**改成 `WHERE source <> '裁决'`**（`media_ref` 与
  `scrape_probe` 上没有裁决那一源的行，人写的是值不是采集记录，所以只有这一张表要设），
  钉住它的是 `crates/core/src/catalog/scrape.rs::整份清掉刮削结论时裁决一条都不删`。

  **收尾审查之后又走远了一步：`--refresh` 现在压根不清库**，它只是**不看那道输入指纹**
  （见 Q103）。于是「裁决不会被动」不再靠那句 `WHERE` 顶着，而是构造上的——重采这一趟
  一个 `DELETE` 都不发，只走 `put_scraped_within`，而它只在这一趟点名的字段之内替换。
  `clear_scraped` 留着，它仍然是「换一套源之后整份重来」的那把工具，只是不在重采这条路上了。
  行为两条测试各钉一遍：`crates/core/tests/scrape.rs::重采不碰裁决与手工维护的元数据`、
  `crates/gui/tests/library.rs::刮削走任务台而且裁决与手工写的元数据一个字都没动`。
  **命令行与界面一起改**，「行为与命令行一致」那条验收因此仍然成立。

### Q95 — 「这一趟要什么」进了输入指纹，而且**只在该进的地方进**

  作品那一格照旧由**全部**变体攒起来（名单、条目、代表变体），只是「这个作品要不要采」
  由范围里有没有它名下的变体说了算。理由有两条：作品层的中文匹配读的正是「名下变体撞到
  哪些条目号」（票 02），名单跟着范围抖动的话，同一部作品先刮一半再刮另一半会得出两个
  不同的类型与简介；而那份名单进**输入指纹**，抖动一次缓存就整片作废。
  代价是 `Plan::build` 眼下仍然读全库的变体与候选（范围只在最后过滤），**范围收窄省下的
  是采集与网络请求，不是建计划那一步**。真库上建一次计划是秒级的活，而它跑在任务台上
  （不在画帧那条线程），所以没就地优化。
- **谁来裁：** 收尾
- **状态：** open

### Q102 — 界面那条刮削装配与命令行是两份，只把会改结论的那几样并了

- **来自：** 票 `gui-redesign/10`
- **类别：** 实现取舍
- **在哪：** `crates/gui/src/scrape.rs::run` 对着 `crates/cli/src/main.rs::scrape`
- **为什么没停线：** 领域判断一条都不在界面那一层（ADR-0005 成立）——两边摆的都是**原料**
  （哪份优先级表、哪份中文索引、哪份裁决），而怎么用那些原料全在 `scrape::run` 里。
- **这张票实际做了什么：** 界面要跑一趟刮削，就得把命令行那一段装配再摆一遍：优先级表、
  中文离线索引（连结构版本对不上时的就地重建）、匹配裁决、网络句柄。**没有整段抽进核心**
  ——命令行那一侧缠着它自己的七八个开关（`--priorities` / `--name-rules` / `--manifest` /
  `--tuning` / `--online-budget` …）与一串 `eprintln!` 的说明，整段抽出来要连那些一起搬。
  **但凡会让两条路得出不同结论的，这一票都并了**：
  - **剥离规则**与**平台清单**原先界面这边写死用内置那份，改成走
    `sources::rules` / `sources::manifest`（把 `sources.rs` 里那两个私有查法公开）——
    正题正是拿去撞中文离线源的那串字，两边各用一份规则，同一个变体会撞到不同的条目，
    而那是**写进库里的结论**；
  - 匹配参数（`zh::Tuning`）两边都是 `default()`（命令行不给开关时就是它）；
  - **中文索引打不开是错，不是「少一层」**：库在、只是坏了或者比程序新时静悄悄跑下去，
    用户会对着一份缺简介的报告以为数据源就是这么浅。与命令行同一条口径。
  剩下的差别只有说明文字（命令行印 `eprintln!`，界面把同样的话摆在面板与回执里）。
  真要整段合，出口是给核心加一个「从工作目录装配一趟刮削」的入口，让命令行也改走它——
  那是一次独立的重构，不该塞进这张票。
- **谁来裁：** 收尾
- **状态：** open
