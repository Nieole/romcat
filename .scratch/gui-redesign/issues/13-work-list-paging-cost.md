# 13 — 作品级主列表的翻页代价

**What to build:** 让浏览屏那张表在真库规模上翻得快——眼下一次翻页的代价与库有多大成正比，而且搜索框里打了字之后还要再贵一倍出头。

两条挂单说的是同一件事的两半：

- **Q64**：主列表按**聚合列**排序。「这个作品有几个变体、合计多大、横跨哪几个平台」要先看过它的每一个变体，于是 `GROUP BY` 折成行、再按聚合出来的列排序，**两步都没有索引接得住**。变体表那一层每条 `ORDER BY` 都有一条索引正好接住（`variant_bytes_key` 那几条），一次翻页是索引倒着扫；作品级这一条不是。
- **Q108**：搜索那三条命中路（名字 / 标题集合 / 简介）在 `WHERE` 里是三条 `OR`，给每一行多加两次索引探查。实测（dev profile，合成数据 46,483 个变体收敛成 3,596 行）：不搜 `work_page` 208 ms，`work 0`（只有别名命中）425 ms。

**内存那一半一点没退**（一扇窗还是 512 行，`MAX_PAGE` 还在），涨的是每次翻页的时间。这张票要治的只是时间。

**先量再改。** 眼下手上的数一半是 release、一半是 dev，两者不可直接比（Q64 的表是 release，Q108 的是 dev）。第一步是在同一个 profile、同一份数据上把两条一起量一遍，得出「慢的到底是 `GROUP BY` 还是 `ORDER BY`，还是那三条 `OR`」。

**几条能走的路**（不预先定死，量完再挑）：

- 给作品级那几样聚合结果**落一张物化表**（变体一变就失效重算），把翻页变回一次索引扫。
- 只给**默认排序**（按作品名）铺索引，别的列排序照旧慢——真库上人多半不换排序。
- 搜索那三条 `OR` 拆成三次 `UNION ALL` 再去重，让每一条各自吃到自己的索引。

**不许动的**：一扇窗 512 行那条线、`MAX_PAGE`、以及票 03 立的「按当前筛选」口径。**主库只读**（ADR-0004）。

**Blocked by:** 无 —— 可立即开工

**Status:** ready-for-agent

- [ ] 同一个 profile、同一份数据上把 `work_total` / `work_page` 的代价量一遍，分得清慢在哪一步
- [ ] 数进 `docs/library-facts.md`，与其他事实同一个格式、带日期
- [ ] 真库规模（46,428 变体 → 10,978 行）上一次翻页的时间比现在明显短，报出前后两个数
- [ ] 搜索框里打了字之后的翻页代价与不搜时在同一量级
- [ ] 内存那一半不退：一扇窗还是 512 行，`window().retained()` 不涨
- [ ] 挂单 Q64、Q108 标为 resolved，写清走了哪条路
- [ ] 门禁命令全绿（带 `--all-features`）

### Q64 — 作品级主列表按聚合列排序，代价与库有多大成正比

- **来自：** 票 `gui-redesign/03`
- **类别：** 这一票新引入的代价（票只说「十万行级别下翻得动」，没说甩滚动条那一种）
- **在哪：** `crates/core/src/catalog/browse.rs::Catalog::work_page`
- **为什么没停线：** 这是「一个作品一行」这件事的**内在**代价，不是可以绕开的实现细节：
  「这个作品有几个变体、合计多大、横跨哪几个平台」要先看过它的每一个变体。变体表那一层
  每条 `ORDER BY` 都有一条索引正好接住（`variant_bytes_key` 那几条），一次翻页是索引
  倒着扫；作品级这一条要先 `GROUP BY` 折成行、再按聚合出来的列排序，两步都没有索引接得住。
  **内存那一半一点没退**（一扇窗还是 512 行，`MAX_PAGE` 还在），涨的是每次翻页的时间。
- **这张票实际做了什么：** 走「查询整个下推 + 每页再补两样」这条路——`GROUP BY` 与
  `ORDER BY` 全在 SQLite 里，「元数据齐不齐」与「最高置信度」这两样**排不了序**，
  所以只对这一页那几十行补（`fill_missing` / `fill_confidence`），不摊到全库上算。
  `work_total` 那一条也不连年份那张表——它只数行。实测（release，`--bench`）：

  | 主列表行数 | 常态滚动（每帧 3 行） | 一趟甩到底（每帧都读库） |
  |---|---|---|
  | 46,483 | 中位 **0.85 ms**（1,173 fps），240 帧读库 **1 次** | 中位 **114 ms** |
  | 100,000 | 中位 **0.74 ms**（1,344 fps），240 帧读库 **1 次** | 中位 **317 ms** |

  真库的形状比这两行都轻：46,483 个变体收敛成 3,596 行时，换一次筛选 **44 ms**、
  点开一行 **21 ms**、每帧中位 **3.26 ms**（`--bench-browse`）。上面那两行是**每个变体
  各自一行**的极端形状（合成数据一个作品都没认出来），也就是这条代价的上界。
- **值不值得治：** 常态滚动没问题，咬人的只有「拖着滚动条一路甩到底」那 3 fps。
  两条路：把窗口开大（读得少但一次读得更久，且现有测试拿「一千行与十万行内存里一样多」
  钉着窗口大小），或者甩的时候先画空行、松手再补（那是画法，不是查询）。
  两条都超出这张票。
- **谁来裁：** 票 `12`（布局可调与视觉一致性收尾）
- **票 `12` 裁定：不在这张票里做，升成新票 `gui-redesign/13`。** 它是**核心库的查询代价**，
  与「版式可调与视觉一致性」不沾边；而它与 `Q108`（搜索那三条命中路）是同一条代价线上的
  两半，分两张票各治一半只会各自量一遍。新票把两条合起来：先在同一个 profile、同一份数据上
  量清楚慢在 `GROUP BY` 还是 `ORDER BY` 还是那三条 `OR`，再挑路。
- **状态：** open（转 票 `gui-redesign/13`）
- **收尾裁决：** **由本票接着做** —— 它就是从这条挂单立起来的。

### Q66 — 浏览屏顶上那三个批量操作按钮还没画

- **来自：** 票 `gui-redesign/03`
- **类别：** 票之间的接缝（原型上有，这张票的验收里没有）
- **在哪：** `crates/gui/src/browse.rs::edit_panel`（作用范围那一行就是它们的位置）
- **为什么没停线：** 原型 `.scratch/gui-redesign/prototype.html` 的浏览屏抬头摆着
  「刮削选中…」「存成子库」「★ 收藏」三个按钮，而它们各自是票 `10` / `11` / `06`
  的正文。这张票的十条验收一个都没点到它们，票据也点名「详情面板里媒体那一块只留位置」。
- **这张票实际做了什么：** 把**它们要的那样东西**铺到位并钉住语义——
  `Catalog::scoped_variants` / `scoped_variant_total` 把「选中的这几行」展开成一串变体的键，
  界面上常驻一句「选中 N 条、作用于 M 个变体」，`Screen::batch_variants` 是三个按钮
  按下去该拿的那一批。按钮本身留给各自的票，**不提前画一个按了没反应的**。
- **顺带记一条给接它们的人：** `WorkAnchor::Work(id)` 里那个数是 `work` 表的行号，
  **重跑识别会把它换掉**（`clear_identifications` 整批删了重建）。眼下界面上还没有
  「重跑识别」这个按钮，所以咬不到人；哪张票把识别接上任务台，就要在那一趟跑完之后
  把浏览屏的选中与点开的那一行一起丢掉，否则批量操作会打到另一个作品头上。
- **谁来裁：** 票 `06` / `10` / `11` 各接一个
- **状态：** open
- **收尾裁决：** **由本票接着做** —— 它就是从这条挂单立起来的。

### Q108 — 搜索那三条命中路让一次翻页贵了一倍出头，与 Q64 在同一条代价线上

- **来自：** 票 `gui-redesign/05`
- **类别：** 这一票新引入的代价
- **在哪：** `crates/core/src/catalog/browse.rs::Search::filter`（`WHERE` 里那三条 `OR`）
- **为什么没停线：** 常态还在可用范围里，而且它与 Q64 是同一件事的两半——作品级主列表
  本来就要扫全表再 `GROUP BY`，搜索只是给每一行多加两次索引探查。
- **实测**（**dev profile**，合成数据 46,483 个变体收敛成 3,596 行；Q64 那张表是 release，
  两者不可直接比）：

  | 搜索词 | 命中行数 | `work_total` | `work_page`（一页 512） |
  |---|---|---|---|
  | 不搜 | 3,596 | 107 ms | 208 ms |
  | `幻想`（名字命中） | 359 | 240 ms | 301 ms |
  | `work 0`（只有别名命中） | 10 | 238 ms | 425 ms |
  | `外星人`（一条都不命中） | 0 | 270 ms | 296 ms |

  最后一行是**上界**：三条 `EXISTS` 每一行都跑满了才得出「一条都没有」。
- **已经做掉的那点便宜：** 三条 `OR` 按**从便宜到贵**排（名字 `LIKE` → 标题集合 →
  简介），SQLite 的 `OR` 短路求值，名字命中的行根本走不到后两条。
  `title` 那条走主键 `(work, …)` 的前缀，`scrape_value` 那条走 `scrape_value_subject`
  索引——两条都不是全表扫。
- **值不值得治：** 眼下不治。真要治，路是**给搜索加一次防抖**（界面上打字每一个字符
  都换一次查询，而这一层每次换查询要跑三条全表查询：`work_total`、
  `scoped_variant_total`、`work_page`），那是**界面**那一侧的事，不是这条查询的事，
  而且它同样会让「换筛选」那条路一起受益。没在这一票加，因为票据没点它，
  而且防抖要定一个时长——那是个产品决定。
- **谁来裁：** 票 `12`（布局与一致性收尾）或收尾
- **票 `12` 裁定：不在这张票里做，与 `Q64` 合起来升成新票 `gui-redesign/13`。**
  两条是同一条代价线上的两半——作品级主列表本来就要扫全表再 `GROUP BY`，搜索只是给每一行
  多加两次索引探查。而眼下手上的两组数一半是 release 一半是 dev，**不可直接比**，
  新票头一件事就是在同一个 profile、同一份数据上重量一遍。
- **状态：** open（转 票 `gui-redesign/13`）
- **收尾裁决：** **由本票接着做** —— 它就是从这条挂单立起来的。
