# 13 — 作品级主列表的翻页代价

**What to build:** 让浏览屏那张表在真库规模上翻得快——眼下一次翻页的代价与库有多大成正比，而且搜索框里打了字之后还要再贵一倍出头。

两条挂单说的是同一件事的两半：

- **Q64**：主列表按**聚合列**排序。「这个作品有几个变体、合计多大、横跨哪几个平台」要先看过它的每一个变体，于是 `GROUP BY` 折成行、再按聚合出来的列排序，**两步都没有索引接得住**。变体表那一层每条 `ORDER BY` 都有一条索引正好接住（`variant_bytes_key` 那几条），一次翻页是索引倒着扫；作品级这一条不是。
- **Q108**：搜索那三条命中路（名字 / 标题集合 / 简介）在 `WHERE` 里是三条 `OR`，给每一行多加两次索引探查。实测（dev profile，合成数据 46,483 个变体收敛成 3,596 行）：不搜 `work_page` 208 ms，`work 0`（只有别名命中）425 ms。

**内存那一半一点没退**（一扇窗还是 512 行，`MAX_PAGE` 还在），涨的是每次翻页的时间。这张票要治的只是时间。

**先量再改。** 眼下手上的数一半是 release、一半是 dev，两者不可直接比（Q64 的表是 release，Q108 的是 dev）。第一步是在同一个 profile、同一份数据上把两条一起量一遍，得出「慢的到底是 `GROUP BY` 还是 `ORDER BY`，还是那三条 `OR`」。

**几条能走的路**（不预先定死，量完再挑）：

- 给作品级那几样聚合结果**落一张物化表**（变体一变就失效重算），把翻页变回一次索引扫。
- 只给**默认排序**（按作品名）铺索引，别的列排序照旧慢——真库上人多半不换排序。
- 搜索那三条 `OR` 拆成三次 `UNION ALL` 再去重，让每一条各自吃到自己的索引。

**不许动的**：一扇窗 512 行那条线、`MAX_PAGE`、以及票 03 立的「按当前筛选」口径。**主库只读**（ADR-0004）。
