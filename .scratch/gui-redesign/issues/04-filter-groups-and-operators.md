# 04 — 筛选器：嵌套分组与两个新运算符

**What to build:** 在浏览屏上用**可嵌套的条件组**筛库：每组选「全部满足 / 任一满足 / 都不满足」，组里可以再套组。筛到满意按「存成子库」，条件原样变成那个子库的**规则**。

**筛选器就是规则语言**，同一套东西两处用。这一票要做的是把它补齐：

- 新增两个运算符：`^ 以…开始`、`$ 以…结束`

- 维度补上**收藏**，以及元数据齐了之后的开发商、发行商、简介

**旧的平铺规则要原样解析**——它等价于一个「全部满足」的顶层组，已存的子库不该因为这一票失效。

- **来自：** 票 `gui-redesign/04`
- **类别：** 规格没说（验收第 5 条要求「原样变成规则」，但屏上有条件规则表达不了）

  多，而那正是这条约定要消灭的东西。测试

### Q71 — 括号：读得进来的比写得出去的宽，界线划在 `parse` 与 `build` 之间

- **来自：** 票 `gui-redesign/04`（这一条在收尾审查里改过一版，见下）
- **类别：** 规格没说（新语法与已有数据的边角）
- **在哪：** `crates/core/src/sublibrary/rule.rs`（模块文档那两节、`opens_group`、
  `matching`、`split_items`、`Clause::build`）
- **为什么没停线：** 组要嵌套就得有分界符，而作品名里带括号是常态
  （`Pocket Monsters (Japan)`），**而且未必配对**（`口袋妖怪(日` 这种截断的名字）。
- **走的是哪条路：** `(` **只在一项的开头**（前面那一段去掉空白之后是空的、或者正好是

  数括号那件事由 `opens_group` 一处说了算，`split_items` 与 `matching` 两处共用它

    **不许有两侧带空白的连接词**，**括号得配对**。因为它造出来的东西马上要被
    `Rule::from_group` 印成一行字存进中立库，而印出去读回来必须还是它自己。
- **剩下的那点边角**：一个值里带落单 `)` 的**老**子句，若被手写进一个组里

  够不着这条路；新造的一律过 `build` 那道闸。
- **要根治得加转义**（`\(`）或者引号包值，两样都会让手写规则变难看。眼下真库里没有
  这种作品名，先不加。

### Q72 — 年份那一维在两个求值器里的「读不成数就扔掉」是两套写法对齐的

- **来自：** 票 `gui-redesign/04`
- **类别：** 执行里冒出来的（同一条语义要在 Rust 与 SQLite 里各写一遍）
- **在哪：** `crates/core/src/catalog/filter.rs::YEAR_VALUE` / `RATING_VALUE` 对
  `crates/core/src/sublibrary.rs::ScrapedInto::absorb`
- **为什么没停线：** 刮来的年份是字符串，里面有 `199X` 这种写法。内存那一侧是
  `value.trim().parse::<i32>()`——读不成就扔掉；SQL 那一侧 `CAST('199X' AS INTEGER)`
  会读成 `199`。两边不一样的话，屏上筛出来的与同步搬过去的就差那几条。
- **这张票实际做了什么：** SQL 那一侧加一条「**转回文字还是原样**」的闸
  （`trim(value) = CAST(CAST(trim(value) AS INTEGER) AS TEXT)`），正好把读不成整数的值
  挡在外面。`crates/core/tests/filter.rs` 的 fixture 里特意塞了一条 `199X`，
  六条年份规则各跑两遍比键。
- **还有一条对不齐的边角**：`+1990` 这种带正号的写法 Rust 读得出、这条闸读不出。

### Q73 — 左栏上下两半在做同一件事：五个一按就有的档，与那棵条件组

- **来自：** 票 `gui-redesign/04`
- **类别：** 票之间的接缝（布局与视觉收尾是票 `12`）
- **在哪：** `crates/gui/src/library.rs::filter_panel`
- **为什么没停线：** 平台 / 合集 / 语言 / 中文这四个档，条件组里都写得出来
  （`平台=GB`……）。两套并存，等于同一件事有两个地方点。
- **为什么眼下留着两套：** 那四个档**各自带着条数**（`Catalog::facets` 一次 `GROUP BY`
  问出来），而条件组里的值是打出来的——没有条数的下拉框，人只能一个个点开试。
  一按就有的那一半是**探索**，条件组是**表达**，两件事。而且把四个档折进条件组
  要重做票 03 的 `WorkQuery` 形状与它那一批测试，风险与收益不成比例。
- **代价说清楚**：「存成子库」时两半都要折进同一条规则（`WorkQuery::to_rule` 做的），
  多一处会漏的地方；`识别状态` 那一档还折不进去（Q70）。
- **谁来裁：** 票 `12`（布局与视觉收尾）——要么把四个档做成「点一下就往条件组里加一条
  子句」的快捷键，要么明确两半各管一段并在屏上说清。
- **票 `12` 裁定：走第二条路——两半各管一段，在屏上说清。**
  不把四个档折进条件组：那要重做票 03 的 `WorkQuery` 形状与它那一批测试，而收益是
  「少一个地方点」；也不做成「点一下就往条件组里加一条子句」的快捷键：那会让**带条数的那一半
  当场失去意义**（加进条件组之后，那个值就变成打出来的了，条数没了）。
- **屏上眼下写着：** 上半的抬头是「**一按就有的档**」，副题「各带着条数——点一下就知道
  库里有多少」，悬停里写明它是**探索用的那一半**、「识别状态」这一维只在这儿有；
  下半的抬头从「筛选器」改成「**条件组**」，副题「值要自己打——说得清楚，也存得成子库的
  规则」，悬停里写明它是**表达用的那一半**，以及上头那五个档存成子库时会折进同一条规则里
  （「识别状态」折不进去，`Q70`）。
- **状态：** resolved
- **收尾裁决：** 已在队列进行中裁决过（见本条原有的状态行）。

### Q74 — 规则语言里**没有**按路径匹配的维度，所以票 02 那条键形状的改动咬不到它

- **来自：** 票 `gui-redesign/04`
- **类别：** 核对过的、确认不用改的（但下一个人会问同一个问题）
- **在哪：** `crates/core/src/sublibrary/rule.rs::Dimension`
- **为什么记下来：** 票 02 把**变体的键**改成了「根名 + 相对根的路径」，挂单 Q58 说
  「`--under` 那类前缀从此带根名」，而这张票的硬约束点名「规则语言里凡是按路径前缀
  匹配的地方都受这条影响」。**核对结果：一处也没有。** 十三个维度筛的是平台、语言、
  中文、合集、收藏、类型、作品名、年份、评分、体积、开发商、发行商、简介——
  没有一维读变体的键。ADR-0020 的 NFC 归一管的是**路径键**，规则里的值不是路径键
  （作品名来自 DAT 条目，平台名来自平台清单）。
- **但 `^ 以…开始` 让「按根筛」变成一个自然的期待**：`键^卡二/` 这种写法眼下写不出来
  ——**键**与**根**都不是维度。浏览屏上按路径找那条路走的是**搜索框**
  （`VariantQuery::contains`，按 `variant.key` 取子串），而搜索框进不了规则（Q70）。
  于是「把某一块盘上的东西存成一个子库」眼下只能靠平台或合集绕。
- **要加是件小事**：一维 `根`（或 `键`），`VariantFacts` 多一列、`filter.rs` 里一条
  `variant.key LIKE ?`。没在这一票加，因为票据没点它，而且加一维**路径**会把
  「规则选的是内容」这条语义撑开一个口子——路径是内容住在哪儿，不是内容是什么。
- **谁来裁：** 票 `11`（子库屏；「这块盘上的全部」是不是个真需求，那一屏最看得出来）
- **状态：** settled —— 票 `11` 的裁决：**不加，明确留给将来。**
  子库屏重做完之后那一屏上**没有一个动作需要按根筛**：卡上每一格问的都是「送到哪」
  （目标路径、前端格式、容量条三段、待同步步数），要什么内容整个搬去了浏览屏。
  于是「这块盘上的全部」是个**浏览**的问法，不是子库的问法——而浏览屏上按路径找走的
  是搜索框（`VariantQuery::contains`，按 `variant.key` 取子串），它进不了规则是 Q70
  已经裁过的事。硬要加一维 `根`，会让「规则选的是内容」这条语义破一个口子：
  路径是内容住在哪儿，不是内容是什么；而一个游戏从甲盘挪到乙盘之后，一条按根写的规则
  会**悄悄换掉下次同步的那一批**——与 Q70 挡掉「识别状态」是同一条理由。
  还有一条硬的：票 `11` 的硬约束点名「票 04 的规则语言不许顺手改形状」，加一维正是改它。
  **真要按盘分卡，眼下的路**：按平台或合集绕；或者在浏览屏上把那几个变体记成
  **例外**（这一票把例外的加减搬到了浏览屏的详情面板上，指得准哪一份）——
  但那是几个的量级，不是整块盘的量级。哪天真有「按盘分卡」的需求，
  开成一张新票，连 `根` 这一维与搜索框进规则那件事一起想。
- **收尾裁决：** 已在队列进行中裁决过（见本条原有的状态行）。

### Q75 — `/code-review high` 报的四条，四条当场收掉

- **来自：** 票 `gui-redesign/04` 的收尾审查
- **类别：** 审查发现
- **在哪：** 见每一条后面的落点
- **为什么没停线：** 全部在这张票的范围之内，改动都不大，而且第 1 条正是这张票立的那条
  硬约束（屏上筛出来的那批 ＝ 同步搬过去那批）被打破的地方。
- **这张票实际做了什么：**
  1. **高 · 界面搭出来的规则存进子库会变成另一条** —— `Clause::build` 对值不做任何
     检查，而 `Rule::from_group` 把值原样拼进那行文本。在「作品 ~」那格里打
     `RPG 且 平台=GB`，屏上按**一个**子句筛（求值走的是内存里那棵树），存进中立库那行字
     下次读回来却是**两个**子句；`生存 或 毁灭`、`Pocket Monsters (Japan` 更是直接读不
     回来，落成 `BrokenRule`，那个子库一条都选不中。**而且静默。**
     `Clause::build` 加两道闸（值里不许有两侧带空白的连接词、括号得配对，新增
     `RuleError::JoinerInValue`），`Clause::parse` 那条路**不加**——它读的是库里已经
     躺着的规则（见 Q71）。
     审查顺带发现的**回归**一并收掉：`split_items` 原先全层数括号，把这一票之前合法的
     `作品~口袋妖怪(日` 变成了 `UnbalancedParen`。改成只认**项开头**那个 `(`
     （`opens_group` 一处说了算，`matching` 与 `split_items` 共用），老规则原样读得懂。
     测试：`rule.rs::值里落单的括号不影响这一层怎么切`、`造一条新子句时挡住印出去会走样的值`、
     `造出来的子句套进组里印回去还是它自己`。
  2. **中 · `facet_clause` 只挡逗号** —— 合集名是用户自己起的，「送朋友的 或 备份」
     「口袋(日版」都合法，折成规则后与第 1 条同样的后果。新增 `Unruly::Unwritable`，
     把 `Clause::build` 那两道闸翻成一条说得出口的话。测试补在
     `crates/core/tests/filter.rs::写不成规则的条件当场挡住而不是悄悄少写一条`。
  3. **中 · 建子库不是原子的** —— `save_as_sublibrary` 先 `put_sublibrary` 再
     `add_rule`，后一步失败会留下一个**一条规则都没有**的子库（同步过去是空的），
     而那个名字从此被重名检查占着，人按原名重试还被挡。改成失败就
     `remove_sublibrary` 退回去，并在回执里说清名字还回来了没有。
  4. **低 · 评分那一维两个求值器会分家** —— `YEAR_VALUE` 有「转回文字还是原样」那道闸，
     `RATING_VALUE` 没有对应的一手：`CAST('优秀' AS REAL)` 给 `0.0`（落在 0–1 里！）、
     `1.5` 照收，而内存那侧的 `parse_rating` 两种都扔掉。于是 `评分<=0.5` 在 SQL 那侧
     会把一批评分写成非数字的变体选中。补上「里面得有个数字」与「落在 0–1 之间」两道闸，
     测试 `crates/core/tests/filter.rs::评分那一维读不成数与超出范围的值两边都得扔掉`
     手塞三条值验它（真库里眼下一条评分都没有，挂账 D68）。
- **审查另外核对过、确认不用改的：** 各维在取不到值时都落 `COALESCE(…,0)`、`!=` 用
  `NOT COALESCE(…)` 翻过来，与 `satisfies` 的骨架逐条对得上；大小写折叠两侧都是
  `to_ascii_lowercase` / SQLite `lower()`（这一处审查途中刚从 `to_lowercase` 改过来）；
  语言两头补逗号之后四个运算符对应四种 `instr`，`en` 撞不上 `Danish`；`negate()` 的
  拍平规则与 `render_group` 的加括号规则互为逆（手推了 8 种组合）；旧平铺规则的
  `split_items` 行为与老 `split_clauses` 一致。
- **谁来裁：** 收尾
- **状态：** open
- **收尾裁决：** **settled** —— 这条的决定已经落进代码，并有测试钉着。
