# 03 — 浏览屏：作品级主列表与详情面板

**What to build:** 主列表一个游戏一行——**10,978 行**，不是 46,428 个变体。点开一行，右边详情面板摆出它包含哪几个变体、每个变体有哪些文件、各自的置信度与依据。

元数据本来就锚在**作品**这一层，所以这个粒度与数据模型天然对齐。六成作品下面挂着不止一个变体，它们在详情面板里选。

**选中语义**是这一票要钉死的东西：
- 选中主列表的行 = 选中这些**作品**；批量操作作用于它们的**全部变体**
- 在详情面板里选中某一个**变体** = 变体级的操作只作用于它

主列表能按作品名、平台、变体数、容量、年份排序，能多选与全选。

**这是十二票里最重的一条。** 若做到一半发现塞不进一个上下文，先把主列表交付完整（能翻、能排序、能多选），详情面板另起一张票——但**不要两边都做半截**。

### Q65 — 「元数据齐不齐」与「最高置信度」的口径是这一票现定的

- **来自：** 票 `gui-redesign/03`
- **类别：** 票没说到那一层（票只写「每行看得见……元数据齐不齐、最高置信度」）
- **在哪：** `crates/core/src/catalog/browse.rs::WORK_FIELDS`、`Catalog::fill_confidence`
- **为什么没停线：** 两条都有现成的 ADR 给出方向，只是没人写死过具体那几样。
- **这张票实际做了什么：**
  - **齐不齐看五样**：年份、发行商、开发商、类型、简介（`WORK_FIELDS`）。**标题不算**
    ——叫法是个集合不是单值（`catalog::title`），缺不缺由标题集合自己答；**汉化组也不算**
    ——它挂在**变体**上（ADR-0012），拿它当作品级的缺口会让一整排原版游戏都显示成「缺」。
    锚点两支分开看：认出作品的看**作品**锚点，没认出来的看**变体**锚点，与
    `adapter::converge` 挑值时同一条岔路——于是屏上写着「齐」的那一行，导出时真填得满。
  - **最高置信度**看的是这一行**当前筛选下**那些变体上的**全部候选**（不只自动通过的那些），
    取最高的一档；一条候选都没有是 `None`，画成**还没识别**——那是独立的一档，
    不是「撞过没撞上」（ADR-0002）。
  - **年份**取「裁决优先，其次各源里最早的那一个」：裁决排在每个字段最前是优先级表的
    第一条规则（ADR-0001），而一部作品跨地区先后发行好几次，最早的那次才是它的年份。
    列表与详情面板走同一条取法（`Catalog::work_year`），两处写的是同一个数。
- **谁来裁：** 票 `10`（刮削面板要选「刮哪些字段」，那份字段清单该与这五样对齐）
- **状态：** open
- **收尾裁决：** **settled** —— 这条的决定已经落进代码，并有测试钉着。

### Q67 — `/code-review` 报的四条，四条当场收掉

- **来自：** 票 `gui-redesign/03` 的收尾审查（`/code-review high`）
- **类别：** 审查发现
- **在哪：** 见每一条后面的落点
- **为什么没停线：** 全部在这张票的范围之内，改动都小。
- **这张票实际做了什么：**
  1. **中 · 点一下表头换排序就把选中静默清空** —— `sync_window` 拿整个 `WorkQuery`
     比相等，而它含 `order` / `descending`。人勾了两百行再按一下「容量」表头，筛出来的
     还是同一批行，选中却没了。判据拆成两条：**换排序**只丢高亮（那是个全序下标，
     重排之后会指到另一行身上），**换筛选**才连选中一起丢（全选说的「当前筛出来的
     这一批」已经不是同一批）。哪几个字段算筛选是查询面自己的事，所以判断落在核心库
     （`WorkQuery::same_filter`）。测试补在
     `crates/gui/tests/browse.rs::多选与全选可用而且屏上看得见选中多少条`。
  2. **中 · 「作用于多少个变体」把读库错误吞成 0** —— `scoped_variant_total` 那一处
     `unwrap_or(0)` 恰好把它自己那段文档说要防的事做了出来：屏上写着「作用于 0 个变体」，
     按下去真会动一百多个。`scope` 改成 `Option<u64>`，数不出来就画「？」并把错落进
     `error`（`Screen::scope_label`）。
  3. **低 · 实测那一行把两个不同口径的数并在一起** —— `BrowseCost::rows` 是**没筛之前**
     的行数，`variants` 是**筛完之后**全选展开出来的变体数，`render()` 却把它们并成
     「N 行作品（M 个变体）」。改成与 `filtered` 配对：「全选展开范围 … ms（筛完那 N 行
     → M 个变体）」。
  4. **低 · 一条测试断言的其实是「一个变体的每条候选置信度都相同」** ——
     `assert_eq!(variant.confidence(), Some(candidate.confidence))` 摆在遍历全部候选的
     循环里。眼下只因合成数据每个变体的候选同档才过；真库上一个变体撞上一条高一条低
     是常态，那条会在**正确**的实现上炸。改成 `<=`（`Confidence` 的 `Ord` 里 `High` 最小，
     行上那一档是 `min`）。
- **审查另外核对过、确认不用改的：** `work_page` / `fill_confidence` 的参数绑定次序与
  SQL 文本里 `?` 的出现次序一致；`Confidence` 的 `Ord` 是 `High < Medium < Low`，
  `.min()` 取到的确实是最高那一档；`scoped_sql` 里 `COALESCE(work_id IN (…), 0)` 那层
  裹得对，全选减例外不会漏掉没认出作品的那些行；表格第一列那个复选框在 egui 的命中
  判定里排在单元格之后注册，会赢下点击，不会被行响应吃掉。
- **谁来裁：** 收尾
- **状态：** open
- **收尾裁决：** **settled** —— 这条的决定已经落进代码，并有测试钉着。
