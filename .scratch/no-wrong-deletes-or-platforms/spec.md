# 移除根、改选择与裁决过的平台不再出错

**Status:** ready-for-agent
**Opened:** 2026-09-23（`/settle` 第五轮收口 → `/grill-with-docs` → `/to-spec`）
**来源：** 挂单 `Q555` `Q1184` `Q602`；已裁定的形状见同目录 `grill.md`

## Problem Statement

三处**错**，不是取舍——每一处都让库里留下的东西和人以为的不一样：

1. **移除一个根，刮削那一层没跟着走。** 人在库屏上移除一个根，那个根底下变体的刮削结论、媒体引用、
   采集记录一行都没删掉。刮削报告因此多报「有刮削结论的锚点」，媒体引用里留着指向已经不在的变体的行。
   根被加回来时，这些陈年结论又会冒出来，像是刚采过的。
2. **「改选择」会清掉同一台的别的规则。** 一台子库现在可以收好几条规则、各有名字。人在子库屏按
   「改选择」、到浏览屏调完按「更新到子库」，回来那一台只剩一条没名字的规则——**别的规则连同它们的
   名字一起没了**，屏上没说一个字。选出来的变体也许还是那批，但人亲手起的名字和分开的几条再也找不回来。
3. **人裁决过的变体，平台判错。** 一张 GB 卡带放错在别的平台目录里，人已经裁决过它是哪个发行版。
   识别在读卡带头之前就因为「裁决过了」短路返回，于是平台按**目录声明**判——刮削照旧按错的平台去撞，
   撞不上；而同一张卡要是没被裁决过，反而判得对。**人越认真裁，结果越错。**

## Solution

1. 移除一个根时，那个根底下**变体**的刮削结论、媒体引用、采集记录一并删掉；**作品**那一层、别的根的
   一条不动。
2. 「改选择」只在不会丢东西的时候走得通：
   - 这一台**一条读得懂的规则都没有**：更新到子库时新添一条。
   - **恰好一条**：更新到子库时只换这一条的条件，**名字与序号照旧**，读不懂的那几条原样留着。
   - **两条以上**：「改选择」变灰，理由写在旁边——「这一台有 N 条规则，用规则行上的 ✎ 逐条改」。
     永远不会悄悄把几条并成一条。
3. 裁决短路之后，平台照样按内容判：先取中立库里算过的卡带头，取不到就把头读出来（只读判平台所需的那
   几十字节，读完落库，下一趟不再读），再按内容重算平台。「裁决过的东西一个字节都不必再读」那句话改成
   「裁决过的东西只读判平台所需的头」。

## User Stories

1. 作为维护主库的人，我想移除一个根之后，那个根底下变体的刮削结论一条都不剩，这样刮削报告的数只数还在的东西。
2. 作为维护主库的人，我想移除一个根之后，媒体引用里不再有指向已经不在的变体的行，这样导出与同步不会去找不存在的媒体。
3. 作为维护主库的人，我想移除一个根之后，那个根的采集记录也清掉，这样把根加回来时刮削会当它们没采过、重新采。
4. 作为维护主库的人，我想移除一个根时**作品**那一层的刮削结论原样留着，因为别的根的变体也挂在同一个作品下。
5. 作为维护主库的人，我想移除一个根时别的根底下变体的刮削结论一条不少，这样移除只动我点名的那个根。
6. 作为维护主库的人，我想「移除之前看见的代价」与「事后报出来的」照旧是同一个数，这次修正不改变那笔账的口径。
7. 作为维护主库的人，我想移除一个根照旧不碰主库一个字节（ADR-0004）。
8. 作为管子库的人，我想一台只有一条规则时按「改选择」→「更新到子库」，那一条的名字还在，这样我起的名字不会被一次调整抹掉。
9. 作为管子库的人，我想一台只有一条规则时改完序号不变，这样报告里的「第 2 条」还是那一条。
10. 作为管子库的人，我想一台还没有规则时「改选择」→「更新到子库」照旧能给它添上第一条。
11. 作为管子库的人，我想一台有两条以上规则时「改选择」是灰的、旁边说清为什么、该用哪颗按钮，这样我不会一按就把几条并成一条。
12. 作为管子库的人，我想灰着的「改选择」说出这一台有几条规则，这样我知道要逐条改几次。
13. 作为管子库的人，我想规则行上的 ✎ 照旧逐条改、只换那一条，这是多条规则时改选择的正路。
14. 作为管子库的人，我想读不懂的那几条规则不算进「几条」，也不被任何一条回程碰到，这样还没修的东西不会被顺手清掉。
15. 作为管子库的人，我想「改选择」→「不改了」照旧什么规则都不写。
16. 作为裁决过变体的人，我想被裁决过、放错目录的卡带照样按卡带头判平台，这样刮削按对的平台去撞。
17. 作为裁决过变体的人，我想裁决过的变体与没裁决过的同一张卡判出同一个平台，这样裁决不会让结果变坏。
18. 作为裁决过变体的人，我想卡带头已经在中立库里算过时一个字节都不再读盘，这样重跑识别照旧便宜。
19. 作为裁决过变体的人，我想卡带头没算过时识别只读那几十字节的头、读完落库，下一趟不再读。
20. 作为裁决过变体的人，我想关掉「允许回盘读」时识别一个字节都不读主库，取不到缓存就照旧按目录声明判，这样开关说的话算数。
21. 作为裁决过变体的人，我想这一次顺手读头**不产出候选**——人已经裁过了。
22. 作为裁决过变体的人，我想裁决说的发行版、汉化组、第几版一样不被这次重算平台改动。
23. 作为看刮削报告的人，我想裁决过的变体按判定的平台出现在报告里，与刮削实际取的平台一致。
24. 作为看库体检的人，我想「平台不符」那一格把裁决过、放错目录的卡带也数进去，这样它不会因为被裁过就从体检里消失。
25. 作为后来读代码的人，我想「裁决过的只读判平台所需的头」这句话写在它生效的那一处，Switch 那条例外与这一条是同一个口径。

## Implementation Decisions

- **移除根（核心库目录模块的移除根那一步）**：刮削三张表按锚点存——锚点种类（「变体」／「作品」）住一列、
  键住另一列。删的时候按**锚点种类是「变体」、键以这个根的前缀开头**删；三句一起改。「作品」那一层照旧不删。
  「移除之前看见的代价」（`root_removal`）不数刮削那三张表，口径不变。
- **「改选择」的三档**（界面子库屏 + 浏览屏的编辑回程）：
  - 子库屏按下「改选择」时数这一台**读得懂**的规则：0 条 → 带着「新添」的去处跳浏览屏；1 条 → 带着那一条的序号跳，
    与规则行上 ✎ 走同一条路（逐条替换，名字与序号照旧）；≥2 条 → 按钮变灰，理由照 ADR-0005 修订段「带理由的拒绝」的形状写在旁边。
  - 浏览屏「更新到子库」只剩两条路：有序号 → 逐条替换；没序号（那一台原来一条都没有）→ 新添一条。
  - **「把读得懂的规则整批删掉、写回一条无名规则」那个核心库函数从此没有调用方，删掉**，免得下一个人又接上它。
    命令行不受影响（它不走这条路）。
  - 灰掉的判断住在界面层——它是「这一下在界面上能不能做」，不是核心库的领域判断。「几条规则」这个数由核心库照旧交出（选择集读回来就带着）。
- **裁决短路后的平台（核心库识别）**：
  - 裁决短路那一支在落结论之前补一步「补齐平台的依据」，与 Switch 那一支（`Q704` 的补依据）并排、同一个形状：
    先从中立库取算过的卡带头事实；取不到、而且允许回盘读，就读头并落库；最后按内容重算平台。
  - 这一步**不产出候选**，不改裁决说的任何字段，只影响平台那一格。
  - 关掉回盘读时取不到缓存就不读，平台照旧按目录声明——与开关的承诺一致。
  - 代码里「裁决过的东西一个字节都不必再读」那几处说法改成「只读判平台所需的头」，并注明 Switch 与卡带头是同一条例外。
- **词表与 ADR 不动**：三处都是把代码改回已经成文的口径（ADR-0011 平台由内容推翻目录、ADR-0005 带理由的拒绝、移除根只动这个根）。

## Testing Decisions

- 好测试只看外部行为：移除之后库里还答不答得出那几条结论、回程之后规则读回来长什么样、识别跑完平台判成什么。不断言 SQL、不断言调了哪个函数。
- 每一处**先写一条在今天的 `main` 上红的测试**，再修。
- **`Q555`**：接在核心库「移除一个根」那份测试的现场旁边。给两个根下的变体、以及它们共同的作品各落刮削结论、媒体引用、采集记录；
  移除一个根之后，经公开的读取入口核：这个根下变体的三样都不在了，另一个根的与作品那一层的一条不少。
- **`Q1184`**：接在界面层（子库屏 → 浏览屏的那条路），照现有「改选择」那几条界面测试的写法走一遍：
  - 一条带名字的规则 → 改选择 → 改条件 → 更新到子库 → 从中立库读回：仍是一条、名字与序号照旧、条件换了。
  - 一条读得懂 + 一条读不懂 → 同上，读不懂的那条原样留着。
  - 两条带名字的规则 → 「改选择」灰着、理由里有「2 条」与 ✎；按下去什么都不发生。
  - 零条 → 改选择 → 更新到子库 → 新添一条。
  - 核心库那边已有「只换第几条规则，序号不变，别的规则一条不碰」的测试，照旧绿。
- **`Q602`**：接在核心库平台纠正那份测试的夹具上（它已经有「按哪个平台算」「目录声明的」两个读法）。
  一张 GB 卡带放在别的平台目录、先落一条裁决 → 跑一趟识别 → 按判定平台读出来的是卡带头那一族；目录声明那一列一个字不动。
  再测两支：卡带头已缓存时这一趟读盘字节数为 0；关掉回盘读、又没有缓存时平台照旧按目录声明、读盘字节数为 0。
- 门禁全绿；本机不分大小写的盘上 `sync_run` 那五条的已知红（`Q479`，归 `gate-and-tests`）不算这一批的回归。

## Out of Scope

- 移除根时**沉淀库**里的东西（人工纠正、平台纠正、裁决）——照旧一个字不动（票 `one-criterion-per-thing/07` 的口径）。
- 「改选择」在多条规则时的更好出路（让人先挑一条、或并成一条前先确认）——拿主意的人选的是「变灰并说明」。
- 手动例外弹层那条「还有 N 个，去浏览屏筛」的跳转（`Q974`）——它要走「改选择」回程，等这一批合进去之后由
  `gui-draws-the-rest-of-the-design` 接。
- 平台判据本身的合并（CGB-only 算不算平台不符，`Q1030`）、报告按哪个平台分组（`Q605`）——归 `core-answers-once`。
- 卡带头里的版本号接不接「第几版」那条链——已裁不接（`Q994`）。

## Further Notes

- 三处互不依赖，可以三张票并行；动的文件不重叠（核心库目录模块、界面子库屏与浏览屏、核心库识别）。
- `Q1184` 是三处里唯一会**丢人手写的东西**的（规则的名字），建议排最前。
- 修 `Q555` 之后，已有的库里残留的那些刮削行不会自己消失——它们挂在已经不在的变体键上，下一次移除或删库重扫时清掉；
  中立库整份可再生，不为它写迁移。
