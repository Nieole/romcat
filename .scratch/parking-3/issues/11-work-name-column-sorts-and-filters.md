# 11 — 变体表那一列作品名排得了序

**What to build:** 维护者翻库时认的是**作品**（不是那些各路来源攒出来的文件名），
所以变体表里有一列作品名——但它排不了序也筛不了，因为它是从一张整份读进来的小表
（真库 9,226 条）里查的，不在查询的排序与筛选里。想按作品找就只能退回「键里含」那个框。
（挂账 `D161`）

**Blocked by:** 10（作品行的形状在 `10` 里刚动过）

**Status:** done

⚠️ **票正文的前提有一半是旧的，收尾时核对过**（挂单 `Q294`）：那一列作品名长在票 `25`
那一版的**变体表**上，票 `gui-redesign/03` 把那张表整个换成了**作品级主列表**——
作品名成了第一列、`WorkOrder::Name` 是默认排序且早就下推在 `ORDER BY` 里，
筛选走 `Dimension::Work` 也早就下推着。所以「排不了序也筛不了」在**主列表**上不成立；
`D161` 点名的那一处（**变体那一层的页查询**）倒是原封不动地还在，本票补的正是它。

- [x] 作品名**下推到页查询里**——排序与筛选一律下推到中立库（ADR-0005），不在内存里补。

      —— `Catalog::variant_browse_page`（`crates/core/src/catalog/browse.rs`）：
      一趟 `LEFT JOIN work ON work.id = variant.work_id`，`SELECT` 里多一列
      `work.name AS work_name`。排序落在 `VariantOrder::Work` 上（`ORDER BY` 拼的就是那个
      别名），筛选落在 `作品^…`（`Dimension::Work` → `catalog::filter`）。
      `variant_page` 与它**走同一条 SQL**（前者只是把作品名那一格丢掉），
      于是**这两个入口**筛的排的绝不会漂开。
      **总数那一条是另一条 SQL**（`variant_total` 只 `COUNT(*) FROM variant`，不连那张表），
      它与页内容数的仍是同一批，靠的是另一条依据：`work.id` 是 `INTEGER PRIMARY KEY`，
      一个变体最多连上一行，`LEFT JOIN` 放大不了行数——这句已写进 `VARIANT_BROWSE_FROM`
      的文档，连同「日后要再连一张表，先回答这一句还成不成立」。
      **`LEFT` 那半个字是要紧的**：还没认出作品的变体会被内连接**整批**筛掉，一个都不剩
      （真库上一千七百多个：作品 9,226 个，而主列表 10,978 行）。
      证据：`crates/core/tests/browse.rs::页查询自己带回作品名而不必整份读那张小表`
      ——只取**中间一页**（第 40 行起 20 行），前面那些行压根没取回来过，那一页每一格
      作品名都对得上 `work_names()` 说的。**突变检查过**：把 `VariantOrder::Work` 的列名
      改成 `key`（「什么都没干」的实现）当场红。

- [x] 另立一个**浏览专用的行类型**，与「变体表的一行」分开——后者被十几处构造着，直接给它加字段会波及一大片。

      —— `romcat_core::catalog::BrowseVariant`：
      `{ variant: VariantRow, work: Option<String> }`。形状照同一个模块里的 `WorkVariant`
      来——**装着**那一行，不把它的字段抄一遍。`VariantRow` 一个字段都没加：它是
      「`variant` 表的一行」，`identify` / `triage` / `scrape::local` / `adapter::converge`
      等十几处都在构造它、按这个意思读它，而作品名不在那张表上。
      `work` 那一格是 `Option`：`None` 是**还没认出作品**，不是「作品叫空字符串」——
      两件事混成一件，排序时它们就会插进真有作品的那一段里。

- [x] 点表头按作品名排序；筛选器里作品名也用得上。

      ⚠️ **照勾，但保留**：**表头那一半在票 `gui-redesign/03` 就落了**
      （`crates/gui/src/table.rs::Table::show` 的表头循环走 `WorkOrder::ALL`，
      `WorkOrder::Name` 那一档标签就是「作品」，再点一次翻方向），本票没动它，
      在这一条上的新增**只有测试**。而本票新加的 `VariantOrder::Work`
      **屏上没有任何表头可点**——`VariantOrder` 在 `crates/gui/src/` 里零出现，
      变体级的表在票 `gui-redesign/03` 之后就不在屏上了。所以规格 User Story 31
      「变体表里那一列作品名点表头就排序」**按字面没做到**，指到挂单 `Q297`。
      **筛选器那一半**走筛选面板那棵条件组（`Dimension::Work`，界面上那个下拉里就有
      「作品」，提示值 `火焰纹章`），一路下推成 `EXISTS (SELECT 1 FROM work w …)`。
      证据：`crates/gui/tests/browse.rs::筛选器里按作品名筛得动而且下推着筛`
      ——走的是屏上那条路（`browse::Screen::set_filter_rule`），断「筛掉了行」
      「筛完内存里还是那一扇窗（`retained() <= SPAN`）」「屏上剩的那几行画的就是那个作品」。
      条件里那个名字**从库里现取**，不写死。
      变体那一层同一件事：`crates/core/tests/browse.rs::按作品名筛也下推到库里`
      （总数与页内容筛的是同一批）。

- [x] 有测试断：按作品名排序之后屏上画出来的次序对。

      —— `crates/gui/tests/browse.rs::按作品名排完屏上画出来的次序就是作品名的次序`。
      看的是**这一帧真的画出来的字**（`shared::画出来的字`），比的是
      「屏上那一串 == 下推出来的那一页的前几行」，再断那一页自己确实按名字排好了；
      **期望从数据自己算出来**（把拿回来的名字自己排一遍），换一份同样合法的数据照样成立。
      两个方向都断，并断「翻了方向屏上真的变了」。中文那一段两边同口径：`ORDER BY`
      是 UTF-8 逐字节比，Rust 的 `str` 也是。
      **突变检查过**：把 `WorkOrder::Name` 的列名改成 `work_id` 当场红。
      对照：既有的 `五列都排得了序而且换排序真的换了次序` 断的只是「五种排法的头一行
      不全一样」，一次都没看屏上的字，在「排了、但排错了」上照样绿（挂单 `Q298`）。

- [x] 有测试断：没有作品的那些变体（作品那一格是空的）排序时的位置是确定的，不是随机漂。

      —— `crates/core/tests/browse.rs::按作品名排序是下推出来的而且作品那一格空着的一律排在末尾`：
      正反两个方向各一趟，断「第一个空的往后全是空的」「空的前面全是有作品的」，
      也就是空格子**连成一段、钉在表尾**，不跟着方向翻。做法是 `ORDER BY` 多一把
      `work_name IS NULL` 的键；这一档是本票现定的，另一条路（照 SQLite 默认）
      记在挂单 `Q295`。**突变检查过**：去掉那把键，正序那一趟当场红
      （SQLite 默认把 `NULL` 排最前，空的那一批跑到表头去了）。
      **主列表上不存在这一格**——那一屏还没认出作品的行画的是自己的键
      （`COALESCE(work.name, variant.key)`，与 `adapter::converge` 的 `Anchor::Loose`
      同一条口径），所以那儿没有「空格子往哪放」这个问题；新那条界面测试顺带断了
      **两种行摆在同一串里**（这一页上 `WorkAnchor::Work` 与 `Anchor::Loose` 都有）。

- [x] 帧率不塌：真库量级（10,978 行）上翻行的代价与总行数无关，实测数字写进报告。

      —— 判据是 `bench::FrameCost::reads`（**读了几次库**，不是秒表；票 `parking-3/01`
      拿掉过一条挂钟断言，票 `17` 立的这条路子）。
      实测（dev profile，同机另有两个 worktree 在跑，`demo::browse`）：
      **按作品名排（默认排序）滚 720 行——946 行读 1 次库、中位 19.20 ms；
      10,978 行读 1 次库、中位 19.27 ms；内存里始终 512 行。**
      读库次数一次不多、中位帧代价差 0.4%，两样都与总行数无关。
      ⚠️ **量法说清楚**：这两个数是在那条门禁测试里临时加一句 `eprintln!` 打 `FrameCost`
      得来的，量完当场撤掉——**没有常设入口，第二个人照不着复现**，也没落进
      `docs/library-facts.md`（挂单 `Q303`）。**读库次数那一半有常设断言守着，
      而且不是本票头一回量出来的**：`docs/library-facts.md:1269`（票 `parking-3/17`）
      已经记着「946 → 10,978 行，两边都是 1 次库读」；本票这一趟是**改完之后确认它没变**，
      不是新结论。
      门禁上守着它的是 `crates/gui/tests/browse.rs::翻行的代价按读了几次库算而且真库量级上一次不多`
      （`大的.reads <= 3` 且 `小的.reads == 大的.reads`），它跑的正是默认排序＝按作品名排。
      **那张 9,226 行的小表这一屏一次都没读过**：主列表那一列作品名从头到尾是页查询自己
      带回来的（`WORK_ANCHOR_COLUMNS` 里的 `COALESCE(work.name, variant.key)`），
      `crates/gui/` 里 `work_names` 零出现。`bench::BrowseCost::facets_ms` 那句
      「连表里那一列作品名靠的那张小表一起」是票 `25` 那一版的说法，本票一并改掉了。
      变体那一层同理：`variant_browse_page` 是一条查询，`work_names()` 一次都不调。

- [x] 挂账 `D161` 标 `settled` 并迁回票 `rom-metadata-automation/25`。

      —— `deferred.md` 的 `D161` 改成 `settled`（走 B），决定与证据迁进

## 说明

「按标题排」是另一件事——那要的是标题选取的结果，SQL 里算不出来。这张票**只做按作品名排**，
标题那条路不在范围内，如实记在挂单里。
