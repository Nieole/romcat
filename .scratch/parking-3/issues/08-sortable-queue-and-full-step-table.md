# 08 — 队列表能排序、步骤表不截断

**What to build:** 两件界面上的事：

1. **队列那一屏点表头就换排序。** 真机上 16,656 条待确认，维护者想按容量或按结论找到
   该先动的那几条，现在只能靠选择器缩小范围——次序永远是变体的键。（挂账 `D153`）
2. **差量预览的步骤表列得全。** 真机量级上一次同步动上万个文件（实测合成数据 8,206 步），
   表列满 2,000 条就打住，想确认第 5,000 步是什么就得转去命令行。（挂账 `D158`）

**Blocked by:** None — can start immediately

**Status:** done

- [x] 队列那一屏点表头换排序，**在内存里排**——它的条目本来就在内存里（几千条），不为它改查询。（这与变体表那种下推到 `ORDER BY` 的路子不同，是有意的：数据在哪就在哪排。）
      —— `triage::ItemOrder`（五列）+ `Queue::order()` / `set_order()`，排的是**整份 `items`**（`Queue::refresh` 先排整份再分区，于是两段各自有序）；界面 `crates/gui/src/queue.rs` 的表头改成可点、带 ▲▼，**箭头照 `Queue::order()` 画，界面不另存一份**。**一次库都不读**。⭐ **排序与分区是同一步**（`refresh` 先排整份再分区）：反过来会让 `selected()` 从「选择器选中的那些」变成「排完之后的前 N 条」，屏上写着 1,396 条、落下的却是人从没选过的变体——`/code-review` 抓出来的，`crates/core/tests/triage.rs` 那条测试拆掉修复当场红。实测 **16,656 条重排再分区 36.6 ms**（`--bench-queue 240`，release，本机 12 核 / 15 GB 合成数据）——与同屏上「点一行分组表」的 22.67 ms 同一量级；只排不分区是 13.4 ms，多花的 23 ms 买的正是那条不变式。
