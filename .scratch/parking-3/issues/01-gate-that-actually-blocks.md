**What to build:** 维护者推一次代码，门禁四条自动跑起来；本地跑的是同一套定义，不会漂。
换一台机器提交，`cargo fmt` 的产出不会突然多出一大片与手上这件事无关的重排。

眼下「门禁」只是 `README.md` 「开发」一节里的四行命令，仓库里没有任何机器执行它的地方，

### Q194 — 门禁跑手落成独立的 `xtask` crate，而不是 `romcat` 的一条子命令

- **来自：** 票 `parking-3/01`
- **类别：** 规格没说
- **在哪：** `xtask/Cargo.toml`、`.cargo/config.toml`、根 `Cargo.toml` 的 `members`
- **为什么没停线：** 票只说「仓库里一个真实可跑的子命令，承载它的东西不进交付出去的二进制」，
  没说是**谁的**子命令；两条路都撤得回来，改动全在这张票之内。
- **这张票实际做了什么：** 走**独立 crate + cargo 别名**这条路（`cargo xtask gate`）。
  另一条路是 `romcat gate`，藏在一个默认关掉的 feature 后面——它站得住（`romcat-gui` 的
  `demo` 就是这个先例），但它与票自己那句「不进交付出去的二进制」相抵：门禁四条的定义会住在
  交付 crate 的源码树里，而**门禁一律用 `--all-features` 跑**，于是那个 feature 在门禁里
  永远是开的，`romcat --help` 上会长出一条只给维护者看的命令。`xtask` 那条没有这一层：
  `romcat` 与 `romcat-gui` 都不依赖它。顺带把 `xtask` 放进 workspace `members`
  （而不是 `exclude`），于是门禁四条照样盖着门禁跑手自己——**门禁跑手自己不守门禁**
  是最难查的一类漏。
