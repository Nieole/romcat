- [x] 它们各自钉的东西（帧率、面板、媒体、版式）跟着**重定基线**——新旧数字并排写进报告，说清每一条为什么变。

  报告在 `docs/library-facts.md` 新一节「浏览屏实测换到真库的形状（2026-09-08，票
  `parking-3/17`）」：**三趟 release 并排**，同一个二进制，旧形状靠 `--rows` /
  `--bench-works` 复现出来，**没有一个数是照新口径推算的**（票 `12` 立的规矩）。
  这台开发机（12 核 / 15 GB，另有三个 worktree 在跑），**合成数据不是真库**。

  | | 旧默认 10 万 / 20 作品 | **新默认 46,428 / 7,407 作品** |
  |---|---:|---:|
  | 主列表行数 | 7,712 | **10,978** |
  | 列一次筛选面板 | 154.4 ms | **68.8 ms** |
  | 换一次筛选 | 58.9 ms（剩 473 行） | **26.9 ms（剩 1,962 行）** |
  | 点开一行 | 17.25 ms | **3.36 ms** |
  | 每帧中位 | 2.39 ms（418 fps） | **0.95 ms（1,053 fps）** |
  | 最慢的一帧 | 4.12 ms | **18.68 ms** |
  | 滚一趟读库 | **0 次** | **4 次** |

  ⭐ **最要紧的一条不是哪个数快了：旧的那两趟根本没滚动过。** 换一次筛选之后只剩
  473 行（旧默认）与 230 行（同样多变体、旧作品数），**都比一扇窗 512 行还少**——
  整份筛出来的东西一次就装进内存，那 238 帧一次库都没读过。作品数一少，同一个平台
  底下就只剩那么几个作品。**那不是虚拟化在起作用，是压根没东西可翻。**
  新形状筛完还剩 1,962 行，滚一趟真的跨窗 4 次，「最慢的一帧」也因此从 4.12 ms 变成
  18.68 ms——那才是维护者真会遇到的那一帧。逐条为什么变，见报告那一节。

  版式与媒体这两样**重定的是基线不是数**：`layout.rs` 那 13 条与 `media.rs` 那 9 条
  在新形状上一条断言都没改就全绿（面板宽窄按点数量、媒体按解没解码，都不跟着行数走）；
  变的是它们脚下那份数据的形状。
