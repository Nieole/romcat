# 推荐执行顺序

26 张未完成的票（01、02 已 done）。顺序在依赖约束下**按交付价值排**，不是单纯的拓扑序。

排序原则：**先打通一条窄而完整的链路直达用户每天真正做的事（挑一批导到掌机），再回头把识别做透。** 这样每一张后续的票都是在改进一个已经跑通的系统，而不是朝着未验证的方向继续堆。

---

## 第一段 · 打通到「看得见命中率」（4 票）

`03` → `05` → `06` → `07`

| 票 | 内容 |
|---|---|
| 03 | 透明容器：zip 与 7z 零解压读 CRC-32。**容量的 91.1% 在容器里**，这是性能地基 |
| 05 | 成型规则与三层模型。**PSV 那 171,073 个文件要在这里收敛成几百个变体** |
| 06 | DAT 仓库。绝不直连 datomatic；Redump 走新域名不走那个镜像 |
| 07 | CRC-32 精确识别，产出带置信度与依据的候选 |

**里程碑：第一次看到真实命中率**——8.6 TiB 里有多少东西能被精确认出来。此前所有判断都在等这个数字。

## 另一条路线（不推荐，但记下取舍）

**先把识别做透再谈导出**：第一段之后直接走第四段，再回到第二、三段。

- **好处**：导出的元数据从一开始就覆盖率高，不用先看着一堆未识别条目。
- **代价**：到「能用」之间隔了 10 张票，中途拿不到任何可用的东西；而且导出与同步这条链路上的设计问题会推迟暴露——那是整个工具真正的出口。

推荐的顺序把这条链路提前，代价是第一次导出时元数据只覆盖精确命中的那部分。**这是个可以接受的中间态，而「识别很准但导不出去」不是。**
