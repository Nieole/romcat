# 挂账

流程里冒出「这里有两种做法」但不值得停线的选择，记在这里，编号连续。
选错也能改天再改、且改的时候不必重做那张票的，都挂在这。

**这是待办队列，不是档案馆。** 裁决之后就迁回它所属的票（票据末尾的「挂账裁决」一节），
指向未来某票的前瞻迁到那张票（「从挂账转来的前瞻」一节），这里只留还没定的。

条目格式：

> ## Dn · 票 NN · 一句话标题
> - **问：** 一句话
> - **选项：** A 照做（推荐，因为 …）｜B 另一种
> - **不处理会怎样：** 一句话
> - **状态：** open

## 编号

全局连续，**不复用**——迁走的条目仍然占着它的号，票据里的「原 D3」「原 D26」这类引用要一直指得回来。

下一个编号是**已出现过的最大号加一**，别记在这里（记了就会过期）。算出来：

```
grep -rhoE '\bD[0-9]+\b' .scratch/rom-metadata-automation/ | sort -uV | tail -1
```

## D29 · 票 29 · 同一块盘上不同区域的最优并发相反，只探一次够不够

- **问：** 真机实测同一块外置盘：`Game/ps` 那片提高并发**快 4.71 倍**（软件开销受限），
  `Game/SFC` 那片提高并发**慢 5.9 倍**（寻道受限）。现在开扫前只探一次，整趟用一个并发数。
- **选项：** A 只探一次，取保守值（推荐，因为过量并发的代价是不对称的——SFC 那片慢 5.9 倍，
  而并发不足最多少赚几成；且实现简单，队列不必按平台分片）｜B 按平台目录各探一次，
  扫到哪片用哪片的并发数
- **不处理会怎样：** 全库扫描在两种区域之间取一个折中值，两边都不是最优。
- **状态：** open

  因为它们现在只在扫描器一处出现，值不值得进 51 个术语的词表还看不出来）
  ｜B 现在就补进词表
- **不处理会怎样：** 用户看得见的文案里有几个词表管不到的词，后面的票可能各叫各的。
- **状态：** open

## D31 · 票 29 · 「扫描」与「遍历」的分工，词表里没说清

- **问：** `CONTEXT.md` 给 **遍历** 列的 `_Avoid_` 词里有「扫描」，可子命令、模块、
  `ScanOptions` 全叫 scan/扫描，词表自己的正文也在用（「是扫描的输入」「一次遍历的编号」）。
  实际的分工像是：**遍历**是那件事的**记录**（`Traversal` 一行），**扫描**是那个**动作**。
  词表没写这一层。
- **选项：** A 在词表里把这层分工写明，代码照旧（推荐，因为改名要动子命令、模块名与
  中立库的表名，代价远大于收益）｜B 代码里也一律改成遍历
- **不处理会怎样：** 每次做词表体检都会重新命中一次，然后重新讨论一次。
- **状态：** open

## D32 · 票 29 · 「导入时保存的原文件副本」没有词，于是文档里一直叫「快照」

- **问：** 票 29 清掉了代码里的「快照」，但 ADR-0001 / 0003 / 0006、`spec.md`、票 16 / 17，
  以及 `CONTEXT.md` **用户状态**词条自己的正文里都还在用它。它们说的是**同一个概念**：
  导入前端元数据时保存的那份原文件完整副本，无损往返靠它做三方合并的基线。
  这个概念**词表里没有**——「快照」被列为 **清单** 的 `_Avoid_` 词，但清单专指子库上次
  导出的记录，不是这个。所以那些地方不是残留，是缺口。
- **选项：** A 给这个概念起个词补进词表，再统一替换（推荐，因为票 16 一开工就要天天用它）
  ｜B 放宽 **清单** 的定义把它涵盖进去
- **不处理会怎样：** 每次做词表体检都会把这些地方报成「快照残留」，而它们改不掉——
  没有词可以换。
- **状态：** open

## D33 · 票 05 · 平台清单用 TOML 还是已经在依赖里的 JSON

- **问：** 平台清单与成型规则是**数据不是代码**（`docs/platforms.md`），要落成一份配置文件。
  `serde_json` 本来就在依赖里，白拿；TOML 要新加一个 crate（`toml` 1.1，连带三个传递依赖）。
- **选项：** A 用 TOML（推荐，因为**这份清单每条规则都得写清「为什么这么定」**——
  `chd` 为什么排在 `cue` 前面、`addcont` 为什么算附属内容、`@@@@#####*` 为什么这么宽，
  而 JSON 没有注释，没注释的规则表下一个人只能靠猜；代价是 TOML 的裸键不许非 ASCII，
  中文键得加引号：`[["平台"]]`、`"名" = "PSV"`）｜B 用 JSON，省一个依赖，注释写进
  一个平行的 `_注释` 字段或者外部文档
- **不处理会怎样：** 已经按 A 落地了。真要换成 B，改的是 `platform.rs` 的解析入口与
  那一份内置清单，成型器与中立库都不动。
- **状态：** open

## D34 · 票 05 · 「附属内容」现在只是变体成员的一种身份，还不是独立实体

- **问：** 词表说**附属内容**「归属某个作品、**有自己的名字与元数据**，但不能独立运行」。
  票 05 只做到一半：PSV 转储里 `addcont/` 下面的东西被标成 `变体成员.身份 = 附属内容`，
  入库、不导出，但它没有自己的一行记录、没有名字。真正独立成实体要等识别能认出
  「这个 DLC 叫什么」——那是票 07 之后的事。
- **选项：** A 现在维持成员身份（推荐，因为这一层只要答得上「它入库了吗」「它会被导出吗」，
  两问都答得上；造一张空名字的表只是把缺口挪个地方）｜B 现在就给附属内容单独一张表
- **不处理会怎样：** 库里数得出「有多少个附属内容文件」，数不出「有多少个附属内容」。
- **状态：** open

## D35 · 票 05 · 「非游戏资产」还没有落点

- **问：** 词表里**非游戏资产**（MAME 的 BIOS set 与 device set）「入库但永不导出」。
  票 05 的成型把 `街机/` 下的每个 zip 都当成一个变体，于是 `neogeo.zip` 会变成一个
  可导出的变体。要分开它，判据在 `mame.xml` 的 `isbios` / `isdevice`（ADR-0010），
  而那份 XML 是票 06 的 DAT 仓库才会有的东西。
- **选项：** A 等票 06 / 票 10（推荐，因为真库里街机只有 265 个文件、3.73 GiB，
  错几个 BIOS 的代价极小，而现在硬猜「名字像 BIOS 的」正是 ADR-0013 明令禁止的
  「按名字一刀切」）｜B 现在按一张手写的 BIOS 名单先挡一下
- **不处理会怎样：** 导出街机时会多出几个点不动的条目。街机与用户的核心痛点（汉化版）
  无关，优先级本来就低。
- **状态：** open

## D36 · 票 05 · 多碟同族只按名字认，不看光盘内容

- **问：** 多碟同族的判据是「剥掉碟片标记之后键相同」。它认得出 `(Disc 1)` / `(Disc 2)`
  与 `…]Disc A` / `…]Disc B`，但认不出**换了个说法的同一套碟**（`上篇` / `下篇`），
  也可能把两个恰好同名的不同游戏并到一起。真正的判据在光盘内部序列号——
  同一套碟共用一个序列号——而那是票 09 的活。
- **选项：** A 现在只按名字（推荐，因为票 09 拿到序列号之后，多碟同族可以从
  「名字规则」升级成「序列号规则」，成型器的形状不用变——它本来就是可重跑的纯计算）
  ｜B 现在就把碟片标记的模式表写得更宽
  **另一半：** 碟 1 不写标记那种形态（`游戏.chd` 加 `游戏 (Disc 2).chd`）现在认得了，
  但两套碟用了不同说法（`上篇` / `下篇`）还是认不出——那也得等序列号。
- **不处理会怎样：** 少数多碟作品会裂成几个变体，或者极少数同名的被误并。
  人工纠正（`romcat shape --merge`）随时救得回来。
- **状态：** open

## D37 · 票 05 · 常规成型不产出平台为空的变体，与「其他掌机是兜底桶」有张力

- **问：** 验收要「变体的平台属性可空，认不出平台的内容照常入库」。列确实可空，
  人工纠正也确实造得出没有平台的变体。但**常规成型不会**：落在平台目录下必得平台，
  落在未映射目录的按 ADR-0011 修订段整体不成型。而 `docs/platforms.md` 那句
  「『其他掌机』不是平台，是兜底桶……扫描到的一切都入库」读起来像是要有变体。
- **选项：** A 维持（推荐，因为 ADR-0011 的**修订段**比 `platforms.md` 那句话晚，
  且用户明确决定「未分类的由他手动处理」；「一切都入库」在中立库的 `entry` 表层面
  是成立的，库体检也照报）｜B 给未映射目录也成型，变体的平台留空——那等于把
  用户说了不管的那 25,615 个文件塞进识别管线
- **不处理会怎样：** 读 `platforms.md` 的人会以为漏了一种情况，然后重新推一遍。
- **状态：** open

## D39 · 票 06 · DAT 仓库引入的一批词还没进词表

## D40 · 票 06 · TOSEC 的映射按平台粒度收，一收就是几百份 DAT

- **问：** TOSEC 一个平台常有十几份 DAT（Games / Demos / Applications / Firmware /

  ｜B 只收 Games 与 Homebrew，其余明确不要
- **不处理会怎样：** DAT 库比必要的大一些，同步一趟多花几分钟。
- **状态：** open

## D42 · 票 06 · 整包那一档的增量粒度是整个包，改一条映射要重新解 48 份 DAT

- **问：** No-Intro 走 GitHub 每日镜像，镜像只发整包，所以「变没变」只能问到整包这一层。
  包变了就把映射命中的 48 份全部重解重写（实测 8 秒）；映射改了也一样，得靠 `--full`
  或者删掉那一件的指纹才重新入库。
- **选项：** A 维持整包粒度（推荐，因为数据源的形态就是这样，而重解一遍只要 8 秒——
  真正贵的是那 106 MB 的下载，而缓存已经挡住了它）｜B 给每份 DAT 单独算一个内容哈希
  当指纹，包变了也只重写真正变了的那几份
- **不处理会怎样：** 每天同步一次时，No-Intro 那一档每次都重写 48 份 DAT 的全部记录。
- **状态：** open
