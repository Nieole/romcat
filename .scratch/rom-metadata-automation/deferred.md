# 挂账

流程里冒出「这里有两种做法」但不值得停线的选择，记在这里，编号连续。
选错也能改天再改、且改的时候不必重做那张票的，都挂在这。

**这是待办队列，不是档案馆。** 裁决之后就迁回它所属的票（票据末尾的「挂账裁决」一节），
指向未来某票的前瞻迁到那张票（「从挂账转来的前瞻」一节），这里只留还没定的。

条目格式：

> ## Dn · 票 NN · 一句话标题
> - **问：** 一句话
> - **选项：** A 照做（推荐，因为 …）｜B 另一种
> - **不处理会怎样：** 一句话
> - **状态：** open

## 编号

全局连续，**不复用**——迁走的条目仍然占着它的号，票据里的「原 D3」「原 D26」这类引用要一直指得回来。

下一个编号是**已出现过的最大号加一**，别记在这里（记了就会过期）。算出来：

```
grep -rhoE '\bD[0-9]+\b' .scratch/rom-metadata-automation/ | sort -uV | tail -1
```

## D29 · 票 29 · 同一块盘上不同区域的最优并发相反，只探一次够不够

- **问：** 真机实测同一块外置盘：`Game/ps` 那片提高并发**快 4.71 倍**（软件开销受限），
  `Game/SFC` 那片提高并发**慢 5.9 倍**（寻道受限）。现在开扫前只探一次，整趟用一个并发数。
- **选项：** A 只探一次，取保守值（推荐，因为过量并发的代价是不对称的——SFC 那片慢 5.9 倍，
  而并发不足最多少赚几成；且实现简单，队列不必按平台分片）｜B 按平台目录各探一次，
  扫到哪片用哪片的并发数
- **不处理会怎样：** 全库扫描在两种区域之间取一个折中值，两边都不是最优。
- **状态：** open

## D33 · 票 05 · 平台清单用 TOML 还是已经在依赖里的 JSON

- **问：** 平台清单与成型规则是**数据不是代码**（`docs/platforms.md`），要落成一份配置文件。
  `serde_json` 本来就在依赖里，白拿；TOML 要新加一个 crate（`toml` 1.1，连带三个传递依赖）。
- **选项：** A 用 TOML（推荐，因为**这份清单每条规则都得写清「为什么这么定」**——

  而 JSON 没有注释，没注释的规则表下一个人只能靠猜；代价是 TOML 的裸键不许非 ASCII，
  中文键得加引号：`[["平台"]]`、`"名" = "PSV"`）｜B 用 JSON，省一个依赖，注释写进
  一个平行的 `_注释` 字段或者外部文档
- **不处理会怎样：** 已经按 A 落地了。真要换成 B，改的是 `platform.rs` 的解析入口与
  那一份内置清单，成型器与中立库都不动。
- **状态：** open

## D36 · 票 05 · 多碟同族只按名字认，不看光盘内容

- **问：** 多碟同族的判据是「剥掉碟片标记之后键相同」。它认得出 `(Disc 1)` / `(Disc 2)`
  与 `…]Disc A` / `…]Disc B`，但认不出**换了个说法的同一套碟**（`上篇` / `下篇`），
  也可能把两个恰好同名的不同游戏并到一起。真正的判据在光盘内部序列号——
  同一套碟共用一个序列号——而那是票 09 的活。
- **选项：** A 现在只按名字（推荐，因为票 09 拿到序列号之后，多碟同族可以从
  「名字规则」升级成「序列号规则」，成型器的形状不用变——它本来就是可重跑的纯计算）
  ｜B 现在就把碟片标记的模式表写得更宽
  **另一半：** 碟 1 不写标记那种形态（`游戏.chd` 加 `游戏 (Disc 2).chd`）现在认得了，
  但两套碟用了不同说法（`上篇` / `下篇`）还是认不出——那也得等序列号。
- **不处理会怎样：** 少数多碟作品会裂成几个变体，或者极少数同名的被误并。
  人工纠正（`romcat shape --merge`）随时救得回来。
- **状态：** open

## D46 · 票 07 · 去头那套按「尺寸说得通」触发，不是一律解压

- **问：** 含头那套零解压就有（容器元数据），去头那套要解压。现在的做法是
  **按未压缩大小先筛**：`.nes` 要 `size % 1024 == 16`、`.smc` 要 `% 1024 == 512`，
  尺寸对不上就一定没有外挂头，两套哈希落在同一串字节上，不再解压。
- **选项：** A 按尺寸筛（推荐，因为尺寸判据是免费的，而且外挂头本来就是「固定长度的头
  加整齐的内容」，尺寸对不上就一定没有头——漏判的可能性只在「头之后的内容长度恰好
  不整齐」那种畸形转储上）｜B 凡是可能带头的扩展名一律整份解压算两套，多读几个 GB
  换一个不必推理的实现

- **不处理会怎样：** 换一台机器（或删了中立库重扫）之后，那张卡上工具自己放的文件
  全部变成「清单之外」——于是一个都删不掉，只能手动清。单人单机的前提下不会发生
  （spec 的 Out of Scope 写着「单人单机」），ADR-0018 那种「盘在两台机器之间来回接」
  说的是**主库**那块盘，不是子库的卡。
- **状态：** open

## D78 · 票 19 · 目标上**被改过**的文件既不覆盖也不删，且没有 `--force`

- **问：** 清单说有、目标上也在，但戳对不上——有人在工具之外动过它。计划器一律
  报告 + 本次不动，没给「压过去」的开关。
- **选项：** A 只报不动（推荐：与 `adapter::transfer` 那条「检测到外部改动就停下来、
  不静默覆盖」同一条纪律；而且这一侧判错的代价是删掉别人的东西）｜B 加一个
  `--force` 压过去——`adapter::transfer` 那一侧确实有，但那边压的是工具自己生成的
  元数据文件，这边压的可能是维护者亲手换上去的 ROM
- **不处理会怎样：** 目标上被改过的文件会**每一趟都报一次**，直到用户自己把它删掉
  或者接受它。真机演练里 10 个被改过的文件就是这个样子。
- **状态：** open

## D79 · 票 19 · 子库内的布局**照搬主库的相对路径**

- **问：** 变体在子库里放哪儿？眼下是「主库里的键原样搬过来」——`GB/口袋妖怪.zip`
  到了卡上就是 `<子库根>/GB/口袋妖怪.zip`。
- **选项：** A 照搬（推荐：与 `adapter::transfer` 那句「导出目录在语义上是主库根的替身」

  ｜B 按平台 / 作品重排成一套规整的布局——那要为「同一个作品的两个变体重名」
  再定一套消歧规则，而且用户在掌机上找不到自己熟悉的目录
- **不处理会怎样：** 主库里那些又长又深的目录名（`GB/GB+GBC游戏合集v1.2（2022.5.7）/
  【其他整理】/…`）会原样出现在卡上。FAT32 的路径长度限制因此可能在票 21 的
  能力档案里撞上——那张票已经点名要检查路径长度。
- **状态：** open

## D80 · 票 19 · 期望状态带上变体的**全部成员**，含内部资源与附属内容

- **问：** 一个变体可能是一个文件，也可能是一棵目录树（PSV 的转储）。搬哪些成员？
  眼下四种身份全搬：主文件、附属文件、内部资源、附属内容。
- **选项：** A 全搬（推荐：ADR-0013 说的「附属内容不导出为**前端条目**」管的是条目，
  不是磁盘上的字节——PSV 的 `addcont/` 不搬过去，游戏在掌机上就少一半内容；
  而且这样「期望总量」与选择集报出的容量是同一个数，两层账对得上）｜B 只搬主文件，
  附属内容另给一个开关
- **不处理会怎样：** 选中一个带大量 DLC 的 PSV 变体时，容量按整棵树算——那正是真实的
  占用。想只带本体得靠例外把整个变体踢掉，没有更细的粒度。
- **状态：** open

## D81 · 票 19 · 一致性判据是 `(大小, 修改时间)`，不是内容哈希

- **问：** 「目标上还是不是工具上次放的那一份」怎么判？眼下比清单里记的
  `(大小, 修改时间)` ——与增量扫描的三元组同一套办法，也与那句「证明不了没变，
  就不能说没变」同一条纪律（取不到时间就算证明不了）。
- **选项：** A 比戳（推荐：一张 512 GB 的卡每次同步前全量哈希要读满 512 GB，
  而 SD 卡的读速正是这条链路上最慢的一环；清单记的又是**写完从目标上读回来的**那个戳，
  于是 FAT32 那 2 秒刻度也不构成问题）｜B 全量或抽样哈希——能认出「大小与时间都没变、
  内容却坏了」的静默损坏
- **不处理会怎样：** 卡上发生位腐（大小与时间都没变、内容坏了）时工具看不出来，
  会当成「保持」。这类损坏要靠票 20 之后另开一张「校验子库」的票去查。
- **状态：** open

## D82 · 票 19（病根在票 18）· 子库的目标路径存的是 NFC，读盘用的却是同一份

- **问：** ADR-0020 定死了「读盘要用系统给的原始路径，只有入库与比较才用 NFC 的键」。
  `put_sublibrary` 把目标路径**存成 NFC**（那是对的：它要当键用），而同步这一步
  只有这一份字符串可用，于是拿它直接去 `canonicalize`。目标目录名若是分解形式，
  在**分解敏感**的文件系统上会打不开——然后被报成「目标不在位」，即最不该说的那个谎。
- **选项：** A 眼下只把 `--target` 那条路修好（已做：给了 `--target` 就拿系统给的原始
  `PathBuf` 去读，NFC 那份只进报告），存进库的那份留着（推荐：真正要读写目标的是票 20，
  那时才知道需要什么；而 macOS 的 APFS 与 Windows 的 NTFS 查找本身都不分解敏感，
  这条路眼下走不到）｜B 现在就在 `sublibrary` 表上另存一列「系统给的原始形式」，
  键与读盘各用各的——那要动票 18 已经写进数据的表
- **不处理会怎样：** 目标目录名带假名或带音标、且挂在分解敏感的驱动上时，
  `sublibrary plan` 会说「目标不在位」。真机上的目标是 `/Volumes/SDCARD/Games`，
  全 ASCII，撞不上。**票 20 真的往目标上写之前必须先定这一条。**
- **工头裁决（2026-09-01）：选 B，由票 20 作为第一件事做掉。** A 的论证依赖「APFS 与 NTFS 都不分解敏感」，但**真正的目标是 SD 卡，那是 exFAT 或 FAT32，它们的规范化行为没人查过**——而 ADR-0018 定的工作流里，卡才是最终落点。这已是这类 bug 的第三次出现（票 16 刚被咬过：导出用 NFC 键去 `fs::write`，在维护者的原件旁边新建了一份）。现在改表零代价（用户尚未建过真实子库），等子库配好再改就是数据迁移。
- **状态：** done —— 票 20 落地：`sublibrary` 表加了 `target_raw` 列（系统给的原始形式），
  `Sublibrary::read_path()` 读盘走它、`target` 那一份只当键与进报告。老行是 NULL、退回
  `target`，行为与从前一致。真机核对：目标目录名用分解形式建出来后，`target` 是 NFC、
  `target_raw` 是 NFD、两串字节不同，`plan` 照样打得开。

## D83 · 票 19 · `sync` 与 `dat::sync` 两个模块重名

- **问：** 词表里**同步**特指「把子库的目标状态与目标设备的实际状态对齐」，而

## D84 · 票 20 · **ROM 一律复制**，硬链接只用在媒体池 → 目标那一段
