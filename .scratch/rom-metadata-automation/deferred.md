# 挂账

流程里冒出「这里有两种做法」但不值得停线的选择，记在这里，编号连续。
选错也能改天再改、且改的时候不必重做那张票的，都挂在这。

**这是待办队列，不是档案馆。** 裁决之后就迁回它所属的票（票据末尾的「挂账裁决」一节），
指向未来某票的前瞻迁到那张票（「从挂账转来的前瞻」一节），这里只留还没定的。

条目格式：

> ## Dn · 票 NN · 一句话标题
> - **问：** 一句话
> - **选项：** A 照做（推荐，因为 …）｜B 另一种
> - **不处理会怎样：** 一句话
> - **状态：** open

## 编号

全局连续，**不复用**——迁走的条目仍然占着它的号，票据里的「原 D3」「原 D26」这类引用要一直指得回来。

下一个编号是**已出现过的最大号加一**，别记在这里（记了就会过期）。算出来：

```
grep -rhoE '\bD[0-9]+\b' .scratch/rom-metadata-automation/ | sort -uV | tail -1
```

## D29 · 票 29 · 同一块盘上不同区域的最优并发相反，只探一次够不够

- **问：** 真机实测同一块外置盘：`Game/ps` 那片提高并发**快 4.71 倍**（软件开销受限），
  `Game/SFC` 那片提高并发**慢 5.9 倍**（寻道受限）。现在开扫前只探一次，整趟用一个并发数。
- **选项：** A 只探一次，取保守值（推荐，因为过量并发的代价是不对称的——SFC 那片慢 5.9 倍，
  而并发不足最多少赚几成；且实现简单，队列不必按平台分片）｜B 按平台目录各探一次，
  扫到哪片用哪片的并发数
- **不处理会怎样：** 全库扫描在两种区域之间取一个折中值，两边都不是最优。
- **状态：** open

## D31 · 票 29 · 「扫描」与「遍历」的分工，词表里没说清

- **问：** `CONTEXT.md` 给 **遍历** 列的 `_Avoid_` 词里有「扫描」，可子命令、模块、
  `ScanOptions` 全叫 scan/扫描，词表自己的正文也在用（「是扫描的输入」「一次遍历的编号」）。
  实际的分工像是：**遍历**是那件事的**记录**（`Traversal` 一行），**扫描**是那个**动作**。
  词表没写这一层。
- **选项：** A 在词表里把这层分工写明，代码照旧（推荐，因为改名要动子命令、模块名与
  中立库的表名，代价远大于收益）｜B 代码里也一律改成遍历
- **不处理会怎样：** 每次做词表体检都会重新命中一次，然后重新讨论一次。
- **状态：** resolved —— 已改准 **遍历** 词条：遍历是那条**记录**，**扫描**是那个**动作**；命令与模块一律叫扫描，落库那一行才叫遍历。「扫描」不再是 `_Avoid_` 词。

## D32 · 票 29 · 「导入时保存的原文件副本」没有词，于是文档里一直叫「快照」

- **问：** 票 29 清掉了代码里的「快照」，但 ADR-0001 / 0003 / 0006、`spec.md`、票 16 / 17，
  以及 `CONTEXT.md` **用户状态**词条自己的正文里都还在用它。它们说的是**同一个概念**：
  导入前端元数据时保存的那份原文件完整副本，无损往返靠它做三方合并的基线。
  这个概念**词表里没有**——「快照」被列为 **清单** 的 `_Avoid_` 词，但清单专指子库上次
  导出的记录，不是这个。所以那些地方不是残留，是缺口。
- **选项：** A 给这个概念起个词补进词表，再统一替换（推荐，因为票 16 一开工就要天天用它）
  ｜B 放宽 **清单** 的定义把它涵盖进去
- **不处理会怎样：** 每次做词表体检都会把这些地方报成「快照残留」，而它们改不掉——
  没有词可以换。
- **状态：** resolved —— 已补进词表：**底本**——导入时保存的原文件完整副本，无损往返靠它做基线。取代散落各处的「快照」（那是 **清单** 的 `_Avoid_` 词）。

## D33 · 票 05 · 平台清单用 TOML 还是已经在依赖里的 JSON

- **问：** 平台清单与成型规则是**数据不是代码**（`docs/platforms.md`），要落成一份配置文件。
  `serde_json` 本来就在依赖里，白拿；TOML 要新加一个 crate（`toml` 1.1，连带三个传递依赖）。
- **选项：** A 用 TOML（推荐，因为**这份清单每条规则都得写清「为什么这么定」**——

  而 JSON 没有注释，没注释的规则表下一个人只能靠猜；代价是 TOML 的裸键不许非 ASCII，
  中文键得加引号：`[["平台"]]`、`"名" = "PSV"`）｜B 用 JSON，省一个依赖，注释写进
  一个平行的 `_注释` 字段或者外部文档
- **不处理会怎样：** 已经按 A 落地了。真要换成 B，改的是 `platform.rs` 的解析入口与
  那一份内置清单，成型器与中立库都不动。
- **状态：** resolved —— 维持原样。裁决记在本条，**未迁回票 05**（迁回由维护者自己做）

- **状态：** resolved —— 维持原样。裁决记在本条，**未迁回票 05**（迁回由维护者自己做）

## D36 · 票 05 · 多碟同族只按名字认，不看光盘内容

- **问：** 多碟同族的判据是「剥掉碟片标记之后键相同」。它认得出 `(Disc 1)` / `(Disc 2)`
  与 `…]Disc A` / `…]Disc B`，但认不出**换了个说法的同一套碟**（`上篇` / `下篇`），
  也可能把两个恰好同名的不同游戏并到一起。真正的判据在光盘内部序列号——
  同一套碟共用一个序列号——而那是票 09 的活。
- **选项：** A 现在只按名字（推荐，因为票 09 拿到序列号之后，多碟同族可以从
  「名字规则」升级成「序列号规则」，成型器的形状不用变——它本来就是可重跑的纯计算）
  ｜B 现在就把碟片标记的模式表写得更宽
  **另一半：** 碟 1 不写标记那种形态（`游戏.chd` 加 `游戏 (Disc 2).chd`）现在认得了，
  但两套碟用了不同说法（`上篇` / `下篇`）还是认不出——那也得等序列号。
- **不处理会怎样：** 少数多碟作品会裂成几个变体，或者极少数同名的被误并。
  人工纠正（`romcat shape --merge`）随时救得回来。
- **状态：** open

## D39 · 票 06 · DAT 仓库引入的一批词还没进词表

- **问：** 票 06 引入「DAT、数据源、哈希口径（含头 / 去头 / 逐芯片）、条目、文件记录、
  取数纪律」，另有几个**用户直接看得见**的：命令行打「取了 N **件**、跳过 N 件」，
  清单与文档里反复说「**整包**」「**指纹**」。`CONTEXT.md` 的 51 个术语里一个都没有。
  更要紧的是**条目**这个词：一条 DAT `<game>` 通常是**发行版**，但 TOSEC 的
  `[tr zh]` 条目是**变体**——词表现在说不出「有时是这个有时是那个」。
- **选项：** A 记成缺口，等票 07 把这些词再用一遍时一起交给 `/domain-modeling`（推荐，
  因为票 07 才会决定「条目」到底怎么挂到三层内容模型上，现在定名等于替它做决定）
  ｜B 现在就把「DAT」「哈希口径」补进词表
- **不处理会怎样：** 报告里有几个词表管不到的词；票 07 可能给同一个东西起第二个名字。
- **票 07 落地后的补充：** 「条目挂到哪一层」这个悬着的问题现在有答案了——
  **一条 DAT 条目通常是一个发行版**（`release` 表按「源 + DAT + 条目名」去重建行），
  **而带汉化记号的条目是变体**：识别只把它挂到**作品**上，发行版留空等裁决补

- **状态：** resolved —— 已补进词表：**DAT 条目**，并写明「一条 DAT 条目等于一个发行版」这个假设会出错（TOSEC 一次发行多条转储、MAME 记到芯片一级）。其余「件/整包/指纹」是实现词。

## D98 · 票 08 · 沉淀库的锚是 **CRC-32 加大小**，`sha1` 那一列现在一律为空

     A 说的「没人能预期」，预期不了的是没写出来的东西；写在屏上的那个词本身就是预期。
  3. **条数当场跟着变。** 筛选器底下常驻「筛出 N 行 · M 个变体」
     （`Screen::filtered_total`），换一个连接词，那两个数当场重算。行数变多不是事后
     才发现的意外，是按下那一下的**回执**。

  换句话说：A 保住的是**默认路径**（那是它真正在保的东西），B 那点表达力则由一套完整的
  规则语言一次给足，而不是在五个复选框上打补丁——五个复选框各自加一个「或」开关，
  会长出一套只在浏览屏成立、写不进子库的第二语言，那才是这条挂账最坏的收场。

  **顺带收掉的是一条更大的裂缝**：从此浏览屏筛出来的那批与子库同步搬过去的那批走
  **同一套语言**，两个求值器（内存的 `sublibrary::select`、SQL 的 `catalog::filter`）
  由 `crates/core/tests/filter.rs::屏上筛出来的与子库选出来的是同一批` 逐条钉着——
  50 多条规则各跑两遍，比的是两批键完全相同。

## D156 · 票 25 · 排差量预览还跑在画帧那条线程上

- **问：** **同步**已经搬到后台线程（几十 GiB 的拷贝不能卡住窗口），而**排差量预览**
  没有：真机量级的合成数据上 **343 ms**，其中大头是 `sublibrary::facts` 走一遍全库。
  卡上文件多时目标侧那一遍 `observe` 还会更久。
- **选项：** A 先留在主线程（推荐：343 ms 是一次点击的等待，而把 `prepare` 挪到后台
  要把 `Catalog` 的连接也搬过去——`rusqlite::Connection` 不是 `Sync`，等于要为界面
  再开一份连接，那是一条会长出「两份库不一致」的路）｜B 后台线程 + 另开一份只读连接
- **不处理会怎样：** 点「排差量预览」之后窗口会僵住零点几秒到几秒，期间连「停下」
  都没有。
- **状态：** resolved —— **走 B**（后台线程 + 另开一份只读连接），票
  `gui-redesign/01`（任务台）做的。裁决记在本条，**未迁回票 25**（迁回由维护者自己做）。

  **B 当初被否掉的理由是「为界面再开一份连接，那是一条会长出『两份库不一致』的路」。
  那句顾虑靠三条构造上的事实拆掉，不是靠纪律**（`Catalog::read_only` 的文档注释写着
  同样三条，`crates/core/tests/task.rs::后台那份只读连接读得到同一份库而且写不动`
  钉着）：

  1. **它写不动。** 连接带 `SQLITE_OPEN_READ_ONLY` 开出来，往它上面写一个字节都会被
     SQLite 当场拒绝——**全程只有一个写者**，还是界面那条线程手里原来那份。
  2. **它不建表、不改版本。** 建表与写 `schema_version` 那一套只在 `Catalog::open` 里
     做一次；只读那份只**核对**版本，对不上就不开（开出一份读得出行却对不上号的库，
     比打不开更坏）。
  3. **它活得比一趟活还短。** 一趟排差量预览开一份、跑完就丢，不是一份放在那儿慢慢
     变旧的缓存。WAL 让它在这几百毫秒里读到一份一致的快照，界面那条线程同时在写也
     不打架。

  「后台读的是排它那一刻的快照」这件事也接不上骗人的路：改过规则之后那份预览本来就
  当场作废（ADR-0016，`Screen::invalidate`），**这张票把正排着的那一趟也一并不认了**
  ——它跑完了也没人认领，因为它说的已经不是眼下这套选择集会做的事。

  另外两件顺带定下的：**分不出第二份连接时直说**（只活在内存里的合成数据库），
  那一趟改为**就地跑**并照样进任务台（挂单 Q52）；**停下的粒度是两步之间**，
  最长那一步是折事实（挂单 Q51）。
