# 09 — 光盘序列号识别与 NKit 前置检测

**What to build:** 光盘类变体的识别不再依赖读完整个镜像——只读镜像前部的几百字节取出内部序列号。识别一个 8GB 的 ISO 不需要读 8GB。

同时插入 NKit 检测，且必须卡在任何 CRC 匹配之前：NKit 文件的 CRC-32 可能与完好转储相同而内容并不一样，漏掉这一步会把 NKit 误认成完好转储。

**Blocked by:** 05, 07

**Status:** done

**收尾（2026-09-02）**：791 个测试全绿，`cargo clippy --workspace --all-targets` 与
`cargo fmt --check` 干净。九条验收逐条见下，**两条带保留**（第 6 条的 CHD 与第 7 条的
「够不到 `0x200`」，各指向一条挂账）。

**这票要的那个数**：真机 46,444 个变体 → **命中 30,734**（票 07 是 30,024，**+710**）。
**撞了 DAT 的里面 72.9%**（票 07 是 71.7%），**全部变体里 66.2%**（64.6%）。
**+710 全部落在光盘世代**：PSV 67.6% → **94.1%**、PSP 51.0% → **54.1%**、
PS1 10.5% → **29.4%**、NGC 24.6% → 26.6%、PS2 38.8% → 39.5%、WII 0% → 1.0%。
**8.60 TiB 里只读了 1.93 GiB**（0.022%），首趟 232.4 秒；事实落库之后重跑
**11.9 秒、0 字节**。全部实测数字进了 `docs/library-facts.md` 的

  真机 PS1 命中 36 → **101**（10.5% → 29.4%）。测试

- [x] 从 PSP 与 PS3 的参数文件取得光盘标识与标题标识

  `identify::sfo` 读 PARAM.SFO（索尼四代机共用的那张键值表），`disc::read_sfo` 从
  `PSP_GAME/PARAM.SFO` 取 `DISC_ID`、从 `PS3_GAME/PARAM.SFO` 取 `TITLE_ID`，
  两处都顺带取 `TITLE` 与 `APP_VER` / `DISC_VERSION`。另有 PSP 的**免解析通路**：
  主卷描述符的 Application Used 区（`0x8373`）写着 `ULUS-10339|…`，形状卡死成
  「四字母 + `-` + 五位数字」；它**排在最后**，只在那份 SFO 落在读取上限之外时顶上
  ——SFO 那条还带着标题与版本。**标题与版本写进依据**（「盘里的标题是「…」，版本 …」）。
  真机 PSP 命中 3,091 → **3,284**。测试 `sfo::读得出规范里那份最小示例`、
  `magic_不对就不是_sfo`、`条目数写得再离谱也不会空转`、
  `disc::psp_的免解析通路读得到序列号` / `只认那个形状`、集成测试
  `psp_的参数文件读得出光盘标识与标题`。

- [x] 从 PSV 变体内的 `param.sfo` 取得 TitleID、标题与版本（库体检实测全库 809 个，明文）

  **这是这张票最大的一块。** PSV 的 1,416 个变体多半是**目录树转储**——整个变体里
  没有一份「整文件」可以算哈希，票 07 在它们身上只能报「无判据」。锚是里面那份
  一两千字节的 `sce_sys/param.sfo`：`probe_discs` 扫变体的**全部成员**（含角色为
  **内部资源**的那些，它们压根不产生候选、也就不在 units 里）找按名字叫 `param.sfo` 的，
  读出 `CONTENT_ID` / `TITLE_ID` / `TITLE` / `APP_VER`。真机探到 **1,582 份、读出 1,538 条**。
  **PSV 命中 347 → 779，命中率 67.6% → 94.1%。** 测试
  `psv_目录树转储靠_param_sfo_认出来`（连 `CONTENT_ID` 精确、`TitleID` 只对上里面
  那一段两档一起验）。

- [x] PSV 目录名里直接写着的 TitleID（`AIME00001(...)` 这类）作为一条独立依据

  `identify::serial::title_id_in_name` 认「四字母加五位数字、前后都是边界」这个形状，
  变体名里任意位置都找得到（`A11 新罗罗的炼金工房[PCSG00245][日版]`）。它产出一条
  **独立的候选**，但**永远不自动通过**——目录只是强先验（ADR-0011），这一条连内容
  都没看，依据里明说「这一条只看了名字没看内容」。盘里读出同一串时它不重复落一条，
  盘读不到时（`--no-read-library`、盘不在位）它顶上。**同一个形状只写一处**：
  `scope::title_id_prefix` 判 homebrew 前缀走的是同一个 `title_id_head`。
  测试 `serial::目录名里的_titleid_认得出来`、`不是那个形状的名字不许硬切一段出来`、
  `名字上看来的那一条永远不自动通过`、集成测试
  `目录名里的_titleid_是一条独立的依据且不自动通过`。

- [x] 压缩镜像被当作变体本身的形态处理，不被当作容器解包

  `identify::disc` 一个也不「解包」（ADR-0014）：**它就是变体本身的形态，
  身份从它自己的结构里读**。CSO 解的是**头几个块**——那是格式自带的随机访问
  （索引项低 31 位左移 `index_shift` 是偏移，高位表示这一块没压），不是把它当归档展开；
  其余全是定长偏移上的明文读取。`ContainerKind::for_path` 一个压缩镜像扩展名都不认，
  这张票也没往里加。测试 `pbp_与_cso_都不解全就取得到标识`、
  `压缩镜像的光盘头在固定偏移上读得到`。

- [x] 从 PBP、CSO、CHD、RVZ、WBFS 的固定偏移处读取明文结构取得标识，不完整解压
      —— **带保留，见挂账 D106 / D107**

  | 壳子 | 读哪儿 | 真机探了 / 读出标识 |
  |---|---|---|
  | PBP | `+0x08` 的 `param_sfo_offset`（通常 `0x28`）处那张**未压缩**的 PARAM.SFO | 272 / 269 |
  | CSO | 头部给出原始大小与块索引，头几个块 deflate 解出来就是 ISO 的开头 | 41 / 28 |
  | RVZ / WIA | 光盘头 `0x80` 字节原样躺在**文件偏移 `0x58`** | 与未压缩镜像并计 |
  | WBFS | Wii 光盘头 256 字节在 `1 << hd_sector_shift` 处 | 186 / 184 |
  | CHD | 头部 `+12` 版本、`+32` 逻辑流长度、`+64` `rawsha1`、`+84` `sha1` | 84 / **0** |

  **CHD 那 0 是保留。** 票据的交底原话是「CHD 的 `chdman info` 给的两个 SHA-1 都对不上
  Redump——别拿它去撞 DAT」，所以它的「固定偏移明文结构」读到了、也如实记下了
  （版本与逻辑流长度进报告），**但不产出能撞 DAT 的标识**。盘内的 `SYSTEM.CNF` 要先解
  Huffman 编码的 hunk map 再解一个 hunk（`cdlz`/`cdzl`/`cdfl` 三种编解码器），
  那是一整套解码器不是「读几百字节」——**挂账 D106**。ZSO（lz4）、DAX、GCZ 同理，
  真机上三种加起来 3 份文件，**挂账 D107**。测试
  `pbp_的_param_sfo_在固定偏移处且没被压缩`、`cso_的前几块解得出来`、
  `cso_v2_明说读不了而不是解出一堆乱码`、`wbfs_的光盘头在_hd_sector_size_处`、
  `chd_只记下它是什么绝不产出能撞_dat_的标识`。

- [x] NKit 检测在任何 CRC 匹配之前执行，判据为光盘逻辑偏移处的标记
      —— **带保留，见下**

  判据是**光盘逻辑偏移** `0x200` 处的 `NKIT`（Dolphin `VolumeDisc::IsNKit()`）。
  **「逻辑」两个字是这张票对票 07 的更正**：票 07 按**文件**偏移验，而 `.nkit.gcz`、
  WBFS、CSO 里那一处不在文件的 `0x200` 上——按文件偏移验等于对整批压缩镜像装作验过了
  （ADR-0014 三修订）。

  **顺序**：`probe_discs` 跑在 `assemble` 之前，任何命中被**接受**之前 NKit 已经有结论。
  决定探不探的判据取自**内容自己的形态**（`disc::may_hold_nkit`：形态上可能是一张
  GC / Wii 光盘的一律照探），**不取自 CRC 撞上了什么**——拿 CRC 的结果决定要不要验 NKit
  就把顺序倒过来了，而 NKit 存在的理由正是 CRC 会骗人。代价是多读 0.24 GiB、多花 49 秒。
  名字里的 `.nkit.` 只**补充**结论、不代替它（只会往「更难自动通过」的方向抬）。

  **保留**：WBFS 只交得出 256 字节的 Wii 光盘头、WIA/RVZ 只交得出 `0x80` 字节，
  两种都**够不到 `0x200`**；CHD 与 GCZ 的负载解不开。这些一律记成**没验过**
  （`nkit` 留 `None`），**没验过就不许自动通过**。真机：**验过 1,967 份、0 份是 NKit**，
  另有 4,647 份没验。测试 `disc::nkit_在逻辑偏移_0x200_上认出来并且盖在标识之前`、
  `没验过与验过不是一回事`、`名字里写着_nkit_的只补充不代替字节判据`、集成测试
  `没验过_nkit_的_gc_与_wii_镜像不许自动通过`，以及票 07 留下的
  `nkit_验在撞_crc_之前撞上了也不许自动通过`、`验不了_nkit_的_gc_与_wii_镜像不许自动通过`。

- [x] 检出的 NKit 文件被明确标记，不参与精确哈希命中

  `ContentUnit::nkit()` 分三态（**没验过 / 验过不是 / 是**），`candidate_of` 据它把
  哈希命中降一档：验出来是 NKit 的、以及**撞上的记录说它是 GC / Wii 光盘却没验过的**，
  一律 `accepted = false`、置信度中置信，依据里写明「Dolphin 明说它的 CRC32 可能与
  好转储相同而内容不同，不许自动通过（要先转回 ISO）」。序列号那一层同样受这条约束
  （`Evidence::nkit_clean`）——一份 NKit 镜像的序列号照样是对的，但它不是一份好转储。
  报告里 NKit 单独一行计数。真机这块盘上是 0 份，闸门本身有 fixture 上的可断言证据。
  测试 `serial::nkit_验不了的序列号命中也不自动通过`，加上上一条那几个。

- [x] 序列号命中的候选置信度等同于精确哈希命中

  `identify::serial::candidates`：DAT 里那条记录写的**就是这一串**（折平之后完全相等）
  → **高置信、自动通过**，与精确哈希命中同档。落到实现上分了两档，因为「对上」这件事
  本身有粗细之分：DAT 写的是一条 CONTENT_ID 而只有里面那段 TitleID 对上时 → 中置信、
  通过但标记——同一个 TitleID 下面躺着本体、更新和一堆 DLC，光凭它说不出是哪一条。
  真机撞出 **6,016 条**序列号候选，**373 个变体是只靠序列号才认出来的**（第一命中层
  在它们身上一条自动通过的候选都没有）。测试 `serial::精确命中的序列号候选自动通过`、
  `只对上_content_id_里那一段的不自动通过`，集成测试
  `ps1_的启动配置读得出序列号并撞上_dat`（断言 `Confidence::High` 且 `accepted`）。

## Comments

**落地形态**：核心在 `crates/core/src/identify/` 新增四个模块——`sfo`（PARAM.SFO，
索尼四代机共用）、`iso9660`（最小定位器：只回答「`SYSTEM.CNF` 在哪、多长」，
不认 Joliet、不递归整棵树）、`disc`（壳子探测 → 逻辑光盘的一段字节 → 标识与 NKit）、
`serial`（第二命中层：折平、撞 DAT、产出候选）；DAT 那一侧新增 `dat::serial`（折平与拆分）
与 `dat::lookup::lookup_serial`；中立库多一张 `content_disc`。命令行没加参数——
这一层是 `romcat identify` 的一部分。

**DAT 库结构版本 1 → 2，必须重新同步一次。** 序列号写在 `<rom serial>` 属性与
`<game_id>` **子元素**上，**不在 `<game serial>` 上**——票 06 的解析器只读后者，于是
Vita 与 PSP 两个平台一条序列号都读不到。补上这两处之后，395 份 DAT 索引出
**95,022 条**序列号。升版本正是为了逼出那一趟重新解析。

**中立库结构版本没动（仍是 4）**，这是一个有意的取舍：`content_disc` 是**新加的表**，
`CREATE TABLE IF NOT EXISTS` 在已有的库上直接建出来，不必让用户删掉 8.60 TiB 的中立库
重扫一遍。代价是这张表不能依赖「谁记得去作废它」，所以它**每一行自带有效期**
（算这一条时那个成员文件的 `len` 与 `mtime_ns`，读回来先对一遍）——即便一个不知道这张表
存在的旧版本程序更新过 `entry`，也不会读到过期的行。

**读不到不落库（ADR-0021）。** 探测的结果分两档：`Probe::Read` 是关于这份内容的**结论**，
只要文件没变就一直成立，落库；`Probe::Missed` 是「**这一趟**没读到」，**绝不落库**
——缓存一次读失败等于让它永久生效，而 macOS 的 fskit 驱动下读不到的那 4,085 个文件
在 Windows 上是正常的，ADR-0018 定的工作方式正是两台机器轮流碰同一块盘。
真机第二趟照样去试了那 74 份。

**一个真机撞出来的性能陷阱：solid 块。** 7z 的一个块里几个条目是连着压的，解压器
跳不过中间的字节。第一次跑真机时，一份 7z 里的 `.iso` 排在几 GB 的东西后面，
「只读几百字节」当场变成解几个 GB，**一个变体卡住整趟识别**。判据零解压可得
（`block` 与每条的未压缩大小都在容器头里），所以闸设在**开工之前**：排在前面的东西
超过 64 MiB 就放弃，如实报「solid 块太深：这一条前面还压着 X」。真机吃掉 **2,508 条**
（其中 2,459 条是 PSV `.7z` 里 DLC 目录下那份 `param.sfo`；本体那一份通常排得浅，
所以 PSV 照样跳到了 94.1%）。取舍记在**挂账 D109**。

**报告平台表多一列「序列号」。** 与票 07 那条「DAT 条目」同理：**Redump 的官方 DAT
一条序列号都不写**（实测：`<game>` 只有 `name` 与 `id`、`<rom>` 只有四套哈希），
而 PS2 / NGC / WII 的主力弹药正是 Redump。于是这三个平台读得出 `SLPS-25604` 与 `GALE01`
却无处可撞——弹药分别只有 178 / 58 / 27 条。**没有弹药的平台命中率低，与识别准不准
无关**，这一列就是为了让那件事一眼看得见（**挂账 D110**）。

## code-review 处置（fixed point `2cb27b5`）

**采纳 11 条：**

1. **读失败被当成事实缓存，覆盖掉 ADR-0021 的第三态**（Standards，硬）—— 承认。
   `content_disc` 的有效期只看 `(len, mtime_ns)`，而不可读条目这两列是 NULL、`IS` 比较
   恒真，于是一次读失败**永久生效、再也不重试**；同时 `units[].blocked` 被盖掉，
   「元数据读不到（ADR-0021 的第三态）」从报告里消失。已引入 `Probe::{Read, Missed}`：
   `Missed` 不落库、不覆盖已有的 `blocked`（只在那条本来什么都没说时才补一句），
   并单独计数打进命令行那一行。真机第二趟照样重试了那 74 份。
2. **NKit 不再前置于 CRC**（Spec，最严重）—— 承认。`worth_probing` 原先拿「撞上的那条
   记录说它是 GC / Wii」当判据，而那是**用 CRC 的结果决定要不要验 NKit**，顺序倒了。
   已换成 `disc::may_hold_nkit`：判据取自**内容自己的形态**，撞上了也照验。
   代价是真机多读 0.24 GiB、多花 49 秒，写在验收第 7 条里。
3. **文件名当了 NKit 的判据**（Spec）—— 承认。名字里的 `.nkit.` 原先**盖过**字节检查。
   已改成字节判据先跑、名字只**补充**（且只往「更难自动通过」的方向抬），
   补充时依据里写明是按名字算的。测试 `名字里写着_nkit_的只补充不代替字节判据`。
4. **PSP 免解析通路缺形状校验**（Spec）—— 承认。那 512 字节在别的盘上装的是什么谁也
   说不准，只要求「够长、首字母大写」的话一段随机字节就能变成一条自称高置信的序列号。
   已卡死成「四字母 + `-` + 五位数字」（调研 A.13.3 的形状）。测试
   `psp_的免解析通路只认那个形状`。
5. **PS2 漏了 PCSX2 的格式校验**（Spec）—— 承认。已按调研 A.12.2 补上，且**只给
   `BOOT2`**：DuckStation 那边（PS1 的 `BOOT`）一概不校验，照抄两边而不发明第三套。
   测试 `ps2_的_boot2_过格式校验而_ps1_的_boot_不过`。
6. **`library-facts.md` 新小节只写「（数字待填）」**（Standards，硬）—— 承认，那是
   收尾没跟上。已补全（命中率对比、按平台、读了多少、标识从哪儿读出来、NKit、
   solid 块、Redump 没有序列号）。
7. **`Facts.shell` 与 `IdKind` 拿展示词当持久化键**（Primitive Obsession）—— 承认：
   改一次报告用词就会静默作废整张缓存。已按仓库既有的 `FailureReason::code` /
   `ContainerKind::code` 加稳定短码，serde 走短码。
8. **`state.facts` 是三个 `String` 的元组**（Data Clumps）—— 承认，而且同一份 diff 里
   `Wanted` 的文档刚说过「元组里写错顺序编译器不会说话」。已改成
   `catalog::identify::DiscFactRow`。
9. **「四字母加五位数字」写了两遍**（Duplicated Code）—— 承认。`scope::title_id_prefix`
   与 `serial::title_id_in_name` 看的是同一个形状（前者用来跳过、后者当依据），
   两边各写一遍，改一次判据就会有一边跳过、另一边当依据。已抽成
   `serial::title_id_head` / `title_id_at`，`scope` 调它。
10. **`Logical` 就是 `Cow<[u8]>`，`borrowed` 还有个从不使用的参数**
    （Speculative Generality）—— 承认，已删掉换成 `Cow`。同时删掉
    `header::may_be_nkit`（调用点没了，Spec 那边也点了这条死代码）、
    `sfo::looks_like`、`disc::Facts::is_empty`。
11. **两处小疵**：集成测试里 `assert_eq!(x, Some("…").or(x))` 是恒真断言（`.or` 纯噪音，
    读起来却像故意放宽），已改成真断言并顺手断言标题进了依据；`testing/disc.rs`
    自建了一个 `SECTOR` 常量，已改用 `iso9660::SECTOR`——两处各写一个 2048，
    改一次就会有一边造出解析器读不懂的样本。另外测试名 `没验过与验过不是两码事不许混`
    说反了，改成 `没验过与验过不是一回事`。

**驳回 6 条：**

1. **「CHD 不产出任何标识，票据第 6 条含 CHD」**（Spec）—— 驳回。票据的交底原话就是
   「CHD 的 `chdman info` 给的两个 SHA-1 都对不上 Redump——**别拿它去撞 DAT**」。
   它的「固定偏移明文结构」读到了、也如实记下了；读盘内的 `SYSTEM.CNF` 要先解 Huffman
   编码的 hunk map 再解一个 hunk（LZMA / Deflate / FLAC 三种编解码器），那不是
   「读几百字节」，而这张票的口号正是那句话。挂账 D106 写清了什么时候补、怎么补。
2. **「`title_id_in_name` 对所有平台跑，票据限定 PSV 目录名」**（Spec）—— 驳回。
   票据点名 PSV 是因为维护者在那儿看见的，而「名字里写着一串 TitleID 形状的东西」
   这个判断与平台无关；它产出的候选**永远不自动通过**，所以多认一条只是多一条依据。
   限定 PSV 的话，一个名字就叫 `SLPS00898` 的 PS1 目录拿不到依据，而形状一模一样的
   PSV 目录拿得到——那才是说不通的。（票 07 限定 PSV 的是 `scope` 那条**跳过**判据，
   那一条照旧限定，因为错跳一个的代价是一个本来认得出来的变体永远不进管线。）
3. **「`MAX_SOLID_DRAIN` 64 MiB 闸是范围蔓延」**（Spec）—— 驳回。没有它，票据自己那句
   「不完整解压」就不成立：真机第一次跑当场卡在一份 7z 上，解了几个 GB 去够一个
   要读几百字节的条目。判据零解压可得、闸设在开工前、踢掉的逐条点名进报告。挂账 D109。
4. **「报告多一列序列号 / 命令行多一行 / `content_disc` 缓存表是范围蔓延」**（Spec）——
   驳回。那一列回答的是与票 07「DAT 条目」同一个问题（**没有弹药的平台命中率低与识别
   准不准无关**），而 Redump 一条序列号都不写这件事只有那一列说得出来；`content_disc`
   是为了不让这张票**毁掉**票 07 已经兑现的那条性质（挂账 D14：第二趟 0 字节）——
   没有它，第二趟要重读 1.93 GiB。
5. **「`SCHEMA_VERSION` 1→2 强制重解析全部 DAT 是范围蔓延」**（Spec）—— 驳回。
   序列号只写在 `<rom serial>` 与 `<game_id>` 上，票 06 两处都没读；不重新解析一遍，
   这张票**一条弹药都没有**。DAT 库本来就是「删了重取」那条便宜路（`dat::repo` 的
   模块文档），升版本是这件事的正规出口。
6. **「`serial_counts` 用 `prepare` 而不是相邻的 `prepare_cached`」**（Standards）——
   驳回。它一份报告只跑一次，与紧挨着的 `dat_games` 同一档；`prepare_cached` 是给
   每个变体都要跑一次的 `lookup` / `lookup_serial` 用的。

**未处置 1 条（记成挂账 D111）：** 「`.vpk` 里的 `param.sfo` 读不到」（Spec）——
承认。`.vpk` 就是一个 zip，但调研明说**它不是透明容器**（重新打包会得到不同哈希，
No-Intro 就哈希整个 `.vpk`），把它加进 `ContainerKind` 会让它在整条管线里变成「包装」，
与 `CONTEXT.md` 的定义冲突。正解是让光盘那一层**自己**按 zip 打开它读一个文件，
那是另一种接法。真机影响：PSV 的 14 个 `.vpk` 主文件变体加 17 个裸 `.vpk`。
