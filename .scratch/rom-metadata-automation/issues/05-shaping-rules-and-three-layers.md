# 05 — 成型规则与三层内容模型

**What to build:** 扫描产出**变体**而不是裸文件。每个平台声明自己的成型规则，把散落的文件聚成一个变体：`cue` 与它引用的 `bin`、整个 `PS3_GAME` 目录、`(Disc N)` 同族文件。中立库开始承载**作品**、**发行版**、**变体**三层内容层级。

平台由目录给出，但目录只是强先验——文件内容可以推翻它，而这类冲突正是**库体检**最该报的东西之一。

**PSV 是这票最吃重的地方，库体检数据出来后才看清。** 它占全库 **67% 的文件（171,073 个）**，绝大部分是**内部资源**（`at9` 音频 39,360 个、`psarc`、`cpk`、`pck`、`awb`）——库体检里那 56.4% 的「未归类」主要就是它们。**成型规则若没把整个目录树吞成一个变体，库里会炸出十几万条垃圾条目。**

PSV 的安装形态还不止一种：TitleID 直接写在目录名里（`AIME00001(...)`）、`param.sfo` 躺在目录内（全库 809 个）、`.vpk` 安装包、以及被 `.7z` / `.tar.zst` 裹着的。成型规则要认得这几种形态都是「一个变体」。

## Comments

**范围**：只把**成型规则**外置成了声明式配置。`docs/platforms.md` 那句话里的另外三项（头部解析、DAT 源、模拟器映射）还在代码里，等票 07 / 票 06 / 票 21 各自落地时再搬，文档里已注明。

**新增 ADR-0022**「成型跑在中立库上，不跑在遍历途中」，记下三件事：为什么成型不塞进遍历、规则顺序为什么不交给配置、名字模式为什么不用正则。

## code-review 处置（fixed point `0b47cc7`）

**采纳 12 条：**

1. **`变体根 = 上级` 会把合集目录吞成一个变体**（Spec，**这条最严重**）—— 真库形态是 `PSV/PSVENJP/<游戏名>/…`，只要有一份转储的锚落在 `<游戏名>` 那一层，上溯就会落到 `PSVENJP`，「外层的赢」再把同级 220 份**已经正确成型**的转储全吸进去。已加 `refuse_collection_dirs`：候选根底下若坐着另一个锚，而那个锚自成一份转储、且不在候选根紧下面的分区目录里，这个锚就退回自己那一层。回归测试一对：`合集目录不许把同级的几份转储吞成一个变体` 与 `同级的几份转储各归各的分区目录照样吞得下`（守卫不许误伤 `app`/`patch`/`addcont` 与 MaiDump 的 `<TitleID>_patch`）。

## 挂账裁决（2026-09-01 本票完成时）

- **D28 报告里「未归类」与词表 `内部资源` 的 `_Avoid_` 词撞名** — **维持那一栏的名字，理由更硬了**。成型跑起来之后，「未归类」与「内部资源」在报告里**同时出现且含义分明**：前者是「扩展名不在任何表里」（三类构成那一节），后者是「变体内部的文件」（成型那一节的成员身份）。真盘上 158,641 个内部资源里绝大多数确实也是「未归类」，但两个数各自回答不同的问题——一个问「探针覆盖到没有」，一个问「它属于哪个变体」。改名反而会把这层区分抹掉。**结掉。**

## 三条已知限制
