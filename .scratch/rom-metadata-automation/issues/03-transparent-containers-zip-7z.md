# 03 — 透明容器：zip 与 7z 零解压读取

**What to build:** 工具能不解压就读出 zip 与 7z 内部每个文件的 CRC-32、未压缩大小与文件名。体检报告因此能看见容器内部的真实构成，而不只是「这里有一个 3GB 的压缩包」。

这是整个项目性能可行性的支点：DAT 的每条记录都带大小与 CRC，因此第一命中层可以完全不解压。

**Blocked by:** 02

**Status:** done

- [x] 不解压即可读出 zip 与 7z 内部文件的 CRC-32、未压缩大小与文件名 —— 测试 `zip_不解压就读出内部文件的名字与未压缩大小与_crc32`、`七z_不解压就读出内部文件的名字与未压缩大小与_crc32`。真盘实测：FC + GB + gba 三个子树 8,512 个真 zip 与 299 个真 7z、13,639 个内部文件，**零解压读到的 CRC-32 与完整解压实算的一一对上，0 出入**；FC 子树一趟扫完 26,986 个内部文件，其中 26,984 个（**100.0%**）带 CRC-32
- [x] 正确处理 zip 的通用标志位第 3 位——局部头部的 CRC 与大小为零时改读中央目录 —— 测试 `zip_通用标志位第三位置位时改读中央目录`，它先断言样本的 local header 那 12 字节确实全是零，再断言清单给出的是真值。**保留：** 真盘 FC 子树抽了 6,000 个真 zip，置了第 3 位的是 0 个，这一条只有手造样本的证据
- [x] 正确处理 ZIP64 哨兵值 —— 测试 `zip64_哨兵值指向_extra_field_里的真值`（条目级哨兵 + 归档级 ZIP64 EOCD 两种）与 `zip64_的_extra_field_被写满时按位置取而不是按哨兵顺序取`（现实里有工具无条件写满前几个字段）。**保留：** 同一批 6,000 个真 zip 里没有 ZIP64，同样只有手造样本的证据
- [x] 7z 按 solid block 分组读取，一块一趟流式喂多个 hasher，不对每个内部文件各解压一遍 —— 测试 `solid_的_7z_一块只解一次而不是一个文件解一趟`（断言 `blocks_decoded == 1` 且解压量等于块的总大小，并与朴素做法逐条对照）、`非_solid_的_7z_每个文件自成一块`、`一趟流同时喂多个_hasher`。真盘实测 27 个真 solid 7z，最狠的一个（920 个内部文件）按块调度解 **9.29 MB**、朴素做法解 **3.83 GB** —— **412 倍**，比调研估的约 100 倍还大
- [x] 提供流式部分解压能力：读取内部文件前若干字节后即可提前中止 —— 测试 `zip_读够前若干字节就中止`（64 KiB 的条目只解出 0x200 字节）、`solid_块里最后一个想要的条目读完就中止`、`zip_跳过的条目一个字节都不解`。真盘实测：2,000 个真 zip 与 167 个真 7z（含 23 个 solid）按 `Demand::Prefix(512)` 读，每个内部文件都正好拿到 `min(512, 大小)` 字节，0 出入
- [x] 体检报告能给出容器内部的文件数与构成 —— 测试 `体检报告说得出容器内部的文件数与构成`、`盘不在位时报告照样说得出容器里装着什么`、`关掉穿透就一个容器都不去读`。真盘实测（FC 子树，2 分 47 秒）：容器 20,312 个、穿透 20,276 个、穿不透 36 个（全部归类为「不是这个格式」，与系统 `unzip` 对同一批文件的判断完全一致）、内部文件 26,986 个共 6.12 GiB、带 CRC-32 100.0%、solid 容器 23 个；内部构成按三类主线与按扩展名各出一张表
- [x] 有测试覆盖 solid 与非 solid 两种 7z、以及存储与压缩两种 zip 条目 —— solid/非 solid 见上一条对应的两个测试；zip 的存储与压缩两种条目见 `zip_不解压就读出内部文件的名字与未压缩大小与_crc32` 与 `zip_存储与压缩两种条目都取得出内容`。`crates/core/tests/containers.rs` 共 24 条，全绿

## Comments

**范围**：只做了 zip 与 7z。`rar`（票 04）与 `zst`（票 26）有专门的测试 `rar_与_zst_这票不碰` 钉着「这票故意认不出来」。

**真盘查出来的一个真 bug**：主库 GB 目录下那批 2002 年的 zip，EOCD 之后还挂着 3 个填充字节。原先按「EOCD 必须正好收在文件末尾」去找，把它们整批判成不是 zip（GB 子树 110 个、FC 子树 1 个）。改成「候选放得下自己声明的注释，且顺着它算出来的中央目录起点上真的坐着一条 `PK\x01\x02`」之后，GB 子树 3,000 个真 zip 全部读得出来。回归测试是 `eocd_后面还挂着东西的_zip_照样读得出来` 与 `压缩数据里碰巧出现的_eocd_签名不会认错`。

**code-review 处置**：采纳 9 条、驳回 3 条，逐条见提交说明。其中两条是 spec 轴查出来的真错：zip 把目录条目也数成了块（`Contents::blocks`）；穿不透的容器被当成「已穿透」记进基线，于是一次性的读失败会变成永久结论——后者与库里 1.59% 在 fskit 下读不到元数据的文件直接相关。

**挂账**：D21–D27（zip 解析器自己写、内部文件名的编码、7z 用 sevenz-rust2、穿透不抽样、MSRV 1.85→1.93、中立库结构版本 1→2、「穿透 / 穿不透」不在词表里）。
