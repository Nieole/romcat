# 26 — 透明容器：zst 与 tar.zst

**What to build:** 工具能识别 `.zst` 与 `.tar.zst` 里的内容。这是主库中容量第二大的一类（2,685 个文件、2.50 TiB），且是**第一个进不了「零解压读 CRC-32」快路的容器**——识别管线要为它开一条新路径。

代价是一次性的：全量解压约 3.8–7.6 小时，瓶颈全在磁盘（zstd 解压速度是磁盘的 7–10 倍，解压等于免费）。**结果必须缓存**，否则每次扫描都要重付。

**Blocked by:** 03

**Status:** done

- [x] 零解压读出 zstd 帧头：`Frame_Content_Size`（**仅 53% 的真实文件带它，不能假设存在**）、`Content_Checksum` 标志、字典 ID
  - `container::zst::parse_frame`（≤14 字节，自己按规范位定义解，不借 `zstd-safe`——它不透出校验和标志）。
  - 单元测试 7 条（`帧头四个字段各自解得出来`、`tar_zstd_那种帧头没有大小也没有校验和`、`单段帧的大小只有一字节而且就是窗口`、`两字节的大小要加二百五十六`、`字典_id_零解压就查得出来`、`旧版帧与不是_zstd_是两句不同的话`、`保留位为一是结构坏了`）。
  - **真机 1,009 个 `.zst` 普查，每个只读 ≤131 KB，合计 33 秒**：带 `Frame_Content_Size` **559 个（55.4%）**、带 `Content_Checksum` **1,009 个（100%）**、字典 ID **0 个**。与调研的 53% / 100% / 0% 一致。**新发现：它按打包来源分岔**——NDS 那批 559 个全有，PSV 那批 450 个全无（记进 ADR-0014 再修订）。

- [x] 帧头里带外部字典 ID 的文件被标记为无法独立解压（真实库中为 0，但不能假设）
  - `ContainerError::NeedsDictionary(u32)` → **新的** `FailureReason::NeedsDictionary`（报告数得出「有多少个缺字典」，与「结构坏了」分开）。
  - 头部抽样那一侧报 `Parsed("zstd 帧：需要外部字典 N，无法独立解压")`——**不是 `Mismatch`**：帧头不但读到了还完全读懂了，读懂的结论就是它解不开（code-review 采纳）。
  - 测试 `帧头带外部字典_id_的被标记为无法独立解压`。真机 1,009 个里 0 个，与调研一致。

- [x] 流式解压读出 `.tar.zst` 内第一个 tar 条目的名字与大小，读够即中止；上界按 `Block_Maximum_Size = min(Window_Size, 128 KiB)` 约 131 KB
  - `container::zst::peek` / `peek_bytes`，`PEEK_LIMIT = 14 + 3 + 131_072 = 131_089`。
  - 测试 `读第一条的读盘量有硬上界而且不必整份打开`：拿一个 800 KB 的 `.tar.zst`，用一层**记账主库**断言 `read_head` 只被要过一次、要的正是 `PEEK_LIMIT`，且 `open()` **一次都没调过**——「读够即中止」是量出来的，不是口头的。
  - 真机：1,009 个文件走这条路合计 33 秒（NDS 559 个 10.5 秒、PSV 450 个 22.9 秒，含整趟目录遍历）。

- [x] **正确处理 pax 头**：bsdtar 默认产出 pax，第一个 512 字节块是 `PaxHeader/…` 伪条目（`typeflag='x'`），真条目在偏移 1024。「读前 512 字节取文件名」是错的
  - `container::zst::member` 走条目链，伪条目返回 `None`。
  - 测试 `pax_伪条目不会被当成真条目`：**先断言样本真的带着那个坑**（偏移 0 是 `PaxHeader/真条目.vpk`、`typeflag='x'`、真条目在 1024），再断言两条路径拿到的都是真名字。
  - **真机多出一个坑，调研没写、`tar` crate 也没接住**：NDS 那批 559 个里 **414 个（74%）** 用的是 GNU longname，而 `././@LongLink` 块是**老式 v7 头**（magic 处全零）——`tar` crate 要求伪条目自带 `ustar` 魔数，于是把它当成真文件交出来（**448 条假条目**），真条目的名字停在 100 字节处、常截在 UTF-8 字符中间（**163 条有损**）。`member` 自己认 `typeflag='L'`；修正后假条目 0、有损名字 0、内部文件 1,173 → 725，**随机抽 10 份与系统 `bsdtar` 的 `tar -tvf` 逐条一致**。测试 `gnu_longname_伪条目不会被当成真条目而且真名字不被截断`。

- [x] 列全内部清单时如实走完整解压——tar 是顺序格式，没有捷径；该路径的结果必须持久化缓存
  - `container::zst::list`：`zstd::Decoder` → 取 512 字节明文认 tar → `Chain` 接回去 → 走完整条流。
  - 落库沿用已有的 `container` / `container_entry` 两张表，与 zip / 7z 同一条路，**没有为 zst 另开表**。
  - 真机（NDS 559 个 / 21.20 GiB）：完整列清单 **2 分 51 秒**与 **2 分 40 秒**（两趟），约 125–135 MB/s，CPU 34–37%——**全程磁盘受限**，与调研「解压等于免费」一致。外推全库 2.50 TiB 约 **5.4–5.8 小时**，落在调研估的 3.8–7.6 小时内。
  - **缓存实测：二次扫描 1.0 秒**，数字一字不差（2:51 → 1.0 s）。

- [x] 单文件 `.zst`（非 tar）与 `.tar.zst` 分别处理，内部名的推导规则不同
  - 判据是**字节不是扩展名**：解出第一个块，看前 512 字节是不是 tar 头（`ustar` 魔数**或**头部校验和自洽，后者接住老式 v7）。
  - `Inner::Single` 的内部名 = 外层文件名去掉 `.zst`（与 RetroArch 的 zstd 后端同一条规则），大小优先取 `Frame_Content_Size`，没有就量一遍。
  - 测试 `裸_zst_的内部名是外层名去掉后缀`、`名字像_tar_zst_而里面不是_tar_时按单文件处理`、`老式_v7_的_tar_靠头部校验和也认得出来`、`裸_zst_的内容取得回来`。

- [x] 容器读取层的接口不因 zst 而变形：调用方拿到的仍是「内部文件的名字、大小、可得的校验和」，只是 zst 的校验和字段为空
  - `InnerEntry` / `Contents` / `Listing` / `ReadPlan` / `read_entries` 一个字段都没动；zst 只是多了一个 `ContainerKind::Zstd` 与一个 `Locator` 分支。
  - `InnerEntry::crc32` 在 zst 上恒为 `None`；测试 `列全清单读得出每条的名字与大小但一条_crc_都没有` 断言 `without_crc() == file_count()`。真机 33,410 个 zst 内部文件（NDS 724 + PSV 32,686），带 CRC 的 **0 个**。
  - 唯一的签名变化是 `FailureReason::all()` 从 `[Self; 5]` 变成 `[Self; 6]`（新增缺字典这一类）。
  - **保留：**「代价」这一侧确实变形了，而这躲不掉——zip / 7z 穿得透，zst 穿不透。于是 `ContainerKind::is_penetrable()` 把这个区别摆到台面上，报告与调度器都照着它说话；`CONTEXT.md` 的 `透明容器` / `穿透` / `穿不透` 三条同步改准。

- [x] 缓存以文件的路径、大小、修改时间为键，与增量扫描一致
  - **没有另造一套**：直接沿用 `Baseline`（`(路径, 大小, 修改时间)` 三元组）与 `Baseline::penetrated`，与 zip / 7z 走的是同一条判据。
  - 测试 `加了开关才读并且第二趟直接沿用中立库里的结论`、`内容变了就重解一遍而不是沿用旧清单`。
  - 真机：读过一次之后二次扫描 **1.0 秒**；换了内容 + 拨了 mtime 则重解（单元测试覆盖，真机未造改动——**主库只读**，ADR-0004）。

## Comments

**默认不跑，要 `romcat scan --zst`（挂账 D94，偏离票据）。** 票把代价定性为「一次性的」，没说要不要默认付。真机实测这一趟全库约 5.4–5.8 小时，而默认的 `romcat scan` 眼下是半小时量级——不打招呼就让它变成一整夜是不该做的事。于是加了开关，默认关；没读过的那批**既不是穿透了也不是穿不透，而是「还没读过」**，报告单列一栏并说清「加 `--zst` 就能读」，免得 615 个容器从报告里整个消失。理由与取舍写在 D94 与 ADR-0014 的再修订里。

**识别层这一版不为没有 CRC 的内部条目开「解压算哈希」的慢路（挂账 D95）。** zst 的内部条目一条校验和都给不出来，它们落进 `identify` 已有的「容器没记这一条的 CRC-32」那条挡路理由。真正要认的是 `param.sfo`（票 09）与外层文件名里的 TitleID，那是票 09 / 10 按变体决定值不值得解，不该在第一命中层无差别地对 2.50 TiB 开慢路。

**票 09 的前置已经通了。** 真机 PSV `【迷你游戏】` 71 个 `.tar.zst` / 13.30 GiB，1 分 34 秒读出 32,686 个内部条目，其中 **136 个 `param.sfo`，71 个容器全都有**；实取一份（第 2,095 条 / 共 2,106 条）拿到前 512 字节，头 4 个字节是 `00 50 53 46`（`\0PSF`）。取一条要解 111 MiB 是**顺序流跳不过去**的实价，如实记在 `ReadStats::bytes_decompressed` 里。
