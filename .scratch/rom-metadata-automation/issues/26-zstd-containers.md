# 26 — 透明容器：zst 与 tar.zst

**What to build:** 工具能识别 `.zst` 与 `.tar.zst` 里的内容。这是主库中容量第二大的一类（2,685 个文件、2.50 TiB），且是**第一个进不了「零解压读 CRC-32」快路的容器**——识别管线要为它开一条新路径。

代价是一次性的：全量解压约 3.8–7.6 小时，瓶颈全在磁盘（zstd 解压速度是磁盘的 7–10 倍，解压等于免费）。**结果必须缓存**，否则每次扫描都要重付。

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] 零解压读出 zstd 帧头：`Frame_Content_Size`（**仅 53% 的真实文件带它，不能假设存在**）、`Content_Checksum` 标志、字典 ID
- [ ] 帧头里带外部字典 ID 的文件被标记为无法独立解压（真实库中为 0，但不能假设）
- [ ] 流式解压读出 `.tar.zst` 内第一个 tar 条目的名字与大小，读够即中止；上界按 `Block_Maximum_Size = min(Window_Size, 128 KiB)` 约 131 KB
- [ ] **正确处理 pax 头**：bsdtar 默认产出 pax，第一个 512 字节块是 `PaxHeader/…` 伪条目（`typeflag='x'`），真条目在偏移 1024。「读前 512 字节取文件名」是错的
- [ ] 列全内部清单时如实走完整解压——tar 是顺序格式，没有捷径；该路径的结果必须持久化缓存
- [ ] 单文件 `.zst`（非 tar）与 `.tar.zst` 分别处理，内部名的推导规则不同
- [ ] 容器读取层的接口不因 zst 而变形：调用方拿到的仍是「内部文件的名字、大小、可得的校验和」，只是 zst 的校验和字段为空
- [ ] 缓存以文件的路径、大小、修改时间为键，与增量扫描一致
