# 29 — 扫描器三处改进

**What to build:** 挂账逐条确认时定下来的三件活，都落在已交付的扫描器上，互不依赖，可一并做。

**Blocked by:** 02

**Status:** ready-for-agent

## 一 · 并发按介质自适应（挂账 D9）

默认并发是「按 CPU 数取，夹在 2 到 8」——**那是按 CPU 密集型工作设计的**。真机实测扫 NTFS 外置盘时 CPU 占用只有 **2.7%**，线程绝大部分时间在等文件系统驱动返回，是**高延迟 I/O 密集型**。两者的最优并发差一个数量级。

改成先探测几次目录读取的延迟，据此定并发。这个探测顺带能分辨两种相反的情况：**磁头寻道受限**（提高并发会造成寻道风暴、更慢）与**驱动软件开销受限**（提高并发能掩盖延迟、更快）。

- [ ] 开扫前探测目录读取延迟，据此定默认并发；`-j` 仍可手动覆盖
- [ ] 探测本身要能分辨寻道受限与软件开销受限两种情况
- [ ] **改默认值之前必须有一次干净的实测**：用两个**都是冷缓存**的可比目录，各跑一个并发档，按「目录/秒」归一化后比较。同一目录跑两次永远会被缓存污染——上一次的单侧检验就是这么失败的（热缓存快 11.8 倍，把并发效应完全淹没）
- [ ] 实测数字写进 `docs/library-facts.md` 或专门的调研文档

## 二 · `--library` 给主库起名（挂账 D16）

中立库的文件名现在按主库**绝对路径**的哈希取。可 macOS 重挂一次盘就可能从 `/Volumes/新加卷` 变成 `/Volumes/新加卷 1`，Windows 上盘符也会变——**换了挂载点就找不到原来那份中立库，全库白扫一遍**。而 ADR-0018 定的工作方式正是盘在两台机器之间来回接，所以这事会反复发生。

中立库里的键已经是相对路径了（ADR-0020），偏偏定位那份库的文件名还是按绝对路径取的。

- [ ] 加 `--library <名字>`，中立库跟名字走而不跟绝对路径走
- [ ] 不给 `--library` 时维持现有行为（按绝对路径哈希），不破坏已有的库
- [ ] 同一个名字在不同路径下能找到同一份中立库。**用本地 fixture 验，不要卸载重挂用户的外置盘**：把 fixture 目录扫一遍，改名或移到另一个路径，用同一个 `--library` 名字再扫，确认判为全部未变而不是全部新增
- [ ] 两个不同的主库用同一个名字时要报错而不是混表——中立库的键是相对的，混表会直接撞车
