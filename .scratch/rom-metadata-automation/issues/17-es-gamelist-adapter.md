# 17 — ES gamelist 适配器无损往返

**What to build:** 第二个无损往返档的适配器。它一个顶好几个——多个安卓端前端直接复用这个格式，做透它，多设备并用就基本成立了；中文社区分享的现成元数据包也大多是这个格式，维护者因此能把别人做好的成果吃进来。

两个必须处理的细节：这个格式的文件有两个根元素，技术上不是合法 XML，标准解析器会直接失败；以及**用户状态**字段就长在同一个文件里，导出时若省略等于把维护者的收藏与游玩记录清零——必须从快照原样搬运。

**Blocked by:** 16

**Status:** done

- [x] 能正确解析双根元素的文件，不因其不合法而失败

  不用文档级解析器：`crates/core/src/adapter/gamelist.rs` 自己写了一遍词法，把文件拆成一串带零件的 `Node`（标签名、每个属性的引号与前后空白、`>` 之前的空白、自闭合与否）。词法里根本没有「根元素只许一个」这条规矩。
  证据：单元测试 `两个根元素的文件读得动而且往返一个字节都不差`、集成测试 `两个根元素的文件读得动_档位是实测出来的`、命令行测试 `导入别人分享的_gamelist_把用户状态搬运的账说出口`。真机 22 份文件里 `<alternativeEmulator>` 那一段导出后原样还在。

- [x] 收藏、游玩次数、上次游玩等用户状态从快照原样搬运，绝不生成也绝不覆盖

  `USER_STATE` 那七个元素（`favorite` / `playcount` / `lastplayed` / `playtime` / `gametime` / `timeplayed` / `completed`）**一个都不折进** `Game`——中立模型里没有它们的位置，于是「生成一个」这条路径在构造上不存在；它们只躺在快照里，导出时随没变的那些一起原样搬回去。`Preserved::user_state` 数搬了几处，导入报告直接印。
  证据：单元测试 `用户状态一个都不折进中立模型_只在快照里躺着`、`导出时用户状态逐条原样搬过去_省略等于清零`、`从头生成时一个用户状态元素都不写`；集成测试 `导入把包里的值落进中立库_而用户状态一处都不落`、`导出把用户状态逐条原样搬过去_省略就等于清零`。
  **真机数字**：往 22 份导出的 gamelist 里注入 33,165 处用户状态（每 7 个条目一组，五样俱全），导入后报告数出 33,165 处，再导出一趟盘上仍是 33,165 处、值一字未改，`<game>` 段数 46,380 前后不变。

- [x] 导入他人分享的元数据包时与现有内容合并而非覆盖

  文件侧：`render` 里两趟认领（先 `Entry::origin`，再按 `<path>`），两趟都没认领到的段**原样留着**；段内没变的元素一律照搬原文。
  证据：单元测试 `别人分享的包里没认出来的条目照搬不删`、集成测试 `导出是合并不是覆盖_包里没认出来的条目一条不少`（别人机器上那个游戏连它的 `playcount` 一起留着，而台版那一条是合并进原段、没有写成第二条）。真机上 `kept_verbatim` 为 0、段数不变，说明既没漏认也没重复写。
  **保留**：中立库侧「先后导入两份**不同**的包」这一档没验——两份包共用同一个源名 `ES-Gamelist`，而 `put_scraped` 是按「锚点+主体+源」整组替换的，后一份会把前一份没覆盖到的字段一起顶掉。根因是源名不能按文件分（它是 `priorities.toml` 的键）。挂在 **D139**。

- [x] 往返测试通过

  档位是**断言**不是声明：`assert_capability` 在手上这份真文件上读进来、以自己为基线写回去、逐字节比。
  证据：`crates/core/tests/gamelist.rs` 全部 9 项、`adapter::gamelist` 21 项单元测试（含 BOM、自闭合标签、CRLF 混 LF、末尾无换行、缺前导 `./`、单引号属性、未知实体引用、`<folder>` 段）。
  **真机数字**：22 份真导出的 gamelist 全部导回来，**22/22 逐字节相同**，实测档位「无损往返」；46,380 条条目**全部**对回中立库里的变体、0 条对不上，落库 96,576 条字段值。导出那一趟每写一份还自查一遍，22/22 也过。

- [x] 媒体目录结构按该格式的约定铺设

  `Gamelist::media_placement` 交出 `downloaded_media/<平台目录>/<类型>/<镜像 ROM 相对路径>/<ROM 主名>.<扩展名>`，类型目录取自官方那 12 个目录名（`covers` / `screenshots` / `videos`），槽是 `None`——ES-DE 官方原话是 gamelist.xml 里不再包含媒体路径，所以条目里一个媒体路径都不写。与 Pegasus 的内容寻址 `media/` 完全不同。
  证据：单元测试 `媒体按文件名约定铺_条目里一个路径都不写`（照官方那个 `c64/Multidisk/Last Ninja 2` 的例子逐字对）、`两家的媒体布局差得很远`；集成测试 `子库的媒体按_downloaded_media_铺_条目里一个路径都不写`（真的走 `sync::media::lay` + `sync::frontend::lay`）、`同一个变体的第二张同类图被挤掉_而且这件事说得出口`。
  **保留**：这个格式一个变体一个类型只放得下一张图，第二张起被挤掉——那是格式的容量不是缺陷，但已经数进 `Laid::crowded_out` 并在差量预览里说出来，不再静默。

- [x] 能力档位正确反映实测结果

  `Adapter::ceiling` 只声明上限，实测由 `assert_capability` 断言；没过自动降一档并指出第一处分岔在第几行。`romcat adapters` 列得出「ES-Gamelist / 无损往返 / gamelist.xml」，导入报告印的是**实测**那一档（全部文件里最低的那一档），导出那一趟也印。
  证据：命令行测试 `能力档位对用户可见`、`导入别人分享的_gamelist_把用户状态搬运的账说出口`（`--dry-run` 就报出实测档位）。真机 22 份文件实测「无损往返」，与声称的上限一致。

## 挂账裁决

这一票冒出来的挂账：**D139**（分享包与自己写的共用一个源名：优先级同档 + 先后导入互相顶掉）、**D140**（ES 的 system 名取磁盘目录，与 ES-DE 内置短名不一致，用户得自己写一份 `custom_systems/es_systems.xml`）、**D141**（一个 `<game>` 只装得下一个文件，收敛在这个格式里摊了回去：26,938 个条目摊成 46,380 段）。三条都 open。

## 顺手修掉的两处硬伤

都是这一票的路径上真的会丢东西的，不是重构：

- `transfer::landed` 在**还没认出作品**时把标题与其余字段分成两条推给 `put_scraped`，而那是按「锚点+主体+源」整组 `DELETE` 再插入的——第二条当场把标题抹掉。真库 16.3% 的变体还没认出作品，那就是每六条手工维护的标题丢掉一条。
- 导出报告的 `kept_verbatim` 在共用那一层按 `Entry::origin` 数，把摊开的多文件段全算成「没认领」——真库一趟导出是 19,442 段的谎。改成归适配器答（`Adapter::kept_verbatim`），真机复验后是 0。
