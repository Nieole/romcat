# 10 — 卡带内部头解析

**What to build:** 哈希未命中时，从卡带 ROM 的内部头取得发行版级的识别结论。汉化补丁通常不改动这些字段，因此即使一个汉化版对不上任何数据库，工具仍能认出「这是哪个游戏」——缺的只是「谁汉化的第几版」。

同时区分**官中版**与**汉化版**。注意 ADR-0019 定下的世代裂缝：**这票覆盖的全是卡带世代，官中在这里确实是独立发行版**（有独立序列号、DAT 里独立一条），走精确哈希直接过；汉化版是变体，改过字节。数字世代那套（中文是语言属性）不适用于这票。

**Blocked by:** 07

**排序依据的更正**：这票原本写的是「按库体检的文件数排序」。那是错的——**任务重不重取决于要识别多少个变体，不是要遍历多少个文件**。正确的数字由票 05 的成型规则产出，而 05 → 07 → 10 的依赖顺序保证了排到这票时它已经存在。库体检的文件数只能当粗略的上界信号。

**Status:** done

- [x] 解析各卡带平台的内部头字段，字段偏移与长度有据可查
  —— `identify::cart` 解析七种头：**GBA**（`0x0AC` Game Code，GBATEK A.4）、
  **NDS**（`0x00C` Gamecode，logo CRC16 常量 `CF56h` 作 magic，GBATEK A.5）、
  **GB/GBC**（`0x13F` Manufacturer Code，Pan Docs A.3）、**MD**（`0x180` Serial，
  plutiedev A.8）、**N64**（`0x3B` Game Code，n64brew A.7）、**SFC**（扩展头
  `−0x0E` Game Code，bsnes 四点打分 A.2.5）、**FC**（iNES 头，NESdev A.1——
  它**没有编号**，A.18.1 说得明白，所以只读得出字段读不出编号，这一条如实写进了 note）。
  每个偏移在代码里逐条注明出处；`cargo test -p romcat-core --lib identify::cart` 15 条。
  **保留**：SMS/GG、WS、Lynx、NGP、PC Engine 没做（挂账 D113——真机上这几个平台
  合计 3 个变体，PC Engine 压根没有内部头）。
- [x] **排序依据已确定**（票 05 落地后实测，见下）。文件数是错的依据——PSV 有 171,073 个文件却只有 1,416 个变体，收敛 121:1

**卡带平台的开工顺序（2026-09-01 实测变体数，工头独立复核）：**

| 平台 | 变体数 |
|---|---|
| **FC** | **20,516** |
| **SFC** | **5,576** |
| **GB** | **5,463** |
| GBA | 1,657 |

前三个占卡带变体的 **86%**，先做它们。光盘平台（PSP 6,959、PSV 1,416、NGC 699、PS2 629、PS1 622、3DS 588）归票 09，不在这票范围内——**注意 PSP 按变体数是全库第二大平台**，按文件数排时完全看不出来。
- [x] 字节序与拷贝机头部在解析前完成归一化
  —— `cart::normalize` 在任何一个解析器跑之前做完三件事：**N64 的三种字节序**
  （`.z64` / `.v64` 半字交换 / `.n64` 字交换，判据是头四个字节，mupen64plus
  `src/main/rom.c`）、**SFC 的 512 字节拷贝机头**（判据复用票 07 的
  `header::dump_header`，**剥掉**而不是把偏移后推——bsnes 就是先剥再打分，
  后推会让复位向量取址落到文件外面）、**MD `.smd` 的去交错**。
  测试：`n64_三种字节序都归一化到同一个游戏码`（同一份真实 z64 折成三种排法，
  都读出 `NMQE`）、`sfc_带拷贝机头时先剥掉再解析`。
- [x] 内部头命中产出发行版级候选，置信度低于精确哈希但高于文件名
  —— 判据落在 `ident::IdKind::release_level_only`：**卡带游戏码永不自动通过**，
  中置信、进待确认队列（ADR-0008 已加一段修订记下这件事）。「高于文件名」这一头
  同时补齐了：只看名字没看内容的那条候选（`serial::title_id_in_name`）从中置信
  降到**低置信**——那正是 ADR-0002 说的「文件名规则」那一档。
  测试：`内部头这一层只说得到发行版这一层不自动通过`、`四字符游戏码不许撞到别的机器的_dat_上`。
  **真机**：GBA 5.8% → **70.3%**、NDS 4.4% → **47.8%**、GBC 0% → **34.0%**、
  MD 59.5% → **92.5%**、SFC 80.1% → **88.4%**、N64 0% → **14.3%**；
  2,340 个变体是只靠内部头才认出来的。
- [x] 官中版被识别为发行版，汉化版被识别为变体
  —— 测试 `官中版是发行版汉化版是变体`：一份 CRC 精确命中的 `(Zh)` 条目自动通过并
  **立起一条发行版**（`release_id.is_some()`）；一份撞上 GoodNES `[T+Chi]` 的汉化条目
  同样精确命中，但**发行版留空**（`release_id == None`），只挂作品等裁决补。
  这正是 ADR-0012 与 ADR-0019 说的卡带世代那一侧：官中有独立序列号、DAT 里独立一条，
  走精确哈希直接过。**真机**：官中版 215 个、汉化版 1,315 个（票 09 时是 1,064）。
- [x] 内部头与目录声明的平台冲突时记录冲突
  —— 落在中立库 `content_cart` 的 `platform` 与 `family` 两列上，报告一条 SQL 折出来
  （`Catalog::platform_conflicts` / `platform_conflict_count`，报告里单列一节）。
  **判据是头的家族不是那一个平台**：GB 与 GBC 共用一份卡带头，一份 CGB 卡躺在 `gb/`
  目录里不是冲突——按家族判之前真机报 1,722 份，之后 1,352 份 / 1,090 个变体。
  测试：`内部头与目录声明的平台冲突记下来`（目录说 GBA、字节是 NDS）。
- [x] 头部解析器的测试用真实 ROM 的头部字节，不用手工编造的字节
  —— `testing::cart` 里七段字节全部从 `/Volumes/新加卷/Game` 那份真主库逐字节读出来
  （只读，ADR-0004），每一段注明是哪一份文件、编号是什么、在哪个 DAT 里对得上：
  GBA《洛克人EXE6》汉化版 `BR6J`、NDS《逆转检事》汉化版 `C32J`、
  GBC《007 黑日危机》繁体修正版 `BO7E`、MD《光明力量2》简体汉化版 `G-5521 00`
  （海外标题栏已被改成 GBK 中文，产品码没动）、SFC《3x3只眼》汉化版 `A83J`（HiROM）、
  N64《Paper Mario CH》`NMQE`、FC《快杰洋枪2》的 iNES 头。**七份里六份是汉化版**
  ——编造的头会把「真实世界里长得不太一样的那些」全抹平。


## 从挂账转来的前瞻

- **补真正的中文占比统计（原 D8）**：规格里「看到中文资源占比」这条故事在切票时没人认领。票 01 用「文件名含汉字占比」做了粗略代理（实测 15.6%）。这票能区分**官中版**与**汉化版**，是补上发行版级统计的时机。

  **落地了。** 识别报告多出一节「中文（这是识别结论，不是从文件名猜的）」，按平台给出
  官中版 / 汉化版 / 中文占比三列，**并排摆着票 01 那个文件名代理**——两列的差就是这一层
  还没认出来的中文。官中版与汉化版**分开数、绝不加成一个「中文条目数」**（ADR-0012：
  前者是官方发行版、精确哈希直接过，后者是改过字节的变体）。
  数据源是 `Catalog::chinese_by_platform`。

  **真机实测（2026-09-02，46,444 个变体）**：官中版 215 个（0.5%）、汉化版 1,315 个
  （2.8%）；文件名含汉字的 24,213 个（**52.1%**——票 01 那个 15.6% 是按**文件**数的，
  这里按**变体**数，两者不可直接比）。按平台最值得看的几行：
  MD 34.8%、PSV 10.0%（全是官中）、FC 4.9%（官中 20 / 汉化 976）、
  PSP 2.6%、GB 1.3%、SFC 1.0%、GBA 0.7%。

  **这个数还偏低，而且低在哪是说得清的**：只有识别撞出候选、且那条候选的**条目名**上
  带中文记号的才数得进去。GBA 与 NDS 的汉化版在 DAT 里根本没有对应条目（TOSEC 的 GBA
  中文条目仅 13 条、NDS 无 DAT），这一层认出来的是它们**基于哪个原版发行**，
  而「它是中文的」这件事只有裁决说得出——这正是 ADR-0008 说的那条缝。

**三条路各贡献了多少**（同一趟）：

- **卡带内部头**：探 11,919 份内容、读出游戏码 4,094 份、撞出 5,252 条候选，
  **2,340 个变体只靠它才认出来**。
- **SHA-1 那条窄路**：撞出 2,754 条候选，**2,646 个变体只靠它才认出来**（全是 FC 与 MD）。
- **DAT 那一头的丝印编号折平**（`dat::serial::game_code_in`）：MAME 的卡带 software list
  记的是卡上丝印的 `AGB-BR6J-JPN`，而卡带头里只有中间那四个字。不拆，MAME 那几份一条
  都撞不上。拆完序列号弹药：GBA 6,234 → **8,457**、GBC 1,713 → **3,147**、
  SFC 2,364 → **3,224**、N64 2,023 → **2,876**、GB 2,161 → **2,699**。
  （`dat::repo::SCHEMA_VERSION` 因此从 2 升到 3，逼出那一趟重新解析。）

**SHA-1 那条路划不划算：划算。** 2,646 个变体（占这一趟新增命中的 53%）靠它才认出来，
FC 因此从 82.8% 到 95.6%。代价是 FC 与 MD 那 2.76 GiB 内容整份读一遍，而且大部分是
**白拿的**——那批内容本来就要为「去头哈希」读一趟，SHA-1 只是挂在同一趟上
（`fingerprint::Sha1::Free`）；真正多花的只有第一命中层落空之后那一档
（`Sha1::Pay`，闸设在 64 MiB，把光盘镜像整批挡在外面，挂账 D118）。
算过的存进 `content_hash.sha1`，第二趟是零。

**增量兑现**：第二趟识别 **27.0 秒、回盘读 0 B**（第一趟 736.9 秒、493 MiB；
那一趟还带着「`content_cart` 从零重建」的代价）。

**门禁**：`cargo fmt --all`、`cargo clippy --workspace --all-targets`、
`cargo test --workspace`（31 个测试目标全绿，其中 `identify::cart` 15 条单元测试、
`tests/cart_header.rs` 8 条集成测试）。

**挂账**：D113–D118（见 `deferred.md`），另在 D98 上补了一条票 10 的注记。
