# 13 — 刮削器离线档与媒体池

**What to build:** 在**识别**结论的基础上取得元数据与媒体。离线策略档案只用本地数据完成，全库刮削不消耗任何在线配额。所有媒体按内容哈希进入**媒体池**，文件名不再是媒体的主键——因为各前端的媒体匹配键在文件名、标题、标签之间横跳，且净化函数多对一不可逆。

多个数据源按字段级优先级合并，结果持久化缓存。

**Blocked by:** 07

**Status:** done

- [x] 离线档只用本地数据源，运行时不发起任何网络请求
      —— 七个源全部自报 `Locality::Local`（`scrape::Locality`），**档案是一道运行时闸门**
      而不是注释：`scrape::offline_sources` 逐个查 `Profile::accepts`，自报「要联网」的源
      当场被拒（同 `dat::guard` 的套路）。`scrape::run` 的参数表里根本没有网络句柄——
      它拿到的是主库的只读视图、中立库、优先级表。测试
      `离线档只用本地数据源`、`离线档不收联网源`、`离线档那七个源全是本地的`。
      真机：全库刮一遍 2.3 秒，零请求。

- [x] 多个数据源按字段级优先级合并，优先级可配置
      —— `scrape::priority::Priorities`：内置一份 `priorities.toml`（**数据不是代码**，
      同 `platforms.toml` / `sources.toml`），`--priorities` 整份换掉，
      `--dump-priorities` 导底稿，工作目录里的 `priorities.toml` 自动生效。
      三条规则各有测试：人工来源（`裁决`）永远排第一、按平台可覆写、没列到的源按
      时间戳兜底。**合并在产品里真的跑了一遍**：报告的「合并之后谁说了算」那一节
      逐个锚点合并再数出来（`report::winners`）。
      真机证据（`docs/library-facts.md`）：标题上 No-Intro 胜出 6,945、TOSEC 胜出 1,869
      （No-Intro 沉默时它接上）；**年份与发行商只有 TOSEC 给得出，共 12,500 条**——
      按源排的话，「No-Intro 优先」等于把它们一起丢掉。
      测试 `字段级优先级用一个源的标题配另一个源的年份`、`报告把合并真的跑了一遍`。

- [x] 刮削结果持久化缓存，重跑不重新计算
      —— `scrape_probe` 记每个「锚点 × 源」的**输入指纹**，一样就整条跳过，
      **「查过、没有」也记着**（调研 13.3(4)）。算过的媒体哈希落在 `media_blob`，
      由扫描按文件的三元组作废（与 `content_hash` 同一条路，挂账 D14）。
      真机：首趟 2.3 秒 → 第二趟 **0.8 秒**，119,322 个「锚点 × 源」整条跳过；
      `--refresh` 全部重采 **4.1 秒、回盘 0 字节**。
      测试 `重跑不重新计算`、`refresh_把结论重采一遍但池里的文件一个都不删`。
      **指纹盖住全部会改变结果的输入**，包括 `--max-media-mib`——实测把上限从 32 提到 64，
      53 份媒体真的进来了（测试 `调高媒体上限之后那些媒体真的会被收进来`）。

- [x] 媒体按内容哈希存入媒体池，中立库只记录映射
      —— `scrape::pool::MediaPool` 是内容寻址存储，落点 `<池>/<哈希前两位>/<哈希>.<扩展名>`，
      哈希是 **SHA-256**（CRC-32 是校验不是指纹，32 位在几万份媒体上撞一次就是一张封面
      悄悄变成另一张）。池在**本机**的工作目录下（`workspace::media_pool_dir`，ADR-0009），
      不跟着盘走、也不带 `Slug`——同一张封面在两块盘上算出来是同一个哈希。
      中立库只有 `media`（哈希 → 扩展名、字节数）与 `media_ref`（锚点 → 哈希）两张表，
      **文件名一个字都没进主键**。
      真机：池里 516 份 / 1.60 GiB（上限 32 MiB 那一趟），引用 538 条。
      测试 `媒体按内容哈希入池且同一份只存一份`（断言哈希是 64 位十六进制、池里那个文件
      真的在）。

- [x] 同一份媒体被多个条目引用时只存一份
      —— 内容寻址天然给的，不是另加的去重步骤：两个锚点引用同一串字节，算出来是同一个
      哈希，落在同一个文件上。`MediaPool::adopt` 发现目标已存在就删掉临时文件。
      真机：**538 条引用落在 516 份内容上**，23 次「算出来发现池里已经有了」，
      **18 份被不止一个锚点引用**。
      测试 `媒体按内容哈希入池且同一份只存一份` 断言 `blobs=2 / refs=3 / shared=1`，
      并断言两个变体旁边那两份同内容不同位置的封面拿到同一个哈希。

- [x] 识别与刮削是两个可分别重跑的阶段
      —— `romcat scrape` 是独立子命令，**连 DAT 库都不打开**（要的东西识别已经抄进
      中立库的候选里）；它从不重新判断「这是哪个游戏」。反过来，重跑识别会把它自己造的
      作品与发行版整批删掉重建、行号全变，而刮削结论挂在**自然键**上（作品名 / 变体的键），
      因此活得下来。
      测试 `识别重跑之后刮削结论还在`（重跑识别后逐条比对刮削结论一字不差，
      再刮一遍回盘 0 字节）。**保留**：一个源不再说话时它上一轮的结论会被清掉
      （测试 `一个源不再说话时它上一轮的结论被清掉`）——这是对的；但**锚点自己消失时
      留下的孤儿行还没人收**（`vacuum` / `validate` 那一档），挂在 **D52**。

## code-review 处置

两轴各跑一遍（fixed point `ebd7145`）。

**采纳并改掉：**

1. `pool::ingest` 的 `# Errors` 引用了不存在的 `Ingested::Skipped`——而且那句话把代码
   刻意分开的三态又说回成一态。改成点名三个「没收」变体。
2. `extension_of` 在 `local.rs` 与 `pool.rs` 里逐字重复，十六进制编码写了两遍，
   `rounds` / `squares` 是同一个形状换了分隔符——三处各自合成一份。
3. 零使用的公开面：`Anchor`、`pub use MediaPool as Pool`、`Field::from_label`、
   `dat::chinese_mark`，以及 `DatEntry` 上没人读的 `dat` / `chinese` 两列
   （真库里那是 150,959 行各多背两串字符串）。全删。
4. `Vec<(Field, String, String)>` 这类三元组：第三位是词表一等术语**依据**。
   立 `Finding` / `HarvestedValue` / `HarvestedMedia` 三个有名字的类型。
5. `Run.not_media` 只加不读，而紧邻的注释正说「三种跳过分开数」——进 `Outcome`，
   命令行只在非零时报（非零就说明两处的扩展名表对不上了）。
6. **同源多条目名静默塌陷**：一个源对同一个字段 push 多条，库里主键只留一条，
   而采集记录记着「采到 N 条」，数对不上还查不出为什么。改成 `Harvest::value`
   **第一个胜出**并写明理由（一个字段装多个值是**标题集合**的形状，那是票 15）。
7. 错误层重叠：`ScrapeError` 有 `Catalog` / `Pool` / `Ingest(IngestError)`，
   而 `IngestError` 本身就是 `{Catalog, Pool}`——删掉 `IngestError`。
8. **`--max-media-bytes` 没进输入指纹**（spec 轴，实测确认）：调高上限重跑，缓存会
   一口咬定「输入没变」而整条跳过，真库上那是 108 份永远收不进来的媒体。
   上限进 `Subject::media_limit` 并折进本地媒体源的指纹；实测从 32 提到 64 MiB
   收进 53 份。加回归测试。
9. 上限的判断挪到「复用」**之前**，并在条目大小读不到时用算过的那一份兜底——
   调低上限时，此前收进来的那一份也该被挡在外面。
10. 报告的「锚点」列此前是各源的 `max()`，是个下界却印得像真值——改成
    `field_subjects()` 精确查一次（46,444 → 55,670，此前少算了作品那一层）。
11. **合并在产品里没有消费者**（spec 轴）：`Priorities::merge` 只被测试调用。
    报告新增「合并之后谁说了算」一节，逐个锚点真的合并一遍再数出来。
12. 优先级表里点名了、而这一档没有的源**静默排到链尾**——报告新增一节点名
    （`Priorities::sources_not_in`）。
13. 词表从轻项：用户可见文案里的「缓存」一律改成「采集缓存 / 采集记录」，
    「去重」改成「只存一份」——那两个词分别是**中立库**与**重复拷贝**的 `_Avoid_` 词。

**另外自己发现并改掉的两处**（不在两份报告里）：

14. **一个源不再说话时，它上一轮的结论没人清**。重跑识别把某个源的候选清空之后，
    上一轮挂上去的年份与发行商还留在库里，带着一条指向已经不存在的条目的**依据**。
    加 `Catalog::forget_scraped`，只清那个源的行。
15. 而这个修法带出一个更坏的后果：`--no-media` 会让本地媒体源「无话可说」，于是把
    此前收好的媒体映射**悄悄删掉**。改成 `--no-media` 时**本地媒体源整个不参加**
    ——「这趟不收媒体」不是「把收过的扔了」。两条都有测试。

**驳回：**

- **「`media_ref.hash REFERENCES media(hash)` 是装饰，没有 `PRAGMA foreign_keys`」**
  —— 事实不成立。`rusqlite` 的 bundled SQLite 编译时开了
  `SQLITE_DEFAULT_FOREIGN_KEYS=1`，实测 `PRAGMA foreign_keys` 返回 1
  （票 07 正因为外键是开着的才要在 `variant` 上补两条索引）。已加测试
  `引用一份池里没有的媒体会被外键挡下` 把这个前提钉住。

- **「`report.rs` 303 行、`开发商`/`类型`/`简介` 三个字段、`--max-media-mib`、
  `MediaKind` 的关键词分类都是范围外」** —— 驳回四项：报告是这个代码库里每个阶段
  交付结论的固定形状（库体检 / 命中率 / DAT 报告都是从中立库折出来的一份报告）；
  那三个字段正是报告答得出「离线档补不上什么」的凭据，藏起来等于假装缺口不存在，
  而它们是票 14 存在的理由；真库上归得上的媒体是 **10.04 GiB**，没有上限这个开关，
  第一次跑就会往本机灌满十个 G；媒体类型是 ADR-0009 说的「各前端的媒体目录按类型铺设」
  的前提，票 20 铺媒体时按的就是它。

- **「`gameId`（跨源合并的锚点）缺席」** —— 调研 13.3(2) 的第三个 ID 是给**在线源**用的
  （ScreenScraper 的 `jeu.id`、IGDB slug、Wikidata QID），离线源一个都没有这种东西。
  它是票 14 的活。已按 D53 记着锚点的取法。

- **「改一个源的解析逻辑不会触发重采」** —— 属实，但不改：把代码版本折进指纹要靠人手动
  改一个常量，忘了改就是同样的静默失效，而 `--refresh` 已经是这件事的出口，
  且实测只要 4.1 秒、回盘 0 字节。已写进 `Source::probe` 的文档。
- **D53 作品锚点是作品名** — 维持。与识别现在的行为一致，不会多错一分。识别哪天改成「同名不同平台是两部作品」，锚点跟着改并重采一次。
