# 04 — 透明容器：rar 头部自实现解析与分卷

**What to build:** 工具同样能不解压读出 rar 内部文件的校验和、大小与文件名，并把分卷压缩的多个分卷视为一个透明容器而不是一堆孤立碎片。

头部解析自己实现，不引入内嵌 UnRAR 源码的第三方库——那份许可会传染，且在部分发行版中被归为非自由软件。工具只需要读头，不需要解压，因此完全可以绕开。

**Blocked by:** 03

**Status:** done

- [x] 自行实现 RAR4 与 RAR5 的头部解析，不依赖内嵌 UnRAR 源码的库
  - `container::rar`（约 1,000 行）：RAR4 走定长字段（`SIZEOF_FILEHEAD3 = 32` 从块首算起），RAR5 走变长整数（**没有固定偏移只有固定顺序**）。`Cargo.toml` 一行没动，**没有新依赖**。
  - RAR4 的文件名还要解 unrar 私有的 Unicode 编码段（`encname.cpp` 的 `DecodeFileName`，两位一个操作码）。少了它，`17.FC天使之翼2修复巴西的荣耀Ver2.1回段BUG.tsh` 只会解成一串 GBK 乱码——而**文件名那一层（票 11）要拿它去撞中文数据源**。
  - 单元测试 `变长整数按小端每字节七位读`、`私有_unicode_名字解得出中文`；集成测试 `crates/core/tests/rar.rs` **17 条**。
  - 真机 1/7 抽样 191 份：**RAR5 139 份、RAR4 52 份**——两种都得认。

- [x] 不解压即可读出内部文件的校验和、未压缩大小与文件名
  - **真机全量 1,333 个 rar：穿透 1,332 个（99.9%）、195 秒、504 GiB 一个字节都没解**。读出内部文件 **203,586 个**（另有 8,115 条目录条目）、未压缩 **562.55 GiB**，其中**带 CRC-32 的 174,785 个（85.9%）**，名字有损 **0 条**。
  - **与官方 `unrar lt` 逐条对照：随机 150 份、16,809 条内部条目，一致 150 / 不一致 0**（名字、未压缩大小、CRC-32、是不是目录四样全比）。
  - 反向也验了：把 `testing::container` 里手写的 RAR4 / RAR5 样本喂给官方 `unrar lt`，它读得出名字、大小与 CRC-32——**那些样本是真 rar，不是「只够骗过自己解析器」的字节**。
  - 唯一穿不透的那一个（`[SJ9E41]舞力全开2…-DL.rar`，1.55 GiB）`unrar` 自己也报 *Corrupt header is found*；报告里它落在「结构读不下去」，理由带上「偏移多少、已经读到几条」。

- [x] RAR5 分卷时，非末段记录的是打包后数据的校验和——必须识别这种情况并拒绝用它比对 DAT
  - `rar::absorb`：**只在见到末段（`SPLIT_AFTER` 未置位）时才把 CRC 记下来**，见不到就是 `None`。跨卷的几段按名字合并成一个条目。
  - 实测造一份三卷 RAR5：同一个 `src/b.bin` 三卷分别记 `DDFAE192` / `B31EA58F` / `9506C014`，只有末段那个等于未分卷时的 CRC；`unrar lt` 把前两个直接印成 **`Pack-CRC32`**。测试 `分卷非末段的校验和是打包后数据的_不许拿去撞_dat`。
  - **真机多出一处同类的坑，票据与调研都没写**：带密码时校验和被密钥搅过（technote 的 *tweaked checksums*，`unrar lt` 印成 **`CRC32 MAC`**）。**随机 60 份里有 20 份带密码**——三分之一。实测 `rar a -p123`：`a.txt` 真 CRC `A3EBCC66`，头里写的是 `D4ED1D67`。同样丢掉，测试 `带密码时被搅过的校验和一律丢掉`。

- [x] RAR5 仅提供 BLAKE2sp 而无 CRC-32 时，该容器被标记为需要完整解压才能识别
  - 逐条那一级：file flag 的 `0x0004` 位为 0 时 `crc32 = None`（哈希在 extra area 的 `0x02` 记录里，32 字节 BLAKE2sp，而 No-Intro / Redump / TOSEC 一条 BLAKE2 都不记）。
  - 容器那一级：`Contents::needs_full_decompress()`——有内容的条目一条 CRC-32 都没有。**判据只用两个数**（内部文件数、其中没有 CRC 的个数），库体检那一侧从 `container` 表的 `files` 与 `no_crc` 照同一条式子再算一遍，两处口径一模一样（code-review 采纳）。
  - 报告新增一行「要完整解压 N 个容器有内容却一条 CRC-32 都没有」，与 zst 同一档处置。测试 `只写_blake2sp_的容器被标记为要完整解压`。
  - **真机 546 个**——不是 BLAKE2sp 那一批（真库里 0 个），全是上一条那批带密码的。

- [x] 正确区分三种分卷形态：RAR 分卷、7-Zip 的通用字节切分、以及 ZIP 官方 split
  - `container::volume`（435 行，8 条单元测试）：判据只看名字、是纯函数，归类 / 成型 / 穿透三处共用同一份，**抄成三份的话「哪些名字算一段」迟早漂成三个答案**。
  - 三种的入口段不在同一头：RAR 与字节切分在最前，**ZIP split 的入口是最后那个 `.zip`**（APPNOTE §8.3.4：末段用 `.zip` 扩展名正是为了让中央目录一次读到）。测试 `三种分卷形态是三样不同的东西`、`三种形态的入口不是同一段`、`zip_官方_split_的主文件是最后那个_zip`。
  - 下一卷的名字按 unrar `NextVolumeName()` 的两套算法算（新式 `.part9.rar` → `.part10.rar` 保位进位；旧式 `.rar` → `.r00` → `.r01`），编号方式由**主头部的旗标**给出而不是猜。
  - 真库里：RAR 分卷 **0 组**；字节切分 **1 组且缺入口卷**（只有 `废都物语_资料合辑_220928.7z.006`）；ZIP split **4 组**（WIIU `XenobladeX-…-WUP.z01…z04 + .zip`，每组约 20 GiB）。
  - **保留**：字节切分那一种**认得出但还读不了**——跨文件的拼接读取器没做，挂在 **D136**（真库 0 组完整的，为 0 个样本改两个模块的接缝是负收益）。

- [x] 分卷的多个文件在体检报告与后续成型中被视为一个容器
  - **报告**：`ContainerKind::for_path` 对**非入口段**返回 `None`，于是数容器、扫描、识别、格式转换四处自动一致——一组分卷只按入口段数一个。「疑似分卷」那一行也只数非入口段（`.7z.001` 与 `.part1.rar` 是入口，不算「多出来的一段」）。
  - **成型**：新规则 `分卷压缩`（`shape::find_volume_groups`）——一组分卷一个**变体**，主文件是入口卷，其余是附属文件。测试 `一组分卷是一个变体而不是一堆孤立碎片`、`zip_官方_split_的主文件是最后那个_zip`、`字节切分的一组也是一个变体`、`同目录里两组分卷不会串到一起`、`一个普通的容器不会被当成一组分卷`、`缺入口卷时那一组也不散成碎片`。
  - **识别**：非入口段当附属文件时一声不吭地跳过（入口段已经把整组交出来了）；当主文件时说「分卷的一段，而这一组的入口卷（…）不在这个变体里」——真库那个孤零零的 `.7z.006` 正是这一句。
  - **穿透**：RAR 分卷走 `volume::next_volume_path` 一卷一卷走下去，跨卷的条目合并成一个；缺一卷时整组报 `FailureReason::MissingVolume`（**新的一类**，与「结构读不下去」分开——下一步是去找那一卷）。测试 `分卷的多个分卷是一个容器而不是一堆孤立碎片`、`缺一卷时不交半张清单`、`旧式分卷从那个普通的_rar_走到_r00`、`跨卷的原样存放条目接起来就是原文`。

那 680 个 rar 变体此前**连撞都没撞过**（无判据不进命中率的分母，ADR-0002）。
现在它们真的撞了一次 DAT：**210 个撞上了**（自动通过的候选 **+36,998 条**，
基本全部来自 rar），其余的撞不上——rar 里装的多是汉化版与 HACK 版，
**DAT 里本来就没有**。撞不上的那批从「无判据」落进「未命中」，分母变大、
分子没同比例变大，百分比就掉了。

按 ADR-0002 的分档，这正是要的方向：**未命中是一条结论，无判据不是**。
掉的这 1.4 个点，换来的是 680 个变体第一次有了可复核的依据。

**这一趟真机读盘 0 字节**（`identification.read_bytes` 对 rar 变体求和 = 0）——
203,586 个内部文件的名字、大小与 CRC-32 全部来自头部，504 GiB 一个字节都没解。

### 三处「字段还在、含义变了」的坑，两处是票据写的，一处是真机撞出来的

票据点名的两处（分卷非末段的 CRC 是打包后数据的、只写 BLAKE2sp 时没有 CRC-32）
都按票据落地了。**真机上真正咬人的是第三处：带密码时校验和被密钥搅过**
（technote 的 *tweaked checksums*，`unrar lt` 印成 `CRC32 MAC`）——
**随机 60 份 rar 里 20 份带密码**，全库 546 个容器落在这一档，
225 个变体因此停在「容器没记这一条的 CRC-32」。不丢掉它，这一批会拿着一串
谁也对不上的数去撞 DAT，然后被记成「未命中」——**一声不响地把命中率压低**，
正是票据第 3 条要防的那类事，只是换了个入口。

真库里 BLAKE2sp 那一档实际是 **0 个**（没人用 `-htb` 打包）；票据要的标记照样做了，
判据与代码都在，只是这块盘上还没有样本。

### 偏离票据的两处

**一、给 rar 加了「一律转不了」的显式拒绝（`capability.rs`）。** 票据没要。
但 rar 进了容器表之后，**差量预览**会以为它转得了——而解压那条路要 UnRAR 的算法，
真跑到同步那一步才失败。差量预览是同步的前置条件（CONTEXT 的「差量预览」条），
它说会转的就得真能转，于是在那一层就说清做不到。

**二、`.z01` 那 16 段的报告口径变了。** 「疑似分卷」从 22 变成 **20 段**，
因为入口段（`.7z.001`、`.part1.rar`）自己就是那个容器，不算「多出来的一段」——
数它会把一组数两次。fixture 的断言同步从 2 改成 1。

### 挂在账上的三条

**D135** 缺一卷时是整组报「缺分卷」还是交一张半截清单（真库 RAR 分卷 0 组，走不到）；
**D136** 字节切分（`.7z.001`）的拼接读取器没做，认得出读不了（真库 0 组完整的）；
**D137** rar 里压缩过的条目取不出字节（真机 85.9% 的内部文件带 CRC-32，
第一命中层本来就吃得下）；**D138** 「要完整解压」的 546 个容器只报了总数没有名单。

### ZIP 官方 split 早就穿得透，票 04 补的是另一半

真库那 4 组 WIIU `XenobladeX-…-WUP.z01…z04 + .zip`（每组约 20 GiB）**一直读得出内部
构成**——中央目录写在末段那个 `.zip` 里（APPNOTE §8.3.4）。票 04 补的是：
`.z01`…`.z04` 不再各自算一个容器、各报一次「穿不透」，而是与末段那个 `.zip`
合成**一个变体**（成型规则「分卷压缩」，真机 **4 组**）。顺带修掉一个真伤：
`zip.rs` 从前把中央目录里的 `disk number start` **读了就扔**，于是取一条落在
`.z01` 上的字节时会拿着别段的偏移在 `.zip` 里乱找，报成「local header 签名对不上」
——一个把人引向错处的理由。现在如实说「数据在第 N 段上」。
