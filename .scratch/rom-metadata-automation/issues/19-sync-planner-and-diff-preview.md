# 19 — 同步计划器与差量预览

**What to build:** 一个纯函数：输入选择集、上次导出的**清单**、目标设备的实际状态，输出操作计划——也就是**差量预览**。产品要求的预览和这个函数的返回值是同一个东西，不是两套需要保持同步的东西。

它也是唯一能守住那条硬约束的地方：**只碰清单里记录过的、工具自己导出的文件**。维护者手动拷进 SD 卡的内容、模拟器存档、金手指、截图——清单之外的一切对工具不存在。

**Blocked by:** 18

**Status:** done

- [x] 计划器是纯函数，不进行任何文件系统写入
  - `sync::plan()`（`crates/core/src/sync.rs`）只吃 `Sublibrary` / `Desired` /
    `Manifest` / `TargetState` 四份**纯数据**，不碰磁盘、不碰中立库、不看时钟。
    折库的 `sync::desired()` 与看目标的 `sync::observe()` 在缝的两边，与票 18 的
    `sublibrary::select()` / `facts()` 是同一道缝。
  - `观测`走 `fs::LibraryFs`——那个 trait **根本没有写的办法**（ADR-0004 的做法），
    于是「排计划这一路写不出去」是类型保证的。
  - `crates/core/src/sync.rs::同一份输入排两次得到同一份计划`（纯性的可观测形式）、
    `crates/cli/tests/sync.rs::差量预览出得来_而且一个文件都没写` 与
    `手动拷进目标的东西一条都不出现在计划里`（**数目标目录下的文件，跑完前后一个不多**）。
- [x] 差量预览给出将新增几个占多少容量、删除几个腾出多少容量、净变化多少
  - `Plan` 上就是这几个字段：`adds` / `updates` + `updates_before` / `deletes` /
    `keeps`（各带**文件数、变体数、字节**）、`net_bytes`、`desired_bytes`。
    **`--json` 打出来的就是 `Plan` 自己**——预览与计划是同一个值，不是两套要保持
    同步的东西（`sync::report` 的模块文档说明了为什么这里刻意没有第二个报告类型）。
  - `crates/core/src/sync.rs::差量预览给出新增删除与净变化`、`净变化在删得比加得多时是负的`、
    `主库那份变了就更新_净变化只算差额`、`一个变体的几个文件折回一个变体数`。
  - **真机**（见下）：新增 922 个 508.01 MiB、删除 0、净 +508.01 MiB。
- [x] 计划中的删除项只可能来自清单，清单之外的文件永不出现在删除列表中
  - 构造上成立：`Act::Delete` 与 `Act::Update` 两类步骤**只从遍历
    `Manifest::files` 的那个循环里长出来**，实际状态那一侧只用来核对。
  - `crates/core/tests/sync.rs::计划里的删除项只可能来自清单_清单之外的文件永不出现在删除列表中`
    ——穷举 2×2×4 = 16 种「期望 / 清单 / 实际」组合外加三个手动拷进去的文件，
    对 `--restore` 开关的两种取值各断言一遍。
  - 落点被清单之外的文件占着时**也不覆盖**（`落点被清单之外的文件占着就不覆盖`），
    而且它**照样算进「清单之外」那一栏**（`落点被占的文件也算清单之外`）——
    ADR-0015 的原话是「清单之外的一切文件对工具不存在」，漏数哪一个，报告都可能
    说出「目标上没有清单之外的文件」而卡上明明有。
- [x] 目标上的意外变化（清单说有、实际没了）被报告而非静默补回
  - 四种意外各成一类：`没了` / `被改过` / `落点被占` / `读不到`（ADR-0021 的第三态），
    **一律报告 + 本次不动**，并带一位 `still_wanted`（选择集还要不要它）——
    用户的处置办法完全不同。
  - 默认**不补回**；`--restore` 明说才补，而且补回的那几条照样进意外那一栏——
    **明知故犯不是静默**。挂账 **D75** 记着这个选择，以及留给票 20 的那个褶子。
  - `crates/core/tests/sync.rs::目标上的意外变化被报告而不是静默补回`、
    `每一种组合的结论都是说好的那一个`（整张判定表逐格对）。
  - 卡不在位**直接失败**而不是当成「空目标」：不然计划会变成「清单里每一条都没了、
    期望里每一条都要重传」（`卡不在位时停住_而不是排出一份全删全传的计划`、
    `crates/cli/tests/sync.rs::目标不在位时停住并说清怎么办`）。
- [x] 选择集超出目标容量时给出超出量与按体积排序的裁剪建议，不自动截断
  - 超没超与砍谁**与票 18 的选择集报告共用一套算法**（`sublibrary::over_capacity` /
    `trim_suggestions` / `Trim`）：两处各写一遍，「这份说装得下、那份说砍这几个」
    这种对不上的账迟早会出现。建议**落在变体这一层**，因为例外记的是变体的键。
  - `Trim` 带**累计**一列——「砍到第几个才够」直接读得出来；十个不够时报告直接说
    「全砍掉也只腾出 X，还差 Y」。
  - 比的是 `目标现占 + 净变化` 而不是子库该有多大：卡上的地方是共用的，手动拷进去的
    存档、落点被占传不上去的、被改过因而不删的全都还占着位置（挂账 **D76**）。
  - `crates/core/src/sync.rs::超容量报出超出量与按体积排序的裁剪建议_不自动截断`
    （三个全在计划里，一个都没砍）、`容量账比的是目标现占加净变化`、
    `删得比加得多时同步之后占得更少`、
    `crates/core/tests/sync.rs::超出目标容量时给出超出量与裁剪建议_一个都不砍`。
- [x] 有测试构造各种状态组合，断言「只碰清单内文件」这条性质
  - 同上第三条：`全部组合()` 穷举出 19 条路径（16 种组合 + 存档 / 金手指 / 截图），
    一次排出计划后逐条断言四件事：删与改的路径必在清单里、新增的路径必在期望里、
    新增的落点上必须**本来什么都没有**、那三个手动拷进去的一条步骤都没有。
  - `每一种组合的结论都是说好的那一个` 把判定表整张写成断言——不只是「没碰错」，
    而是「每一格该是什么就是什么」。

## 真机（`/Volumes/新加卷/Game`，8.60 TiB / 46,444 个变体）

拿票 18 那条规则（`平台=FC,SFC,GB,GBC,GBA,MD 且 中文=汉化`）排一次计划。
**目标设备用本地目录模拟，真实的卡一张都没碰**；中立库也是拷到临时目录的一份副本。

**头一次同步**（清单为空）：

```
新增        922 个文件 / 922 个变体   508.01 MiB
更新        0 个文件 / 0 个变体       0 B
删除        0 个文件 / 0 个变体       0 B
保持        0 个文件 / 0 个变体       0 B
净变化      +508.01 MiB
子库共      508.01 MiB  （922 个文件 / 922 个变体）
```

排计划 **1.2 秒**，**一个文件都没写**。**期望总量与票 18 报出的选中容量是同一个数**。

**增量**（摆一份 860 条的清单与一张摆好五种状态的卡）：保持 800 个 207.34 MiB、
删除 30 个腾出 120.00 MiB、新增 87 个 220.72 MiB、净变化 **+100.72 MiB**；
意外「没了」20 个、「被改过」10 个、「落点被占」5 个，**本次一律不动**
（`--restore` 之后新增变 107 个）；清单之外 8 个 96.40 KiB（3 个手动拷进去的
加上那 5 个占着落点的），**一条步骤都没有**。

**装得下吗**：目标现占 398.53 MiB → 同步之后 499.25 MiB。上限压到 256 MiB 时报出
「超出 243.25 MiB」与带累计列的裁剪建议，并直说「这几个全砍掉也只腾出 232.56 MiB，
还差 10.70 MiB」，**922 个一个没砍**。

细节见 `docs/library-facts.md` 的「差量预览」一节。

## 顺手补上的一个洞

判「主库那份变了没有」原先只比大小，于是**原地改过、大小没变**的文件会被静默判成
不用重传（汉化补丁打完重压一次，大小撞上是常事）。清单因此多记两列
`source_bytes` / `source_mtime_ns`：判据改成**源的键加源的戳**，与增量扫描比的是同一个
三元组，也与那句「证明不了没变，就不能说没变」同一条纪律。顺带把票 21 的一个坑填了
——转完格式之后目标上那份的大小与主库侧那份根本对不上，比目标戳会让整张卡每趟重刷。
单元测试 `主库那份原地改过_大小没变照样要重传`、`目标上占多少与主库那份变没变是两回事`。

## 不做的三件事（留给票 20 / 21）

- **执行**：搬文件、铺媒体、写元数据、同步完更新清单——票 20。`Step` 上带着
  `source_stamp`，于是计划**自己就够执行**，不必回头再查一遍期望状态。
- **媒体与元数据**：`FileKind` 三类从第一天就立着（清单是持久数据），但眼下
  `desired()` 只产得出 `ROM`。票 20 往 `desired()` 里补另外两类，**计划器一个字不用改**。
- **格式转换与文件系统约束**：票 21。能力档案要在预览阶段报出 FAT32 的 4 GiB 单文件
  上限与路径长度限制——那要接在 `desired()` 上（挂账 D79 记着路径布局那一条）。

## code-review 的处置

**Standards 轴 4 条采纳、1 条驳回；Spec 轴 3 条采纳、3 条驳回。**

采纳的：① 注释里用了词表 `_Avoid_` 的「导出目录」，改成「子库根」；
② `--target` 把系统给的原始路径折成 NFC 之后又拿去读盘，违反 ADR-0020
「读盘用原始形式、入库比较才用 NFC」——改成读盘走原始 `PathBuf`，NFC 那份只进报告；
存进库的那一份留给票 20（挂账 **D82**）；③ `MemberFile::role` 读出来没人用
（Speculative Generality），连同它那句 `unwrap_or(Role::Internal)` 的猜测一起删掉；
④ 容量与裁剪建议的算法与票 18 的报告重复（Duplicated Code），提到
`sublibrary::over_capacity` / `trim_suggestions` / `Trim` 共用，顺手把票 18 那侧的
`Vec<(String, u64)>`（Primitive Obsession）也换成 `Trim`；⑤ `same_content` 名不副实
（比的是源的戳不是内容），改名 `source_unchanged`；⑥ 裁剪建议硬截到十条却不给累计量，
加 `Trim::cumulative` 与「还差多少」那句；⑦ 落点被占的文件没算进「清单之外」，
报告可能说出「目标上没有清单之外的文件」而卡上明明有——改成按字面数；
⑧ 容量账口径与它自己的理由不自洽，改成 `目标现占 + 净变化`；
⑨ `六个子命令共用` 的注释过时。

驳回的：
- **把 `dat::sync` 改名成 `dat::refresh` 以让出「同步」这个词**——`romcat dat sync`
  是用户已经在用的命令名，改名要动一张已经 done 的票和一个公开的命令名，收益只是
  省掉一行 `as dat_sync`。挂账 **D83**。
- **`--restore` 是票据没要的**——它**不写任何文件**，只是让「补回」变成一次明说的动作。
  ADR-0015 说的是「不**静默**补回」，不是「永远不补回」；没有它，意外删掉的东西
  除了清空清单再没有别的办法拿回来。挂账 D75 记着这个选择。
- **`Catalog::put_manifest` 是票 20 的活**——清单表是这一票立起来的持久结构，
  读写一起立才测得出往返（`手动拷进目标的存档在整条链路上绝对安全` 里存进去读回来比过
  一次）。只立读的一半，等于让票 20 去改一张已经在被读的表。
- **`FileKind::Media` / `Metadata` 眼下产不出**——同上，清单是持久数据；
  Standards 轴那位也说「carry an argued persistence rationale — leave them」。

## 挂账裁决

这一票新记的：**D75**（意外消失默认不补回）、**D76**（容量账把清单之外的占用也算进去）、
**D77**（清单落在中立库不落在卡上）、**D78**（被改过的既不覆盖也不删、没有 `--force`）、
**D79**（子库内的布局照搬主库的相对路径）、**D80**（期望状态带上变体的全部成员）、
**D81**（一致性判据是大小加修改时间，不是内容哈希）；code-review 之后又加了
**D82**（子库的目标路径存 NFC 却也拿来读盘，**票 20 动手写目标之前必须先定**）与
**D83**（`sync` 与 `dat::sync` 重名）。

## Comments

它由票 20 的执行写、票 19 的计划器只读；票 19 这边提供 `Catalog::manifest` /
