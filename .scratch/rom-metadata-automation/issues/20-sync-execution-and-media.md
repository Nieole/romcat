# 20 — 同步执行与媒体导出

**What to build:** 把计划真正落到目标设备上。媒体从**媒体池**铺到目标：同卷且支持硬链接就链接，不支持就自动降级为复制——SD 卡通常是不支持链接的文件系统，这条降级路径是必需项而非优化。

子库内的路径一律相对于子库根目录，卡插到不同设备、盘符变化都不受影响。

**Status:** done

- [x] 执行严格按计划进行，不做计划之外的任何写入

  `sync::execute::run` 只遍历 `Plan::steps`，不重新看一眼目标、不自己发明任何一次写入；而删除与更新**只可能从清单里长出来**（票 19 的 `plan`），于是这条是**继承来的构造性质**，不是重新守一遍。测试 `执行只走计划里的那几步_清单之外的东西连时间戳都没动`（`crates/core/tests/sync_run.rs`）断言目标上手动拷进去的存档 / 金手指 / 截图**同步前后连修改时间都相等**，且一条都没混进清单。真机演练：卡上 2 个清单之外的文件，同步 92 个文件之后内容哈希与 `(大小, mtime)` 逐条不变。

- [x] 删除前必须先呈现干跑预览

  `romcat sublibrary sync` **先把差量预览印完再动手**，而且没有 `--quiet` 能关掉它；计划里有删除时还要 `--yes` 点头，不点头一个字节都不动。CLI 测试 `同步之前一定先印一遍差量预览`（断言「差量预览」出现在「同步结果」**之前**）、`有删除时不点头就一个字节都不动`、`干跑一个字节都不写`（`crates/cli/tests/sync.rs`）。预览与执行读的是同一个 `Plan` 值，不可能对不上。

- [x] 导出前探测目标文件系统，据此决定硬链接或复制

  `sync::execute::probe` 在**媒体池的临时目录**与**子库根**之间试建一次硬链接，成了报 `Link`、不成报 `Copy`，两个探测文件当场删掉。探测**绝不拿主库里的文件当源**——`hard_link` 会改到源那一侧 inode 的链接数与 ctime，而主库连时间戳都不许碰。测试：`媒体同卷时走硬链接_不重复占用空间`、`探不动硬链接就复制_降级路径在任何文件系统上都成立`、`探测本身建不出文件时报复制`（并断言目标上不留探测文件）。真机演练报「探测结果 硬链接（媒体池 → 目标）」。

- [x] 主库侧在支持硬链接的卷上使用硬链接，不重复占用空间

  ADR-0009 修订段点名的那一段（**媒体池 → 目标**）落地了：真机演练 7 份媒体（24.75 MiB，含一段 41 MB 级视频）**7/7 与池里同一个 inode**（`stat -f %i` 逐份核对，`nlink=2`），零额外占用。单元测试在 unix 上同样断言 inode 相等。

  **保留**：ROM **一律复制、绝不链接**，即使同卷。理由与挂账见 **D84**——`hard_link` 会改主库那一侧 inode 的链接数与 ctime（ADR-0004 说的是「一个字节都不改、时间戳都不碰」），而且真链上了更糟：掌机上一次覆盖写就改到了主库里的原件。因此这一条按「ADR-0009 修订段的 `主库侧` = 媒体池导出」来兑现，ROM 那一侧的省空间留在 D84。

- [x] 子库内元数据中的路径全部相对于子库根目录

  `sync::frontend::lay` 生成的 Pegasus 元数据里，`file:` 写的是变体在主库里的**键**（相对主库根，而子库布局照搬那个键——D79），`assets.*` 写的是 `media/<哈希前两位>/<哈希>.<扩展名>`。两处都不经过任何绝对路径，是**构造上**成立的。测试 `子库内元数据里的路径全部相对子库根`（断言不含主库根、不含目标根，逐行检查 `file:`/`files:`/`assets.` 不以 `/` 或 `X:\` 开头，且指着的文件在卡上真的有）与 CLI 侧 `子库里的元数据路径全部相对子库根`。真机产物：`files: gba/【全部汉化】/…zip`、`assets.screenshot: media/1c/1c4f…jpg`，`grep -c /Volumes/` 为 0。

- [x] 同步可中断，中断后状态一致、可续跑

  每一份都先写同目录的 `<名字>.romcat-part`、`sync_all` 之后才改名到位；复制**每读一块看一眼中断信号**，中断就删掉临时文件——落点上要么是完整的旧文件，要么是完整的新文件。清单在中断那一趟照样落库（记的是「到中断为止目标上真实有什么」）。测试 `中断之后落点上没有半份文件_再跑一趟接着来`、`复制到一半被中断_落点上留的是完整的旧文件而不是半份`（16 MiB 的文件 + 另一线程在第一个 `.romcat-part` 冒头时按停止；实测 3/3 次都真的停在复制途中）、`上一趟遗留的半份文件先清掉再写`。真机演练：搬到第 1 个文件时 `SIGINT` → 0 个 `.romcat-part` 残留、清单与盘上一致；续跑补齐 82 个；第三趟「一个文件都不用动」。

- [x] 同步完成后清单更新为目标的真实状态

  清单里记的戳是**写完之后从目标 `stat` 回来**的那一个（于是 FAT32 那 2 秒刻度不构成问题）；删掉的整条丢掉；没碰的按目标实际状态重判。测试 `清单里的戳是写完从目标上读回来的那一个`（逐条比 `(bytes, mtime_ns)`）、`不要了而且目标上也没有的那些从清单里整条丢掉`。真机演练：92 条清单（83 ROM + 7 媒体 + 2 元数据）拿独立脚本逐条比盘上的 `(大小, mtime)`，**0 条对不上**；清单之外恰好 2 条，就是手动拷进去的存档与金手指。

  这一条顺带把挂账 **D75** 那个褶子处理掉了：清单多了一格 `absent`（「工具放过它，你在目标上删了，工具没补」）。不留这一格的话，同步完那条会整个从清单里消失，于是**下一趟变成一条普通的新增又长回来**——直接违反用户故事 65。测试 `你在目标上删掉的东西不会自己长回来`、`记着不补的那些_加了_restore_才补回来`、`早知道没了_这次也不要了_一句话都不用说`、`记着不补的那份又被拷回来了_照常核对`，以及 CLI 侧 `在掌机上删掉的东西不会自己长回来`。

## 开工第一件事：挂账 D82

工头裁决的那条先做掉：`sublibrary` 表加一列 `target_raw`（**系统给的原始形式**），键与读盘各用各的——`target` 是 NFC 的那一份（当键、进报告），`read_path()` 取原始那一份去开目录。老库那一列是 NULL，退回 `target`，行为与从前一致（真机上票 18 建的「掌机」正是这种）。

真机核对：目标目录名用分解形式建出来之后，`hex(target)` 是 NFC、`hex(target_raw)` 是 NFD、两串字节不同，`plan` 照样打得开。

顺带把 ADR-0020 那条「导出写哪种形式」答了一半，并记下一条实测：**macOS 的 fskit NTFS 驱动查找这一侧不分解敏感**——库里 383 个两种形式不同的键，NFC 与 NFD 都开得了。结论不构成「可以混用」的许可，因此仍留了 `fs::real_path` 兜底（先原样试一次，打不开才逐段列目录按 NFC 折过去认）。
