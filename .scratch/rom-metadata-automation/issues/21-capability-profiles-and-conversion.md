# 21 — 能力档案与格式转换

**What to build:** 每个子库声明它使用的前端与模拟器核心，工具据此决定每个平台的目标格式并在导出时转换。维护者不必记住哪个模拟器吃哪种格式。

**能力档案不只管模拟器**，还必须涵盖目标存储的限制——例如某些文件系统有单文件容量上限，大镜像根本放不进去。这类问题必须在差量预览阶段就暴露，而不是传到一半失败。

格式转换发生在导出侧，主库始终保持原始形态。同一个游戏导到不同设备可以是不同格式。

**Status:** done

- [x] 能力档案涵盖目标文件系统的单文件容量上限与文件名限制
  —— `capability::filesystem::Filesystem`：`max_file_bytes`（FAT32 = 4 294 967 295）、`max_name_chars`（255 个 UTF-16 码元）、`max_path_chars`（260，Windows `MAX_PATH`，**exFAT 与 FAT32 都写**——它是 API 的限制不是文件系统的）、`forbidden`（`\/:*?"<>|` + 控制符）、`reserved_stems`（CON/NUL/COM1…）。测试：`fat32_的_4_gib_单文件上限在预览阶段就拦得下`（含 ±1 字节的边界）、`文件名的字符限制与保留名也查`、`路径上限比的是完整路径`、`max_path_是_windows_的限制_对_exfat_一样成立`。**硬链接支不支持刻意不写**，那由运行时探测答（挂账 D93）。
- [x] 超出目标文件系统限制的内容在差量预览阶段就被报出
  —— `Desired::screen` 在排计划**之前**把它们从期望状态里挑出来进 `Plan::rejected`，于是**它们连一条 `Step` 都长不出来**，「传到一半失败」在构造上不会发生；而清单里已有的**也不删**（`plan` 里的 `barred`）。**真机（PS2，`retroarch-fat32`）：104 个、481.93 GiB 被拦下——101 个超 4 GiB 单文件上限、1 个路径 267 字符超 260、2 个转换落点撞车**，全在预览里点名，零字节写出。测试：`超出单文件上限的在差量预览阶段就报出来_而且一条步骤都长不出来`、`放不进去的不新增_也不删除`、`内置_fat32_档案对一份_4_5_gib_的镜像判放不下`。
- [x] 转换只产生新文件，主库一个字节不改
  —— 读主库只走 `LibraryFs`（那个 trait 没有写的办法，ADR-0004），产物写目标上的 `.romcat-part` 再改名。**真机取证**：转完之后主库那几份源的大小与 mtime 逐条 `diff` 一字不差（外置盘本身也是 `read-only` 挂载）。测试：`卡带的_7z_重打包成_zip_而且产物零解压读得回去` 与 `光盘类不吃归档…` 都断言源文件的 `len` / `mtime` / `inode` / `nlink` / 字节全等。
- [x] 差量预览中给出需要转换的条目数与耗时预估
  —— `Plan::converts`（几个 / 几个变体 / 转出来多大）、`convert_source_bytes`、`convert_ms`、`convert_estimated`，报告排成「要转 / 要读 / 转出来 / 大概要」。**耗时按未压缩量算而不是按源文件大小**——第一版按源大小估，54.11 MiB 的 7z 估出「1 秒」而实跑 3 分 17 秒（debug 构建），这条弯路记在 `Recipe::throughput_mib` 的文档里。**真机（release）：预估 33 秒 / 实跑 28 秒**（另一趟 39 秒，同一批数据两次跑的离散）。测试：`耗时预估随源的大小走而且不是零`、`卡带的_7z…` 断言 `converts.files` / `convert_ms` / `convert_estimated`。
- [x] 转换产物默认不缓存，可选开启缓存目录
  —— 默认边转边流式写进目标的临时文件，**不落第三份**；`romcat sublibrary sync --convert-cache <目录>` 才开，缓存键是 `SHA-256(配方 | 源的键 | 源的戳 | 内部条目序号)`，源一改键就变，取不到过期产物。**真机：第一台设备 24 份真转 39 秒、缓存里 24 份 551 MB；第二台设备同一份源同一条配方，24 份全部命中、用时 5 毫秒，两台卡上的产物逐字节相同。** 测试：`默认不缓存_给了目录才落第三份而且第二趟直接命中`。

## 真机数字（2026-09-02，release 构建）

主库 `/Volumes/新加卷/Game`（NTFS **只读挂载**），目标一律本地 fixture 目录，**没有碰任何真实设备或 SD 卡**。

| 演练 | 档案 | 结果 |
|---|---|---|
| PS2 全平台排计划 | `retroarch-fat32` | 529 个变体 / 832.91 GiB；**要转 294 个、要读 402.48 GiB、预估 1 小时 54 分**；**放不进 104 个 / 481.93 GiB**；**到了目标上打不开 187 个 / 115.85 GiB**。排计划 5.3 秒，**一个文件都没写、外置盘一个字节都没读**（内部构成全从中立库里那份零解压清单来） |
| SFC 汉化版重打包 | `独立模拟器-exfat` | 55 个文件；**24 份 `.7z` → `.zip`，未压缩 827.43 MiB，预估 33 秒 / 实跑 28 秒**；产物 537.35 MiB |
| PS1 解包 | `独立模拟器-exfat` | 443 个文件；**26 份容器解成裸文件（`.7z` → `.PBP` / `.BIN`），未压缩 575.85 MiB，实跑 7 秒**；26/26 的大小与容器头里记的未压缩大小相等 |

**产物是好的，而且换个工具也读得回去：**

- 卡上 50 份 zip **全部通过系统 `unzip -t`**（不是我们自己的读法）。
- 转出来的 `Chrono Trigger.zip` 57 条内部条目的**文件名 + CRC-32 + 未压缩大小，与扫描时零解压从源 `.7z` 头里读进中立库的那一份逐条相等（57/57）**——转换是逐字节忠实的，而且产物仍然零解压识别得了（ADR-0014）。
- 第二趟同步「**一个文件都不用动**」，1.8 秒。

**吞吐常量由这两趟实测定下**：重打包 29.6 MiB/s（取 25 留余量）、解包 82.3 MiB/s（取 80）。两个数都写在 `Recipe::throughput_mib` 的文档里，连同它们的测量条件。

## 挂账

- **D89** 目标吃不下、而且转不了的**照搬过去**（不搬是静默丢掉用户挑中的东西）
- **D90** 重打包成 zip 时**不写 ZIP64**，越界就判「转不了」
- **D91** 只解「**只有一个内容条目**」的透明容器（多条要按块调度重排执行循环）
- **D92** 转换只判**主文件**，附属文件与内部资源一律原样搬
- **D93** 能力档案里**不记**「这个文件系统支不支持硬链接」——听运行时探测的

## code-review 处置

两轴共 19 条，**采纳 15、驳回 4**。驳回的理由：

- **`Desired::screen` 一个方法干两件事（筛文件系统限制 + 查落点撞车）**——两者答的是同一个问题「这一份落得下去吗」，只是理由不同；而且都必须在**同一时刻**跑过**同一份完整的文件列表**（撞车只有看齐全了才发现）。拆开就是两趟遍历、两处要记得调。
- **`Rejected` 与 `Unsupported` 是 Data Clump，该合并**——两者的键不同：前者按**目标落点**（说的是「放不下去」），后者按**主库里那条源**（说的是「这个形态不对」）。合并会逼其中一个揣一个没意义的字段，而报告那两栏给的建议也完全不同（换张卡 / 拿外部工具转）。
- **`RejectReason::Collision` 与「被拦下的也不删除」是票据没要的行为**——撞车不查的话，`plan` 里那个 `BTreeMap<&str, &DesiredFile>` 会**静默丢掉**其中一份（真机 PS2 那一趟就撞出 2 例）；而「拦下的不删」防的是「我们这条声明本身可能是错的」时删掉用户卡上的东西。两条都是为了不说谎，不是新功能。
- **`unsupported` 照搬而不是跳过是自定决策**——是的，已挂 D89 并在票据里写明。这一版选照搬：不搬等于静默丢掉用户亲手挑中的东西，比白占一点地方糟得多。
