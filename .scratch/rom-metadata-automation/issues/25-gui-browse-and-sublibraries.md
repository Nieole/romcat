# 25 — 界面：库浏览与子库管理

**What to build:** 维护者能在界面里浏览整个主库、按平台与合集筛选、查看与编辑条目元数据，并管理**子库**——编辑选择集的规则与例外、查看**差量预览**、触发同步。

所有元数据编辑收敛在这里完成，主库的元数据文件不再是编辑入口。

**Blocked by:** 21, 24

**Status:** done

- [x] 能浏览主库并按平台、合集、语言、识别状态筛选

  五个维度（多一个**中文**，见下）一律下推到中立库的 `WHERE`
  （`catalog::browse::VariantQuery::where_clause`），可选值走一次 `GROUP BY`
  （`Catalog::facets`）。`crates/gui/tests/library.rs::四个维度筛得动而且筛选下推到中立库`
  钉两件事：界面上那个总数与另一条独立查出来的相等；筛完之后内存里还是那一扇窗
  （≤ 512 行）。`五个维度都有得选而且各自带着条数` 钉每一维都非空、合集名不与平台重名
  （ADR-0011 的正交）、「还没识别」是独立的一档。
  实测（release，合成数据照真机 46,483 个变体）：**列一次筛选面板 36.3 ms**
  （平台 17 个、合集 4 个、语言 6 个、中文 2 个，连表里那列作品名靠的小表），
  **换一次筛选 1.3 ms**（平台=NDS，剩 2,735 行），每帧中位 **0.62 ms**，
  滚一整趟读库 6 次、内存里始终 431 行。十万行时是 88.9 / 1.4 ms、每帧 0.92 ms、507 行。

  **超出票面加了一维「中文」**：汉化版是**变体**，它基于的发行版多半是日版，语言那一列
  上一个中文字都没有（ADR-0012）——只按语言筛的话，这个库最要紧的那批一条都不出现。
  `汉化版按中文这一维筛得出来而按语言筛不出来` 钉住它。

- [x] 能查看与编辑条目的元数据，含标题集合与首选变体

  详情面板由 `Catalog::variant_detail` 一次折齐（作品、发行版、合集、语言、识别结论、
  文件成员、**标题集合**、显示/排序标题、**首选变体**、媒体），实测**点开一条 3.05 ms**。
  编辑三样：加/删一条叫法（来源记作**裁决**，`加一条叫法当场进标题集合而且来源是裁决`）、
  裁/撤**首选变体**（`首选变体裁得动撤得掉而中文标题的来源一个字不变`）、写下/撤掉
  **刮削字段值**（年份、发行商、开发商、类型、简介、汉化组、标题，
  `刮削来的元数据看得见也改得动`）。三样都走**裁决**来源，而优先级表把裁决排在每个
  字段的最前——写下之后导出真会用它，不是「记下了但不生效」。

  ADR-0012 那条**首选变体与标题来源解耦**：`chinese_title()` 走
  `title::best_chinese`（`title::choose` 那把排序键原样用在中文那一档上），面板上把
  「中文标题取的是哪一条、与首选无关」写成一行摆出来；测试断言换过首选之后那一条的
  值、来源、类型一个字不变。

- [x] 能创建与编辑子库，含规则与例外

  `crates/gui/tests/sublibrary.rs::建得出子库也写得进规则与例外`：建子库、加规则、
  **写坏的规则当场拦下且不入库**、记一条带说明的**排除例外**。规则怎么读走
  `Rule::parse`，例外走 `Catalog::set_exception` / `clear_exception`，
  一条领域判断都不在 `crates/gui` 里。

- [x] 差量预览在界面中呈现，同步从这里触发

  排计划那条十来步的线搬进核心 `sync::prepare`，命令行与界面调同一个函数、印同一份
  `concerns()`——「预览说的」与「同步会做的」在构造上是同一个值。
  `差量预览摆得出新增与净变化` 钉账目与「清单之外的文件不进计划」；
  `没排过差量预览就同步不了` 钉 ADR-0016 那条硬要求（没预览时目标目录上一个新文件都
  没出现）；`改过规则那份预览当场作废` 钉「不拿旧差量骗人」；
  `同步从这里触发而且只碰清单里记录过的文件` 走完整条路——落到 fixture 目录、
  维护者自己拷进去的存档连修改时间都没动、清单落回中立库、回执说得出新增/更新/删除。
  同步跑在后台线程上，带一个真按得动的「停下」；中断、放弃、有步骤失败三样都印出来。
  实测：**排一次差量预览 405 ms**（8,203 个变体、8,206 个新增、16.26 GiB）。

  **保留**：排差量预览仍跑在画帧那条线程上（405 ms 的僵住），挂在 **D156**。

- [x] 容量超限时在界面上给出裁剪建议

  超出量与按体积排序的建议都由核心算（`sublibrary::over_capacity` /
  `trim_suggestions`，两处画法收在 `trim_ui` 一处），每行旁边一个「排除」按钮——
  点它记一条**排除例外**，**一个都不自动砍**。
  `容量超限时给裁剪建议但一个都不自动砍掉` 断言建议按体积降序、累计值往上加、
  而且三个变体一个不少地全在计划里。实测：4 GiB 上限下超出 15.79 GiB，给 10 条建议。
  另加一条「求值选择集」：只问中立库，**卡不在手边也算得出选中多少与超限多少**
  （ADR-0009，`卡不在手边也算得出选中多少与超限多少`）。

- [x] 媒体资源在界面中可见，能确认某条目缺哪些媒体

  媒体一条条列出来：类型、挂在作品还是变体、哪个源、**它在媒体池里的落点**、依据
  （`媒体一条条列得出来而不只是一个数`）。缺哪些走 `VariantDetail::missing_media()`，
  `点开一条看得见作品发行版标题集合首选变体与媒体` 断言合成数据里缺视频。
  「**没查池子**」与「查了、没有」分成两态（同 ADR-0021 的道理）：媒体池不在工作目录里
  时那一栏留空并直说，而不是报一句「一张都没有」把人赶去重跑刮削。

  **保留**：只列不画图——egui 自身不解码图片，画缩略图要引一个图像解码器进来。
  挂在 **D160**。

### D162 — `work.name` 要不要补 `UNIQUE`

- **裁决：settled，走 A（不补）。** 由票 `parking-3/10` 落地。
- **为什么不补：** 作品是**跨平台、跨地区的游戏概念**（平台在发行版那一层），同名异作是
  真实存在的（1988 与 2004 两部 Ninja Gaiden）。裸约束会把它们强行并成一部，还会把
  「日后人工给其中一部改个名就分得开」那扇门一起堵死。这与挂账 **D53**
  （`resolved —— 维持原样`）是同一条口径：同名在中立库里本来就已经是同一部作品，
  真要分开，该分的是识别那一层的去重键，不是给这张表加约束。
- **条目里那半句「重跑识别可能造出两行同名的作品」怎么解的：** 不靠约束，靠**复用**。
  重跑识别从此**按名字找现成的那一行**（`Catalog::work_named`，同名有好几行时
  **裁决造的优先**），找不到才新建；`clear_identifications` 不再整张清 `work`，
  收尾才收「识别自己造的、如今没人再指着的」那些
  （`Catalog::drop_unheld_identified_works`）。于是 `work.id` 跨识别重跑不换，
  同名两行也攒不出来。
- **钉着它的测试**（`crates/core/tests/identify.rs`）：
  `连跑两趟识别作品行不涨也不换一批_id`、`重跑识别认领裁决造的那一行而不是新建一行`、
  `同名的两条发行版线不会被并成一条`、`同名异作插得进两行而重跑识别不抹掉裁决造的那一行`。
- **留下的那半格**：同名异作在**作品**那一层仍旧只有一行（分得开落在发行版那一层），
  记在挂单 `Q284`。

### D163 — 显示标题不再是中文时，报告口径与详情面板各说一套

- **裁决：settled，走 A（报告改成数「标题集合里有中文的作品」）。** 由票 `parking-3/12`
  落地。
- **为什么对齐到标题集合那一侧：** 「中文覆盖」这个数要回答的是**刮削到底采到了多少
  中文**。显示标题是**后一步**的选择——裁决可以把它定成英文名，回退链里「那条条目还
  叫什么」也会把一串拉丁字顶上去（`title.rs` 的 `best_chinese` 文档列的两种情形）——
  让那一步去抹掉前一步的产出，等于用「我拿哪个当显示名」去回答「我采到了多少中文」。
  选项 B（详情面板改成印显示标题以外的中文名）解不了这条：面板**本来印的就是**
  `title::best_chinese`，也就是标题集合里中文那一档的第一名；要动的从来是报告那一侧。
- **落地的样子：** `TitleReport::chinese_works` 的判据从 `chosen.language == 中文`
  换成 `best_chinese(set, priorities).is_some()`——**与详情面板同一个判据**。中文那几栏
  （按类型 / 按置信度 / 官方译名的来路 / 低置信那一档 / 例子）跟着一起换，好与总数对得上
  （挂单 `Q306`）。新加 `chinese_not_displayed`：那 N 个里显示标题不是中文的有几个——
  报告里「中文覆盖」与「显示标题的回退链」两个数本来就不相等，差的正是它，
  不说出来看报告的人会以为其中一处是 bug。
- **详情面板一个字都没动**（票明写它是对的）。
- **钉着它的测试**（`crates/core/tests/titles.rs`）：
  `显示标题被裁成英文之后中文覆盖照旧算它`（人裁一个英文显示标题，报告照旧算它、
  `chinese_not_displayed` 涨到 1、`VariantDetail::chinese_title()` 仍是「魂斗罗」）、
  `一条中文叫法都没采到的作品不算进中文覆盖`（报告不算它、面板也说没有）。
- **留下的那半格**：真库上改口径之后那个数是多少没量过（真库不在开发机上），
  `docs/library-facts.md` 里 2026-09-01 实测的 6,501 原样留着，记在挂单 `Q304`。

### D157 — 界面上删标题不限于「裁决」来源的那几条

- **裁决：settled，走 A（都能删）**，外加一条选项里没写出来的第三样：**「这条被压掉了」
  这个记号住沉淀库**。由票 `parking-3/13` 落地。
- **为什么不把按钮灰掉：** 删一条明显错的中文名是**当下**就想做的事，而「它会回来」
  只在**重折**之后才成立。灰掉刮削来的那几条，等于要在面板上向人解释一整套来源规则
  （哪些是折出来的、哪些是人写的、为什么后者删得掉），而人要的只是把眼前那条错译名去掉。
- **为什么记号不住 `title` 表上的一列（选项 B 那条路）：** 中立库**整份可再生**——结构一变
  就让用户删掉重扫（`catalog::SCHEMA_VERSION`），那是省下一整套迁移代码的便宜买卖。
  「人删过这一条」不可再生，放进那张表等于说「下一次改结构时你删过的全部复活」。
  它与**裁决**、**收藏**、**人工纠正**是同一类东西，就该与它们同住**沉淀库**（ADR-0006
  的修订段把这条界线写死了）。
- **落地的样子：**
  - 沉淀库 `MIGRATIONS` **追加第 5 条**（前四条一个字没动，`schema_version()` 从 4 变 5），
    建 `title_suppression` 表。键是**作品名加那条叫法的五样**——与 `catalog::title` 那张表的
    主键、与面板上那个「删」删掉的那一行逐字一致（挂单 `Q314`）。
    锚是作品名而不是内容锚：标题挂在**作品**这一层；作品名从 DAT 条目名折出来，
    所以这条记号与内容锚一样**换台机器仍然认得出**。
  - `title::refold` 收 `&Store`，**折完之后照压制记录筛一遍再写库**。筛在写库这一层，
    于是详情面板、导出、报告与搜索读到的是同一张表，各自不必再记得筛一遍。
  - 界面上「删」走 `title::suppress`（删中立库那一行 + 记一条压制），标题集合底下多一栏
    **「压掉的叫法」**，每条带一颗「恢复」——**这一下不是不可逆的**。
    集合为空时那句话分两种写法，屏上因此**分得出「压掉了」与「没采到」**。
  - `source = 裁决` 的叫法删掉**不记压制**：它根本不经过折，没有什么会把它折回来
    （挂单 `Q317`）。
- **钉着它的测试**：`crates/core/tests/titles.rs` 的
  `压掉一条叫法之后重折不把它折回来而同批没压的照旧回来`（压掉「魂斗罗」→ 再跑一整趟
  识别 + 刮削 + 折标题 → 它没回来，而同一批里的「魂斗罗 中文版」照旧回来）、
  `压制记在沉淀库里_中立库整份重建之后它照旧压着`（中立库整份换掉重扫，记号还在）、
  `撤掉压制之后那条叫法下一趟重折就回来`、`裁决来源的叫法删掉就是删掉_不为它记压制`；
  `crates/core/src/verdict.rs` 的
  `第四版的老库带着裁决合集升上来_压制那张表是空的`、
  `压掉一条叫法之后它一直压着_撤掉才放回来而行留着`、
  `压制的键是那条叫法的五样_少一样都不连坐`；
  `crates/gui/tests/browse.rs::删掉一条刮削来的叫法之后屏上分得出压掉了与没采到`
  （断言看的是这一帧真的画在屏上的字）。
- **留下的那几格**：压制记录没进沉淀库的**导出格式**（`Q319`，合集成员关系也没进，
  同一个缺口）；`romcat titles` 的报告没报「这一趟压掉了几条」（`Q320`）；
  「压掉的叫法」这个词还没进 `CONTEXT.md`（`Q318`）；界面上「恢复」之后要等下一趟重折
  才看得见那条叫法回来（`Q316`）。

### D158 — 差量预览的步骤表最多列 2,000 条

- **裁决：settled，走 B（把步骤表也做成虚拟化的，去掉上限）。** 由票 `parking-3/08` 落地。
- **为什么不是 A（截断）：** A 的理由是「那张表是**给人扫一眼**的，账已经在上面的四行汇总
  里；完整清单走 `romcat sublibrary plan --json`」。前半句对，**四行汇总一个字没动**；
  后半句是这条挂账真正的代价——**同步前必须看一遍它要做什么是 ADR-0016 的硬要求**，
  而「想确认第 5,000 步是什么就得转去命令行」等于把那一眼的一半挪出了界面。
  B 那句「代价是要把 `Plan` 整份留在界面状态里」当初就已经写着「它已经在了」
  （`Screen::prepared`），所以这一票**去掉上限的净代价是零**：`TableBody::rows` 只调用
  视口里那几十行的闭包。
- **落地的样子：** 删掉 `TOP_STEPS = 2_000` 与末尾那句「另有 N 步没列」；`steps_table`
  改成 `pub`、多一个 `scroll_to`（**只有量帧率与测试才给**，界面上是 `None`），
  而且**返回这一帧真的画了几行**；`Screen::steps_drawn()` 把那个数交出来。
  上面那四行汇总（`tally_ui`）与「要说出口的怪事」（`concerns_ui`）一个字都没动。
- **判据不是秒表：** 挂钟在门禁上是一张彩票（票 `parking-3/01` 拿掉过一条），
  所以钉这件事的是**「这一帧画了几行」**——照票 `parking-3/17` 给主列表立的那条路
  （`FrameCost::reads`）。
- **实测**（这台开发机 12 核 / 15 GB，合成数据，release，`--bench-sublibrary`）：

  | | 869 步 | **21,571 步** |
  |---|---|---|
  | 每帧画几行 | 35 | **35** |
  | 每帧中位 | 0.76 ms | **1.27 ms** |
  | 最慢的一帧 | 1.21 ms | **1.85 ms** |

  **一次同步动几步：今天是 21,571，不是这条挂账写的 8,206**——那是票 `parking-3/17` 换
  合成数据形状之前量的（`17` 让每九个变体带一个附属文件与一个内部资源，一个变体不再等于
  一个文件）。方向没变，量级还大了一倍半。全文在 `docs/library-facts.md`。
- **钉着它的测试**（`crates/gui/tests/sublibrary.rs`）：
  - `八千步的计划滚到第五千步那一行照样摆得出来`（第 5,000 步与**最后一步**都摆得出来、
    「另有 N 步没列」那句话没了、而且这一帧只画了几十行——摆得出第 5,000 步靠的不是把
    八千行都画出来）
  - `翻行画几行只跟视口有多高有关与总步数无关`（2,000 步与 8,206 步两份**同样合法、
    只是长短不同**的计划，滚到同一个位置画出来的行数必须相等）
  - `差量预览摆得出新增与净变化而且步骤全部展开得了` 补了一句：摊开之后
    `steps_drawn()` 与计划的步数对得上——**屏幕真的走的是那条路**。
- **留下的那半格**：一份两万步的计划摊开之后，那张表在真界面上**整个落在视口之外**
  （卡头、容量条、汇总与怪事那几段加起来就比一屏高），人得先滚外层那个滚动区。
  界面这一票没动，记在挂单 `Q266`；`steps_table` 为什么改成 `pub` 记在 `Q267`。
  同一处还有一件：`card_ui` 每帧把 `Prepared` 整份深拷一次（O(总步数)），于是
  「翻行的代价与总步数无关」这句话是在**单独画那张表**那条路上量到的，真界面那条路上

### D161 — 变体表里那一列作品名排不了序也筛不了

- **裁决：settled，走 B**（页查询里 `LEFT JOIN work`，另立一个浏览专用的行类型，
  把作品名做成可排序列）。由票 `parking-3/11` 落地。
- **条目里那半句已经过时了，先说清楚：** 这条记下来那会儿（本票的 `/code-review` 处置，
  `4abb29c`），浏览屏画的是**变体表**，那一列作品名是取回来之后拿
  `Catalog::work_names()` 在内存里对出来的。票 `gui-redesign/03` 把那张表整个换成了
  **作品级主列表**（`crates/gui/src/table.rs`，一行一个作品）：作品名成了第一列、
  `WorkOrder::Name` 是默认排序且下推在 `ORDER BY` 里，筛选走 `Dimension::Work`
  （`catalog::filter`）也下推着。所以「排不了序也筛不了」在**屏上那张表**已经不成立，
  「只能退回『键里含』那个框」说的是 `VariantQuery::contains`，主列表上那是搜索框加
  筛选器（挂单 `Q294`）。没跟上的是**变体那一层的页查询**——`Catalog::variant_page`
  交回来的还是 `VariantRow`，只带 `work_id`。B 路补的正是它。
- **A 被否掉的理由，与条目里推荐它的理由是同一条：** 条目当年推荐 A（先只做显示）说的是
  「`LEFT JOIN work` 之后 `VariantRow` 就不再是『`variant` 表的一行』，那个类型被十几处
  构造着」。那句话成立，可它反对的是**给 `VariantRow` 加列**，不是反对下推——
  另立一个类型（`BrowseVariant { variant: VariantRow, work: Option<String> }`）之后，
  `VariantRow` 一个字段都没动，十几处一处都没碰。形状照同一个模块里的 `WorkVariant`
  来：**装着**那一行，不把它的字段抄一遍。
- **条目里另半句「真实需求是按标题排」照旧成立，也照旧没做：** 显示标题是
  `title::choose` 挑出来的（优先级表、语言、来源三样一起判），SQL 里算不出来。
  票 `parking-3/11` 明说只做**作品名**那一列，标题那条路不在范围内。
- **怎么做的：** `Catalog::variant_browse_page` 一趟
  `LEFT JOIN work ON work.id = variant.work_id`，`SELECT` 多一列
  `work.name AS work_name`；排序是 `VariantOrder::Work`，筛选是 `作品^…`
  （`Dimension::Work`）。`variant_page` 与它**走同一条 SQL**，于是两个入口筛的排的不会
  漂开。**还没认出作品的那些排在末尾，正反两个方向都是**（`ORDER BY` 多一把
  `work_name IS NULL` 的键）——SQLite 默认那套跟着方向翻，人点一下表头，那一批就整批
  从表尾跳到表头，而它们在这一列上根本没有值可比：没有值的东西，位置不该由方向决定
  （挂单 `Q295`）。
- **钉着它的测试**：`crates/core/tests/browse.rs` 的
  `按作品名排序是下推出来的而且作品那一格空着的一律排在末尾`（两个方向，期望从数据自己
  算出来，并断它与按键排不是同一个次序）、`页查询自己带回作品名而不必整份读那张小表`
  （只取中间一页，那一页每一格都对得上作品表）、`按作品名筛也下推到库里`；
  `crates/gui/tests/browse.rs` 的 `按作品名排完屏上画出来的次序就是作品名的次序`
  （断的是这一帧真的画出来的字）与 `筛选器里按作品名筛得动而且下推着筛`。
  三条突变检查都做过（列名改掉、`IS NULL` 那把键去掉，各自当场红）。
- **实测**：按作品名排（默认排序）滚 720 行，**946 行读 1 次库、中位 19.20 ms；
  10,978 行读 1 次库、中位 19.27 ms**，内存里始终 512 行（dev profile，
  `bench::FrameCost::reads`）。那张 9,226 行的作品表**这一屏一次都没读过**——
  `crates/gui/` 里 `work_names` 零出现。
- **留下的那几格**：**变体那一层的排序屏上点不到**——`VariantOrder` 在
  `crates/gui/src/` 里零出现，新入口眼下服务的是字体自检，`variant_page` 更是连那个
  都没有了（`Q297`，规格 User Story 31 按字面因此没做到）；按作品名排那一档背后没有
  索引（`Q300`）；`platform` 那一列的 `NULL` 次序仍跟着方向漂（`Q296`）；既有那条
  `五列都排得了序` 的断言仍然是弱的（`Q298`）；那两个毫秒数没有常设入口（`Q303`）。
