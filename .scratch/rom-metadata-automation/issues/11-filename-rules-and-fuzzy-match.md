# 11 — 文件名规则解析与中文离线模糊匹配

**What to build:** 数据库覆盖不到时的倒数第二层：把文件名里的汉化组名、版本后缀、以及「完美版」「最终版」「中文版」这类噪音词剥掉，用剩下的中文名去与中文离线数据源做模糊匹配。

这一层零成本、可复现、可反复重跑调参数——这三样是模型推断都没有的。模糊匹配会错配，因此结论必须带置信度并进队列。

**Blocked by:** 08, 10

**Status:** done

- [x] 文件名解析能剥离汉化组名、版本号、以及常见噪音词
  —— `filename::Rules::parse` 分三步：剥扩展名（多层，`.cia.zip` / `.tar.zst`）、
  切**记号组**（`[…]`(…)`【…】`（…）四种括号）并逐组归类（汉化组 / 年份 / 版本 /
  语言地区 / 容量 / 平台词 / 编号 / 记号噪音 / **认不出**）、清**正题**（编号前缀
  `033.`、分类前缀 `動作：`、平台前缀 `GBC海贼王`、词中间插的点 `海.贼.王`、
  尾巴上的 `-美版-休闲益智`、两头的噪音词 `唐老鸭汉化版`）。
  **汉化组认的是词不是名单**（记号里含「汉化 / 漢化 / 翻译 / 移植」等就整组是组名），
  所以没见过的组也认得出。`cargo test -p romcat-core --lib filename::` **26 条**，
  用的全是真库里的名字。`romcat names <文件名>` 当场看得见剥了什么。
- [x] 剥离规则是配置而非硬编码，维护者能补充自己遇到的模式
  —— `crates/core/src/filename/rules.toml`（246 行，每张表都写清为什么），
  `--name-rules <文件>` 换成自己的，工作目录里放 `name-rules.toml` 自动生效，
  `romcat names --dump-builtin` 导出底稿（与 `--manifest` / `--sources` 同一个套路）。
  **默认是补充不是换掉**：`"继承内置" = true`（默认值）时每张表接在内置那份后面，
  加一个新汉化组写三行就够（测试 `用户的规则是补充不是换掉` / `整份换掉也做得到`）。
  闭环靠 `Parsed::unknown`：**认不出的记号进报告**，照着补、重跑一遍就见效——
  真机第一趟报出 `CHS×60`、`官中×28`、`PD×78`…，补进配置再跑，这几条没了，
  换成下一批（`Mai233×41`、`AVG×27`）。全程不碰 Rust。
- [x] 中文数据源以离线形式使用，匹配不消耗任何在线配额
  —— `romcat zh sync` 取一次 Bangumi Archive 的 dump（**415.70 MiB**，
  `dump-2026-09-01.210329Z.zip`），流着读里面 960 MB 的 `subject.jsonlines`
  （**绝不整份读进内存**，本机当时只剩几个 GiB），建成本机一份 11 MB 的 SQLite——
  **110,788 条游戏条目、35,736 条有中文名**，整趟 31.8 秒。
  取数**走票 06 那道闸门**，一个字都没往白名单里加（两个落点本来就在名单上，
  测试 `latest_json_读得出下载地址与指纹` 断言 `guard::check` 放行）；
  匹配那一趟 `Locality::Local`，一个网络请求都不发。指纹（官方给的 sha256 加文件名）
  没变就整件跳过——**不下那 415 MB**。
- [x] 模糊匹配用平台与年份做交叉校验，不只看标题相似度
  —— `zh::Index::lookup`：相似度是二元组的 Dice，**两道交叉校验各三档**
  （`Check::Agrees` / `Unknown` / `Conflicts`），**对不上的整条不产出**
  （不是降档——调研 §13.1「宁可留空也不要写错的中文名」）。
  调研那个反例自己就落选了：`solarjetman` 与 `solar2` 的 Dice 是 0.53（有测试钉着）。
  **光有相似度不够，还加了一道硬闸**：两边的数字与拉丁字母序列必须完全相同。
  这一条是真机抽样逼出来的——低置信档错配率 **68% → 44% → 15%**，错法高度集中在
  `第3次` 撞 `第4次`、`超级机器人大战J` 撞 `超级机器人大战R`（Dice 0.88–0.90）。
  **保留**：年份这一侧真机上几乎永远说不出（文件名里的年份多半是汉化的年份），
  所以中置信那一档的判据是「平台对得上，且名字一字不差**或**年份也对上」——
  一刀切要求两道都对上，那一档在真机上是空的（挂账 D119）。
- [x] 匹配结论带置信度与依据，一律进入待确认队列
  —— `identify::fuzzy::candidates` 产出的候选 **`accepted` 恒为假**，置信度封顶
  **中置信**（高置信留给精确命中与裁决，ADR-0002）。**依据**写全：从哪个名字剥的、
  剥掉了什么、名字上写着哪个汉化组、撞上哪条条目（带条目号）、两道校验各是什么、
  以及那句「这一层一个字节都没看，永不自动通过」。
  接缝测试 `tests/fuzzy_match.rs` **7 条**，其中 `这一层的候选一律进待确认队列`
  直接跑 `triage::survey` 断言它们在队列里、而精确命中的那一份不在。
  **真机**：3,356 条候选（中置信 2,603），涉及 3,119 个变体，**2,400 个变体只靠它
  才有候选**；自动通过 **0 条**。
- [x] 匹配参数可调整并重跑，不需要重新扫描
  —— `--similarity` / `--strong-similarity` / `--fuzzy-limit` / `--year-slack`
  四个参数挂在 `romcat identify` 与 `romcat zh find` 上（共用同一个 `TuningArgs`），
  `--no-fuzzy` 整层关掉。重跑一趟识别 **65.5 秒、回盘 0 B**——算过的哈希、探过的
  光盘与卡带事实都还在中立库里（挂账 D14 那条增量）。
  测试 `换一套匹配参数重跑一遍不必重新扫描`：同一份中立库跑两趟，只换门槛，候选数跟着变。
  刮削那一侧的参数进**输入指纹**（测试 `匹配参数进输入指纹`），调完重跑会重采而不是
  被缓存咬定「输入没变」。


## 从挂账转来的前瞻

- **内部文件名的编码探测（原 D22）**：票 03 对非 UTF-8 的容器内部文件名按有损转换处理（FC 子树实测 7,082 条受影响，多半是 GBK），理由是识别 靠 CRC-32、名字不参与命中。**这票真要拿文件名做匹配，那批乱码就变成实打实的问题**，需要一次像样的编码探测（GBK / Shift_JIS / Big5 字节分布相近，猜错会把一种乱码换成另一种）。

  **落地了。** `container::charset::decode`：UTF-8 严格验一遍，不是就按 GBK / Big5 /
  Shift_JIS 各解一次，**一个替换字符都不许出现**，再按「这串字节落在哪一区」打分——
  GB2312 常用区（首字节 `B0`–`F7` 且次字节 ≥ `A1`）、Big5 常用区（`A4`–`C6`）、
  Shift_JIS 的假名区，而**半角片假名倒扣分**（一串 GBK 汉字在 Shift_JIS 眼里正是一串
  半角片假名，这一条比什么都灵）。平局归 GBK——票 03 实测这批名字多半是 GBK。
  zip 与 zst 两侧的 `decode_name` 都改走它，`InnerEntry::name_lossy` 的含义随之收窄成
  「**连编码都探不出来**」。

  判据**不能是「解不解得出」**：`上海大亨` 用 Big5 解出来是 `奻漆湮箋`，一个替换字符
  都没有——那正是「把一种乱码换成另一种」的样子。单元测试用的是**真库里那四条名字的
  原始字节**（从 `FC/【HACK版游戏】/…/1.FC经典游戏/` 几个 zip 的中央目录里逐字节读出来，
  只读）：`上海大亨.nes`、`圣斗士星矢2汉化.nes`、`封神榜.nes`、`快打旋风.nes`，四条全对；
  另有 Shift_JIS 与 Big5 各一条反向样本。

  **真机口径**：全库 1,016,857 条内部条目里 **21,901 条**不是合法 UTF-8
  （FC 9,207、NDS 2,801、GBA 1,274、PSP 592、GB 427、SFC 379），其中 `.nes` 4,670、
  `.gba` 691、`.smc` 409、`.gbc` 353——真的是 ROM。

  **存量那批也解了**（code-review 之后补的，原挂账 D122 就地裁决）：编码探测挂在**读容器
  的时刻**，只对之后扫的容器生效，而已经落库的那批名字里 `U+FFFD` 已经把原字节吃掉了。
  但**不值得为它重扫整个主库**（27 分钟，还要连带丢掉算过的哈希与探过的光盘/卡带事实）
  ——真正要重读的只有中央目录，一个容器几毫秒。于是有了 `romcat names --recheck`
  （`scan::names::recheck`）：问中立库哪些容器的名字还是乱码，只把那几个的内部构成
  重读一遍，**只改名字那两列**（大小、CRC-32、块号一个不动——那些是识别的判据），
  条数对不上就一条都不改（那说明文件真的变了，该走扫描那条路）。

  **真机实测**：7,126 个容器、**114.2 秒**、**改掉 20,020 条名字**、
  仍然解不出来 **0 条**、读不动 0 个。样例（报告直接印出来给人眼核对，猜错了看得出来）：


## 挂账裁决

- **原 D122（那批已经落库的乱码名字怎么办）**：选**选项 B**——加一条
  `romcat names --recheck`，只把「名字还是乱码」的那些容器的中央目录重读一遍，
  只改名字那两列。理由是选项 A（等下一次全库重扫）要 27 分钟、还要连带丢掉算过的哈希
  与探过的光盘/卡带事实（识别首趟的十二分钟），而真正要重读的只有中央目录——
  真机实测 7,126 个容器 **114.2 秒**就跑完了，改掉 20,020 条名字。
  选项 C（在中立库里加一列存原始字节，从此可逆）没做：那要让用户删掉 8.60 TiB 的
  中立库重扫一遍，换来的只是一件已经解决了的事的第二条退路。
- **D119 中置信判据含「名字一字不差 + 平台对得上」** — 维持。与票据字面的差别靠**依据**那一句说清，已经写了。
- **D124 刮削的「文件名」源不改用剥离规则** — 维持。两条都在标题集合里按置信度排，用户看不见这件事。
- **D127 名字撞出来的候选让「命中」变宽** — 维持。报告已经在同一屏里把两个数并排给了（88.5% 含模糊 / 84.7% 不含）。
