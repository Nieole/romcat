# 07 — CRC-32 精确识别

**What to build:** 识别管线的第一命中层跑通：用透明容器里零解压可得的 CRC-32 加未压缩大小去匹配 DAT，产出带**置信度**与**依据**的**候选**，并在中立库里建立**作品**与**发行版**。维护者第一次看到真实的命中率。

关键约束：No-Intro 按去头哈希，TOSEC 按含头原样哈希。必须同时计算两套，否则会丢掉全部 TOSEC 汉化条目。

**两类东西不该进 DAT 匹配，库体检证实它们真实存在**：**补丁**（如 `《夏莉的炼金工房…》汉化补丁 Ver.1.0.zip`）本身不可运行，撞 DAT 必然落空；**没有发行版链接的变体**（同人移植与 homebrew，如 `AIME00001(wan华镜 v3.1)`、`mGBA-0.10.0-vita.7z`）不在任何官方数据库里。让它们一路掉到模型推断是白烧一遍，而且会产生自信的错误候选。

**Blocked by:** 03, 05, 06

**Status:** done

**收尾（2026-09-01）**：384 个测试全绿，`cargo clippy --workspace --all-targets` 与
`cargo fmt --check` 干净。十条验收逐条见下，**一条带保留**（第 10 条的「不联网」是
结构性证据而非可断言的事实）。

## Comments

**落地形态**：核心在 `crates/core/src/identify/`——`header`（**外挂头**五种 + NKit 判据）、
`fingerprint`（一份内容的两套哈希，三态的 `Headerless` 把「没有外挂头」与「还没看过」
分开）、`scope`（哪些变体不该撞 DAT）、`naming`（从条目名读出作品 / 地区 / 语言）、
`report`（命中率报告）；查询那一侧是 `dat::lookup`（CRC-32 加大小，一条命中就是一条依据）；
中立库多了 `candidate` / `identification` / `content_hash` 三张表，作品与发行版多一列**来路**
（`catalog::identify`）。命令行是 `romcat identify`。

**中立库结构版本 3 → 4。** 加表加列，读到旧版本让用户删库重扫——挂账 D26 说的
「票 08 之前还走得通」这一趟仍然成立，票 08 开始积累裁决之后就不成立了。

**一个真机查出来的取数缺陷**（票 06 的地界，但它把这票堵死了）：GitHub 的发行资产
现在 302 到 `release-assets.githubusercontent.com`，而闸门的白名单里只有
`objects.githubusercontent.com`。于是 **No-Intro 整档一件都取不回来**——48 份 DAT、
76,429 条条目，正是第一命中层的主力弹药。加了那个主机并补了回归测试
`github_发行资产的两个落点都在名单上`。

**一个真机查出来的性能缺陷**：`rusqlite` 的 bundled SQLite 编译时开了
`SQLITE_DEFAULT_FOREIGN_KEYS=1`，**外键检查默认是开着的**。重跑识别要删掉自己上一轮
建的一万八千条发行版，每删一行都要在 `variant` 上找「还有没有人指着我」——没有索引就是
全表扫描，实测 46,444 个变体上要 **3 分半**。加了 `variant(work_id)` 与
`variant(release_id)` 两条索引之后是 **8.2 秒**。

**从挂账转来的两条前瞻，一条兑现一条改判**：

- **D14（增量的价值在这票显现）——兑现了。** 算过的哈希落在 `content_hash` 表里，
  由扫描按文件的三元组作废（与容器内部构成的作废方式同源）。真机：首趟 832.9 秒、
  读 9.04 GiB；**第二趟 7.9 秒、0 字节**，24,604 份哈希从中立库取回。
- **D3（收紧去重判据）——做下来发现拿到的不是那个 CRC-32，改判并记成挂账 D49。**
  这一层算的是**容器内部文件**与**裸文件**的哈希，从不算容器**自己**的哈希；而库里
  91.1% 的容量是容器，重复拷贝也主要是成对的容器。给容器自己算哈希要读 7.84 TiB，
  正是这整张票绕开的那件事。**可行的做法记在 D49**：容器的内部构成本身就是指纹，
  零解压、零读盘，中立库里已经躺着了——但它属于报告那一侧，值得单开一张票。

**报告读出来的三件事**（详见 `docs/library-facts.md`）：

1. **ADR-0008 的判断被真机证实了。** FC 82.8%、GB 91.5%、SFC 80.1%，而
   **GBA 5.8%、NDS 4.4%、GBC 0%**——正是 ADR-0008 点名的「中文玩家存量最大、汉化版
   数据覆盖最差」的那几个。抽样看过 GBC 那 53 个未命中：全是精灵宝可梦的汉化与修正版。
   缺口不在「这是什么游戏」，缺口在汉化版。
2. **GoodNES 那 748 条汉化条目这一层一条都撞不到**：实测它的 30,244 条记录里
   **CRC-32 为 0 条**、SHA-1 为 24,470 条、大小为 0 条。第一命中层的判据是 CRC-32 加大小，
   天然够不着——它得等按 SHA-1 走的那一层（ADR-0002 修订段早说过这件事）。
   真机命中的 1,064 个汉化版**全部来自 TOSEC 的 499 条**。
3. **无判据的近三分之二要等票 26 与票 04**：那 2,913 个 zst 与 rar 容器里装着的东西，
   这一层连看都还看不见。

## code-review 处置（fixed point `0caccbd`）

**采纳 9 条：**

1. **NKit 检测被目录削弱**（Standards，硬；Spec 也独立报了同一条）—— `may_be_nkit` 原先
   要求平台是 NGC / WII，而 ADR-0011 说**目录只是强先验不是权威**；容器里的 `.iso`
   更是从头到尾没验过就自动通过了（它的 CRC-32 零解压白拿，而 NKit 要读字节才验得出）。
   已把**接受**那一侧的判据换成**内容自己给的**：撞上的那条记录说它是 GC / Wii 的光盘，
   这份内容就必须验过 NKit 才敢自动认账；验不了（盘不在位、容器解不开、
   `--no-read-library`）一律降一档。回归测试 `验不了_nkit_的_gc_与_wii_镜像不许自动通过`。
2. **homebrew 的 TitleID 判据没限定平台**（Spec）—— `ULUS10041`（PSP）、`BCAS20228`
   （PS3 的**官中版**）形态上都是「四字母加五位数字」，而那张官方前缀表只列了 PSV 的。
   不限定平台就会把整批官中版挡在识别管线之外，正是 ADR-0012 说「官中版走精确哈希直接过」
   要避免的事。已限定到 PSV。**这条在真机上是实打实的**：修之前 PSP 被跳过 39 个，修之后 10 个
   ——那 29 个是 `ULUS` / `ULJM` 形态的 PSP 序列号被当成了自造 TitleID。回归测试 `别的平台的序列号形态不当成自造_titleid`。
3. **`--max-read-mib` 挡下来的那些说不清自己为什么没判据**（Spec）—— 原先它们既没有
   哈希也没有理由，报告里落进「这个变体里没有可以撞 DAT 的内容」，等于把一条**策略**
   说成「这一层拿不到」。已改成写明「按上限没读：这一份 X，上限 Y」。
4. **`restore()` 认不出外挂头的名字时硬顶一个 iNES 上去**（Standards，静默的错误缺省）——
   猜错了去头哈希就是个撞不上任何东西的数。已补 `DumpHeader::from_label` / `all()`
   （与 `Confidence` / `State` / `Convention` 一致），认不出就当「还没看过」下一趟重算。
   测试 `外挂头的名字能来回折`。
5. **`Hit::cloneof` 查出来没人读、`naming::parse` 的 `cloneof` 恒为 `None`**
   （Standards / Spec，Speculative Generality）—— 承认：ADR-0010 的 parent/clone 归堆
   实际没接上。已接上（候选与它的父条目名成对走，排序不会把它们冲散）。
6. **`Hit::rom_id` 无人读** —— 删掉。
7. **命令行那一段重复**（Duplicated Code）—— 同一对 `(主库根, json)` 守了两遍
   `refuse_writing_into_library`；「序列化 → 写文件 → 打一句」在三个子命令里各抄了一遍。
   已合成一次守卫 + 一个 `write_json` 泛型入口，体检、DAT 仓库、识别三处共用。
8. **`DatRepo::wrap` 现在只剩一句转手**（Middle Man）—— 删掉，全仓用 `error`。
9. **`Origin` / `Unit` 在同一个 crate 里各有两个、`hashing` 与 `convention` 分不出谁是谁**
   （Mysterious Name）—— `catalog::Origin` → `Provenance`（`dat::registry::Origin` 说的是
   「一份 DAT 从哪儿取」）、`identify::Unit` → `ContentUnit`（`dat::repo::Unit` 说的是
   「一次取数的最小单位」）、`hashing` / `convention` → `hashed_as` / `dat_convention`
   （撞上时用的哪套哈希 vs 那份 DAT 声明的口径，两者会不一样，见验收第 1 条）。
   顺带把 `clear_identifications` 与 `candidate_counts` 里四处 `'识别'` 字面量换成
   `Provenance::Identified.label()`——**换的时候顺手撞出一个真错**：外键是开着的，
   删除顺序得从引用方往被引用方走，先删发行版会当场报错。

**驳回 5 条：**

1. **「`evidence` 是 依据 的 `_Avoid_` 词」** —— 驳回。这个仓库的标识符一律是英文
   （`Candidate`、`Confidence`、`platform`、`Penetration`、`Convention`），词表的 `_Avoid_`
   管的是**说这个概念时用哪个词**——而代码里每一处散文、报告里每一行文字说的都是「依据」。
   把字段改成 `basis` / `grounds` 只会让读代码的人多猜一次。测试名里那两处「匹配」倒是
   改了（`跳过_dat_匹配` → `不去撞_dat`）。
2. **「`rank()` 里的数据源先后是 `sources.toml` 的抄件」**（Repeated Switch）—— 驳回。
   清单里的顺序说的是「先取哪一个」，`rank` 说的是「**哪个源的名字更可信**」：
   No-Intro 与 Redump 的条目名、序列号与 parent/clone 关系最整齐，TOSEC 的名字里塞满了
   发行年份与小组名，MAME 是逐芯片的。两者没有理由绑在一起，绑上了反而是一处伪共享。
   理由已写进函数文档。
3. **「`has_ammo` 是超框的优化」**（Spec）—— 驳回。`switch/` 那 91 个变体是 **154 GiB 的
   `.xci`**，而 DAT 库里 Switch **一条记录都没有**（那是票 27）。读完它们只是把 154 GiB
   换成一堆撞不上的数——**首趟会从 14 分钟变成一个多小时**，而这票的交付物就是那个数。
   它不静默：报告里自成一行理由并点名到变体，平台表还专门有一列「DAT 条目」。
   容器里那套零解压的 CRC-32 照撞不误，所以放错目录的东西照样撞得上别的平台的记录。
4. **「`has_ammo` 与体积上限落进无判据，压低了未命中」**（Spec）—— 驳回。「未命中」的
   意思是**撞了 DAT 没撞上**；这两种情形连判据都没有，算进未命中才是虚报。报告把它们
   按理由拆开、逐条点名，读的人一眼看得出哪些是「这一层认不了」、哪些是「我按上限没去拿」。
5. **「`naming` 抽地区与语言超出『建立作品与发行版』」**（Spec）—— 驳回。`release` 表的
   `region` / `languages` 两列是票 05 照 ADR-0019 那道**世代裂缝**建的：数字世代的中文是
   同一条发行版的**语言属性**。两列全留空，那道裂缝就只是一句没人执行的话。抽法保守——
   认不出就留空（TOSEC 名字里第一个括号是年份，不当地区）。

**未处置 1 条（记成挂账 D48）：** 「`scope::decide` 在来路混着时会读错」（Standards，硬）
—— 承认：裁决挂了作品、识别挂了发行版，清完也是「作品有、发行版空」，下一轮会把它当成
homebrew 跳过。真正的出路是让裁决把「确认没有发行版」记成一条**明确的记录**而不是靠链接
为空推断，那是**票 08** 定裁决记录形态时顺手的事，现在替它定形状等于替它做决定。
裁决还不存在，真库上这一态是 0 条。口子写在 `scope::decide` 的注释里。

## 挂账

新开 **D45**（自制内容的判据写在代码里，没进平台清单）、**D46**（去头那套按「尺寸说得通」
触发而不是一律解压）、**D47**（一个变体有好几条自动通过的候选时只挂优先级最高的那一条）、
**D48**（「没有发行版链接」这条判据在来路混着时会读错，见上）、**D49**（收紧去重判据：
这一层能给的判据和以为的不一样，原 D3 改判）。

## 四条已知限制

1. **GoodNES 这一层撞不到**（它不记 CRC-32），那 748 条汉化条目要等按 SHA-1 走的那一层。
2. **zst 与 rar 容器里的东西还看不见**（票 26 / 票 04），2,913 个变体因此无判据。
3. **压缩镜像、目录树转储、光盘序列号**这一层都认不了，等票 09。
4. **逐芯片的命中一条都不自动通过**：MAME 撞出 14,696 条候选、涉及 12,199 个变体，
   全部是中置信。对上一颗芯片不等于对上整次发行，等票 08 的裁决队列。

## 从挂账转来的前瞻

- **收紧去重判据（原 D3）**：票 01 的重复拷贝按「同名 + 同大小」判，零读盘。这票有了 CRC-32 与沉淀库之后，是收紧判据的时机。
- **增量的价值在这票显现（原 D14）**：票 02 的增量扫描没能把扫描本身提速（仍要遍历每个目录）。到这票，跳过未变文件省下的是 7.84 TiB 的 CRC-32 计算，接缝的价值才真正兑现。
