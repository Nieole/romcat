## 被推翻的判断

**街机不是第二大集合。** 资源站全站有 MAME 12,522 条，我据此说「街机条目数巨大、单位处理成本最低、优先级要往前提」。**这个库里街机只有 265 个文件、3.73 GiB。** 优先级判断作废。

**PSV 是文件数的绝对主导：171,073 个文件，占全库 67%**，但只有 1.64 TiB，且含汉字仅 0.5%。它是目录树转储，海量游戏内部资源文件。这是此前完全没有预料到的形态。

**容量最大的平台是 `pc`（2.72 TiB，792 文件），而 `pc` 不在议定的 27 平台清单里。** 同样 `switch`（223.84 GiB）也不在——它比 PS3 还晚一代。

**中文占比是 15.6% 而非资源站的 9%**，但两者口径不同（这里是文件名含汉字，那里是条目分类）。

## 并发：按介质探出来，不按 CPU 数猜

2026-09-01 实测（详见 `docs/research/scan-concurrency.md`）。测法是**两组不重叠的冷缓存
兄弟目录，一组串行一组并发，按目录/秒归一化后比**——同一组目录跑两次只会量到热缓存。

**同一块盘上，提高并发的效果按区域分，方向相反：**

| 区域 | 串行 目录/秒 | 16 线程 目录/秒 | 提速 |
|---|---|---|---|
| `Game/ps` | 8.7 | 40.9 | **4.71×** |
| `Game`（主库根） | 10.7 | 15.2 | **1.42×** |
| `Game/FC` | 42.7 | 36.0 | 0.84× |
| `Game/SFC` | 125.3 | 21.9 | **0.17×**（慢 5.9 倍） |

规律很干净：**串行就读得快的区域，并发一定亏**——目录项在盘上挨着，16 个线程等于把一次
顺序读拆成 16 股互相打断的随机读。

**主库根上量到 1.42 倍**，那是整趟全库扫描该用的样本。票 01 那个「按 CPU 数取，夹在 2 到 8」
的默认值（这台机器上取到 8）**没有依据**，现在由 `scan::probe` 开扫前量出来。

**表里的提速是实测，具体定几个线程是模型外推**：探测只量 1 线程与 16 线程两个点，「主库根上
4 个线程就够到 16 线程吞吐的九成」是把 1.42 倍代进一个饱和模型算的。**「旧默认 8 与新默认 4
哪个扫得快」这个实验做不成**——一个库只有一份，第二遍必然是热缓存。

## 识别：第一次看到真实命中率（2026-09-01，票 07）

拿 46,444 个变体去撞 395 份 DAT 的 481,106 条文件记录，判据是 **CRC-32 加未压缩大小**。

| | |
|---|---|
| 变体 | **46,444 个** |
| **命中** | **30,024** |
| 未命中 | 11,823 |
| 无判据 | 4,537（这一层拿不到判据，不是「DAT 里没有」） |
| 跳过 | 60（补丁 27 + 没有发行版链接 33） |
| **命中率** | **撞了 DAT 的里面 71.7%**（30,024 / 41,847）；**全部变体里 64.6%** |
| 候选 | 150,959 条，自动通过 136,238 条；**16,004 个变体有不止一条候选** |
| 三层 | 建出**作品** 9,226 个、**发行版** 18,571 个 |

**命中率有两个数，两个都得说。** 分母取「撞了 DAT 的」时它回答「这一层准不准」；
取全部变体时它回答「这个库现在被认出来多少」。**跳过与无判据不进第一个分母**——
把「不该撞 DAT 的」和「拿不到判据的」混进未命中，等于拿别的账压低这一层的准确率。

### 逐芯片的命中一条都不自动通过

MAME 的 software list 撞出 **14,696 条候选、涉及 12,199 个变体，自动通过 0 条**。
一条 `rom` 是**一颗芯片**（`prg` / `chr` 的一个 dataarea），不是一个文件——单芯片卡上它
恰好等于去头哈希，多芯片卡上「对上了一颗芯片」离「这个文件就是那次发行」还差着别的芯片。
所以它是**中置信**：通过但标记，等裁决（ADR-0002 的中置信那一档）。

## 第一次真实识别命中率（2026-09-01，票 07）

### NKit：验了 1,967 份，一份都不是

**NKit 是这一层最要紧的那道闸**（Dolphin：它的 CRC32 可能和好转储的相同，即使两个文件
并不完全一样）。判据是**光盘逻辑偏移** `0x200` 处的 `NKIT`。真机结果：

- **验过 1,967 份**（1,939 份未压缩镜像 + 28 份 CSO，那两种交得出逻辑偏移 `0x200`），
  **0 份是 NKit**。
- **另外 4,647 份没验**：WBFS 只交得出 256 字节的 Wii 光盘头、WIA/RVZ 只交得出 `0x80`
  字节，两种都够不到 `0x200`；CHD 与 GCZ 的负载解不开；solid 块太深的那 2,508 条壳都没开；
  `param.sfo` 与 NKit 无关。**没验过就不许自动通过**——这不是保守，是 Dolphin 那句话的
  直接推论。
- **这一层为了 NKit 多花了一笔**：撞上了 CRC 的内容本来不必再探（序列号是第二命中层），
  但「NKit 检测在任何 CRC 匹配之前执行」不许拿 CRC 的结果来决定验不验，所以凡是
  **形态上可能是 GC / Wii 光盘**的一律照探。代价是 1.69 → 1.93 GiB、183.5 → 232.4 秒。

「0 个」是一条结论不是一次落空：这块盘上没有 NKit 处理过的镜像，而闸门本身在 fixture
上有可断言的证据（`tests/disc_serial.rs`）。

### solid 块吃掉了 2,508 条

7z 的一个块里几个条目是连着压的，解压器跳不过中间的字节。真机上 **2,508 条**光盘形态的
内容排在 1.36–3.46 GiB 的东西后面，为它们付那笔解压等于把「只读几百字节」反过来做——
闸设在 64 MiB，超了就放弃并如实报（挂账 D109）。其中 **2,459 条是 PSV 的 `.7z`**，
多半是 DLC 目录里那份 `param.sfo`；本体那一份通常排得浅，所以 PSV 照样跳到了 94.1%。

### Redump 一条序列号都不写

实测：Redump 的官方 DAT 里 `<game>` 只有 `name` 与 `id`、`<rom>` 只有四套哈希。
于是 **PS2 / NGC / WII 三个平台读得出 `SLPS-25604` 与 `GALE01`，却无处可撞**——
它们的序列号弹药分别只有 178 / 58 / 27 条，全来自 No-Intro 的 Non-Redump 附集。
报告因此在平台表上单列「序列号」一列（挂账 D110）。

**序列号写在 `<rom serial>` 属性与 `<game_id>` 子元素上，不在 `<game serial>` 上。**
票 06 的解析器只读后者，于是 Vita 与 PSP 两个平台一条都读不到——补上这两处之后，
395 份 DAT 索引出 **95,022 条**序列号。

### 调参数：门槛从 0.72 提到 0.85，再加两道硬闸

这一层**可反复重跑调参数**（不重扫、不重新取数，一趟 65 秒），于是真的调了两轮。
判据是**人工抽样**：

|---|---|---|
| 门槛 0.72，只有相似度 | **17 / 25 = 68%** | 1 / 25 = 4% |
| 门槛 0.85 + 数字必须一致 + 不拿拉丁残片单独撞 | 11 / 25 = 44% | —— |
| 再加「**拉丁字母也必须一致**」 | **5 / 30 ≈ 17%** | **2 / 37 ≈ 5%** |

（最后一行是两轮抽样合起来的 67 条，逐条人眼核对；按真机上两档的实际条数加权约 8%。）

错法高度集中，两轮都一样：**续作编号与版本记号**。`第3次超级机器人大战` 撞上

### 编码探测：那批乱码名字

票 03 对非 UTF-8 的容器内部文件名按**有损转换**处理，理由是「识别靠 CRC-32、名字不参与
命中」。**到这一层名字开始参与了**，那批乱码就成了实打实的问题：真库 1,016,857 条内部
条目里有 **21,901 条**不是合法 UTF-8（FC 9,207、NDS 2,801、GBA 1,274、PSP 592、GB 427、
SFC 379），其中 `.nes` 4,670 条、`.gba` 691 条、`.smc` 409 条、`.gbc` 353 条——真的是 ROM。

`container::charset` 现在先探编码再解码：UTF-8 严格验一遍，不是就按 GBK / Big5 /
Shift_JIS 各解一次，**一个替换字符都不许出现**，再按「这串字节落在哪一区」打分
（GB2312 常用区 `B0`–`F7`、Big5 常用区 `A4`–`C6`、Shift_JIS 的假名区；而**半角片假名
倒扣分**——一串 GBK 汉字在 Shift_JIS 眼里正是一串半角片假名）。平局归 GBK。

单元测试用的是**真库里那四条名字的原始字节**（从 `FC/【HACK版游戏】/…/1.FC经典游戏/`
下面几个 zip 的中央目录里逐字节读出来）：`上海大亨.nes`、`圣斗士星矢2汉化.nes`、
`封神榜.nes`、`快打旋风.nes`，四条全部解对。**`上海大亨` 用 Big5 也解得出来**
（`奻漆湮箋`，一个替换字符都没有）——这正是「猜错会把一种乱码换成另一种」的样子，
也是判据不能是「解不解得出」的原因。

| 穿透 | **1,332 / 1,333**（99.9%），耗时 **195 秒** |
| 内部文件 | **203,586 个**（另有 8,115 条目录条目），未压缩 **562.55 GiB** |
| 带 CRC-32 | **174,785 个（85.9%）** —— 零解压就能拿去撞 DAT 的那一批 |
| solid 容器 | 82 个 |
| 要完整解压才认得出的容器 | **546 个**（一条 CRC-32 都没有，见下） |
| 名字有损 | **0 条** |
| 穿不透 | 1 个：`[SJ9E41]舞力全开2…-DL.rar`，`unrar` 自己也报 *Corrupt header is found* |

格式分布（1/7 抽样 191 份）：**RAR5 139 份、RAR4 52 份**——两种都得认，缺一种漏一大批。

### 与官方 `unrar` 逐条对照：150 份 / 16,809 条内部条目，零分歧

随机 150 份真库 rar，把本程序读出来的 `(名字, 未压缩大小, CRC-32, 是不是目录)`
与 `unrar lt` 的输出逐条比：**一致 150、不一致 0**。反向也验了一次——
把测试里手写的 RAR4 / RAR5 样本喂给官方 `unrar lt`，它读得出名字、大小与 CRC-32，
说明那些样本是真 rar，不是「只够骗过自己解析器」的字节。

### ⭐ 三处「字段还在、含义变了」的坑，每一处都不报错，只是撞不上

1. **分卷的非末段记的是打包后数据的校验和**（ADR-0014）。造一份三卷的 RAR5 实测：
   同一个文件三卷分别记 `DDFAE192` / `B31EA58F` / `9506C014`，只有末段那个等于
   未分卷时的 CRC；`unrar lt` 把前两个直接印成 **`Pack-CRC32`**。
2. **带密码时校验和被密钥搅过**（technote 的 *tweaked checksums*，`unrar lt` 印成
   **`CRC32 MAC`**）。**随机 60 份里有 20 份带密码**——三分之一，不是边角情形。
   实测造一份 `rar a -p123`：`a.txt` 真 CRC `A3EBCC66`，头里写的是 `D4ED1D67`。
   全库那 546 个「要完整解压才认得出」的容器就是这一批。
3. **只写 BLAKE2sp（`rar a -htb`）时一条 CRC-32 都没有**，而 No-Intro / Redump /
   TOSEC 一条 BLAKE2 都不记。

三条全部落到同一个处置上：**那一栏记 `None`，绝不拿它去撞 DAT**。

### 三种分卷形态，真库里各是什么样

| 形态 | 真库里有多少 | 入口段 |
|---|---|---|
| RAR 官方分卷（`.part1.rar` / `.rar` + `.r00`） | **0 组** | 第一卷 |
| 7-Zip 通用字节切分（`.7z.001`） | **1 组，且缺入口卷**：只有 `废都物语_资料合辑_220928.7z.006`，`.001`–`.005` 不在库里 | `.001` |
| ZIP 官方 split（`.z01`…`.zip`） | **4 组**（WIIU `XenobladeX-…-WUP`，每组 5 个文件约 20 GiB） | **最后那个 `.zip`** |

那 4 组 ZIP split **早就穿得透**——中央目录写在末段那个 `.zip` 里（APPNOTE §8.3.4
说末段用 `.zip` 扩展名正是为了这个），每组交出 **47 条内部条目**、未压缩 20.94 GB。
票 04 补的是另一半：`.z01`…`.z04` 不再各自算一个容器、各报一次「穿不透」，
而是与末段那个 `.zip` 合成**一个变体**（成型规则「分卷压缩」）。

### 命中率掉了 1.4 个点，而那是「不知道」变成了「知道」

同一个门槛（`--similarity 0.72`）前后各跑一趟识别：

| | 票 12 之后 | 票 04 之后 |
|---|---|---|
| 变体 | 46,444 | 46,428 |
| 命中 | 39,519（85.1%） | 38,860（**83.7%**） |
| 未命中 | 4,142 | **4,867** |
| 无判据 | 2,723 | 2,631；其中「rar 穿不透」**680 → 0** |
| 自动通过的候选 | 139,500 | **176,498（+36,998，基本全部来自 rar）** |

那 680 个 rar 变体此前**连撞都没撞过**——无判据不进命中率的分母（ADR-0002）。
现在它们真的撞了一次 DAT：**210 个变体撞上了**，其余撞不上——rar 里装的多是汉化版
与 HACK 版，**DAT 里本来就没有**。撞不上的那批从「无判据」落进「未命中」，
分母变大而分子没同比例变大，百分比就掉了。**未命中是一条结论，无判据不是。**

`identification.read_bytes` 对全部 rar 变体求和 = **0 字节**：203,586 个内部文件的
名字、大小与 CRC-32 全部来自头部，504 GiB 一个字节都没解。

另有 **225 个变体停在「容器没记这一条的 CRC-32」**——那是上面第 2 条那批带密码的
（校验和被密钥搅过）。它们**不是未命中**：工具知道自己手里那个数不能用来撞 DAT。

## Switch 免密钥识别（2026-09-03，票 27）

**一个密钥都没用。** Switch 的内容主体确实加密，但**容器层不加密**——PFS0（`.nsp` /
`.nsz`）与 HFS0（`.xci` / `.xcz`）的头、条目表与**字符串表**全是明文。这一趟证的就是
这件事在真库上成立。

### ⭐ 先补一个洞：`.nsz` / `.xcz` 此前连变体都不是

| | 票 04 之后 | 票 27 |
|---|---|---|
| `switch/` 下的**条目** | 205 | 同左 |
| 成型出来的**变体** | **91** | **146** |
| 其中 `.nsz` / `.xcz` | **0** | 55 |

`nsz` 与 `xcz` 两个扩展名不在 `classify::BARE_FILES` 里，于是那 55 个文件
（**74.67 GiB，Switch 容量的 33.4%**）压根没进过识别管线——不是「认不出」，是**从来
没被问过**。它们归**裸文件**：识别读它们的路子与 `.nsp` / `.xci` 一模一样（容器层完全
相同，压缩只改内部条目的扩展名 `.nca` → `.ncz`），而这个词表里「压缩镜像」的定义是
「模拟器直接读它」——**没有任何 Switch 模拟器读得了 `.nsz`**（词表缺口记在挂账 D146）。

**这个洞也正是票 7 那条验收此前传不过去的原因**：能力档案里 ES-DE 那一档票 21 就写好了
（`es-de` × SWITCH 只吃 `nsp / xci / nca / nro / nso`），传不到那里的不是信息，是**那些
文件根本不是变体**。补上之后链路自己就通了，有一条集成测试走完整条：扫描 → 成型 →
变体 → `capability::decide` 报 `Unsupported`。

### 认出了多少

同一份中立库的两份拷贝、同一个门槛（`--similarity 0.72`），基线跑的是 `e869566`：

### ⭐ 中文在这里是语言属性，不是独立发行版（ADR-0019）

第三方 TitleID 数据库（[blawar/titledb](https://github.com/blawar/titledb)，**MIT**，
每日推送，走票 06 那道取数闸门、`raw.githubusercontent.com` 本来就在白名单上）
取一次 **18 秒 / 276 MB**，第二次 `ETag` 没变、**5 秒整件跳过、零字节**：

| 文件 | 读出 |
|---|---:|
| `cnmts.json` | **173,639** 条 ContentId → (TitleID, 版本) |
| `US.en.json` / `JP.ja.json` / `HK.zh.json` / `CN.zh.json` | 29,416 / 27,061 / 17,260 / **89** |

**官中 9,141 个 TitleID，其中 5,971 个（65.3%）是多区共用的**——调研说的

| SWITCH 变体挂着的发行版 | 变体数 |
|---|---:|

| `Hong Kong`（**亚洲独占 SKU**，中文是它自己的地区 → **独立发行版**） | 11 |

### 文件名与容器的交叉印证：零冲突，而头一版报了 5 个假警

头一版按原样比 TitleID，真机报出 **5 条「文件名与容器对不上」**。逐条看过，**5 条全是
假警**，两种形状：

1. **文件名写的是本体的 TitleID（`…4000`），而卡里那张票据是它的补丁（`…4800`）**
   ——那正是一张「本体加更新」的卡该有的样子。判据改成先按**本体那一串**比
   （`Kind::base_of`：补丁清 `0x800`，附属内容清低 12 位再减 `0x1000`）。
2. **一份合集卡带的名字里写着两个 TitleID**（`Double Pack [0100D49020B84000]
   [0100E7C020B82000][v0].xci`），而卡里确实装着两个游戏。判据改成把文件名里**每一个**
   TitleID 都收下来逐个比。

改完 **0 条冲突**。这不是把警告调松了——真出事时那句警告才有人信，而一个把五张正常的卡
全报成「被改过」的检查，等于没有这个检查。同一份合集卡带还暴露了第二处硬伤：
「本体是 …」那一句取的是**容器里第一张票据**，于是两条候选里必有一条在撒谎；
改成取**这一条候选自己**的那一串。两处都有测试钉着。
