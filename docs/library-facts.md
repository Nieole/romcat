## 被推翻的判断

**街机不是第二大集合。** 资源站全站有 MAME 12,522 条，我据此说「街机条目数巨大、单位处理成本最低、优先级要往前提」。**这个库里街机只有 265 个文件、3.73 GiB。** 优先级判断作废。

**PSV 是文件数的绝对主导：171,073 个文件，占全库 67%**，但只有 1.64 TiB，且含汉字仅 0.5%。它是目录树转储，海量游戏内部资源文件。这是此前完全没有预料到的形态。

**容量最大的平台是 `pc`（2.72 TiB，792 文件），而 `pc` 不在议定的 27 平台清单里。** 同样 `switch`（223.84 GiB）也不在——它比 PS3 还晚一代。

**中文占比是 15.6% 而非资源站的 9%**，但两者口径不同（这里是文件名含汉字，那里是条目分类）。

## 并发：按介质探出来，不按 CPU 数猜

2026-09-01 实测（详见 `docs/research/scan-concurrency.md`）。测法是**两组不重叠的冷缓存
兄弟目录，一组串行一组并发，按目录/秒归一化后比**——同一组目录跑两次只会量到热缓存。

**同一块盘上，提高并发的效果按区域分，方向相反：**

| 区域 | 串行 目录/秒 | 16 线程 目录/秒 | 提速 |
|---|---|---|---|
| `Game/ps` | 8.7 | 40.9 | **4.71×** |
| `Game`（主库根） | 10.7 | 15.2 | **1.42×** |
| `Game/FC` | 42.7 | 36.0 | 0.84× |
| `Game/SFC` | 125.3 | 21.9 | **0.17×**（慢 5.9 倍） |

规律很干净：**串行就读得快的区域，并发一定亏**——目录项在盘上挨着，16 个线程等于把一次
顺序读拆成 16 股互相打断的随机读。

**主库根上量到 1.42 倍**，那是整趟全库扫描该用的样本。票 01 那个「按 CPU 数取，夹在 2 到 8」
的默认值（这台机器上取到 8）**没有依据**，现在由 `scan::probe` 开扫前量出来。

**表里的提速是实测，具体定几个线程是模型外推**：探测只量 1 线程与 16 线程两个点，「主库根上
4 个线程就够到 16 线程吞吐的九成」是把 1.42 倍代进一个饱和模型算的。**「旧默认 8 与新默认 4
哪个扫得快」这个实验做不成**——一个库只有一份，第二遍必然是热缓存。

## 识别：第一次看到真实命中率（2026-09-01，票 07）

拿 46,444 个变体去撞 395 份 DAT 的 481,106 条文件记录，判据是 **CRC-32 加未压缩大小**。

| | |
|---|---|
| 变体 | **46,444 个** |
| **命中** | **30,024** |
| 未命中 | 11,823 |
| 无判据 | 4,537（这一层拿不到判据，不是「DAT 里没有」） |
| 跳过 | 60（补丁 27 + 没有发行版链接 33） |
| **命中率** | **撞了 DAT 的里面 71.7%**（30,024 / 41,847）；**全部变体里 64.6%** |
| 候选 | 150,959 条，自动通过 136,238 条；**16,004 个变体有不止一条候选** |
| 三层 | 建出**作品** 9,226 个、**发行版** 18,571 个 |

**命中率有两个数，两个都得说。** 分母取「撞了 DAT 的」时它回答「这一层准不准」；
取全部变体时它回答「这个库现在被认出来多少」。**跳过与无判据不进第一个分母**——
把「不该撞 DAT 的」和「拿不到判据的」混进未命中，等于拿别的账压低这一层的准确率。

### 逐芯片的命中一条都不自动通过

MAME 的 software list 撞出 **14,696 条候选、涉及 12,199 个变体，自动通过 0 条**。
一条 `rom` 是**一颗芯片**（`prg` / `chr` 的一个 dataarea），不是一个文件——单芯片卡上它
恰好等于去头哈希，多芯片卡上「对上了一颗芯片」离「这个文件就是那次发行」还差着别的芯片。
所以它是**中置信**：通过但标记，等裁决（ADR-0002 的中置信那一档）。

汉化版数据源的实际规模比先前预期**小约一半**，这会影响票 10 对「靠 DAT 能覆盖多少汉化版」的预期。

## 第一次真实识别命中率（2026-09-01，票 07）

**30,024 个变体被 CRC-32 精确认出来。**

| 口径 | 命中率 |
|---|---|
| 有 DAT 弹药可撞的（30,024 / 41,847） | **71.7%** |
| 全部变体（30,024 / 46,444） | **64.6%** |

四类相加正好等于变体总数：命中 30,024 + 未命中 11,823 + 无判据 4,537 + 跳过 60（补丁 27、无发行版链接 33）。**「无判据」与「跳过」不算进未命中**——否则命中率虚低。

建出作品 9,226 个、发行版 18,571 个。候选 150,959 条，自动通过 136,238 条。

**性能**：首趟 832.9 秒，回盘只读 **9.04 GiB（全库的 0.1%）**——零解压读 CRC-32 这条路兑现了。第二趟 **7.9 秒、0 字节**（挂账 D14 说的「增量价值到票 07 才显现」，兑现）。

### 按平台：两个世界

| 平台 | 命中率 |
|---|---|
| GB | **91.5%** |
| FC | **82.8%** |
| SFC | **80.1%** |
| GBA | **5.8%** |
| NDS | **4.4%** |
| GBC | **0%** |

**与 ADR-0008 的预判一分不差**：GBA 与 NDS 是中文玩家存量最大的两个平台，却是汉化版数据覆盖最差的。抽样确认 GBA 的未命中全是宝可梦汉化版。

### 一个结构性事实

**汉化命中 1,064 个全部来自 TOSEC。GoodNES 那 748 条在这一层一条都撞不到——它只记 SHA-1，不记 CRC-32。** 要用上这个数据源，需要一个愿意为小文件付 SHA-1 的层（票 10）。

两套哈希都撞出了东西：含头 141,119 条候选、去头 9,840 条；12,388 条去头口径的记录里有 5,756 条是被含头哈希撞上的。

## 刮削：离线档第一次跑（2026-09-01，票 13）

**在识别结论上取元数据。整趟零网络请求。**

| | |
|---|---|
| 锚点 | **作品 9,226 个、变体 46,444 个**（合计 55,670 个采集单位） |
| 字段值 | **78,902 条** |
| 首趟耗时 | 元数据 **2.3 秒**；连媒体一起 **73.5 秒** |
| 第二趟 | **0.8 秒**，119,322 个「锚点 × 源」因为**输入指纹**没变整条跳过 |

### 按字段：多源合并有真东西可排

| 字段 | 有值的锚点 | 值 | 各源贡献 |
|---|---|---|---|
| 标题 | 55,670 | 65,630 | 文件名 46,444、No-Intro 6,945、TOSEC 6,800、MAME 5,076、Redump 365 |
| **年份** | 5,988 | 5,988 | **TOSEC 5,988**（别家一条都没有） |
| **发行商** | 6,512 | 6,512 | **TOSEC 6,512**（别家一条都没有） |
| **汉化组** | 772 | 772 | **TOSEC 772** |

**这张表就是「优先级必须按字段而不是按源」的证据。** 标题上 No-Intro 的条目名最整齐，
而**年份与发行商只有 TOSEC 给得出**——按源排的话，「No-Intro 优先」等于把它们一起丢掉。

`文件名` 那 46,444 条不是凑数：DAT 认不出来的 16,420 个变体，标题只能从文件名来，
否则前端里是一片空白。它排在优先级链的最后，DAT 说得出话时轮不到它。

**汉化组 772 条**少于识别报出的 1,064 个汉化命中，差的那些是 `[tr zh]` 没署名的条目——
空着比编一个名字强。

### 合并之后谁说了算

报告把优先级**真的合并了一遍**再数出来的，不是只算贡献：

| 字段 | 胜出 |
|---|---|
| 标题 | 文件名 46,444、**No-Intro 6,945**、TOSEC 1,869、Redump 351、MAME 61 |
| 年份 | TOSEC 5,988 |
| 发行商 | TOSEC 6,512 |
| 汉化组 | TOSEC 772 |

**TOSEC 贡献 6,800 条标题、胜出 1,869 条**——差的那 4,931 条是「同一个作品 No-Intro 也
说得上话」，链上排在前面的赢了。而那 1,869 条正是 No-Intro 沉默、TOSEC 接上的地方。
**这就是字段级 fallback 在真库上工作的样子**：不是「用 No-Intro」也不是「用 TOSEC」，
是逐个作品逐个字段地按链取。

MAME 贡献 5,076 条却只胜出 61 条：它排在链的第四位，而前面三家覆盖得比它全。
这一栏正是判断「某个源值不值得继续用」的依据。

### 离线档补不上的三样

**开发商、类型、简介**——本地数据源里没有。这不是漏了，是调研早就写明的结论
（Bangumi 的离线 dump 不含图片、Wikidata 只有标签没有简介）。**报告逐条点名**，
那正是票 14 存在的理由。

### 媒体：库里现成的图归得上 647 份

两条**保守**的归属规则：**同名兄弟**（`游戏.zip` 旁边的 `游戏.png`）与**独占目录**
（一个目录里只有一个变体）。目录里有两个以上变体就一张都不认——`FC/` 底下三千个 zip
挤在一起时，同目录的图属于谁根本说不清。

| | |
|---|---|
| 归得上的媒体 | **647 份**（涉及 230 个变体），全部收进来是 **10.04 GiB** |
| 这一趟（`--max-media-mib 32`） | 收进 **538 条引用 / 516 份内容**，1.60 GiB |
| **去重** | **23 次算出来发现池里已经有了**；**18 份被不止一个锚点引用** |
| 超上限跳过 | 108 份（**文件本身没问题**，与「读不动」是两件事，两个计数器分开） |
| 读不动 | 0 份 |

**「同一份媒体只存一份」是内容寻址天然给的**，不是另加的去重步骤：538 条引用落在
516 份内容上，差出来的 22 份就是省下来的。最大的一份是
`ps3/…/PS3阿修罗之怒[1.0.0汉化]/视频预览.mp4`，662 MiB。

**这些媒体恰恰落在在线源覆盖不到的汉化版上**——ScreenScraper 眼里它们正是「未识别
ROM」（ADR-0007），而它们的预览图与视频就躺在库里。

### 采集缓存：`--refresh` 重采一遍读盘 0 字节

`--refresh` 把 119,322 个「锚点 × 源」全部重采，**4.1 秒、回盘 0 字节**——
539 份媒体的内容哈希从中立库直接取回。重采的是结论，不是重读一遍盘。

### 上限进了输入指纹，调高它那些媒体真的会进来

**上限改变采集的结果，所以它必须进输入指纹。** 实测把 `--max-media-mib` 从 32 提到 64：

| | |
|---|---|
| 新收进来 | **53 份**（另有 2 次算出来发现池里已经有了） |
| 超上限的 | 从 108 份降到 **53 份** |
| 回盘读 | 2.44 GiB / 55 份；**其余 539 份的哈希从中立库直接取回** |
| 跳过的「锚点 × 源」 | 119,322 —— DAT 与文件名那几个源的指纹不含上限，一条都没重采 |

指纹里漏掉上限的话，这一趟会一口咬定「输入没变」而整条跳过，那 55 份永远收不进来，
只有整份 `--refresh` 才逃得掉。反过来调低上限也一样：此前收进来的那些会被挡在外面。
