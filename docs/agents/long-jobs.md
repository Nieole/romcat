# 长活与回执

一件活跑得比一次工具调用久、或者交给别人去跑（门禁、审查）时，怎么跑，日志落在哪儿，以及怎么判断手上那份回执是不是在骗你。

## 回执会骗人，根在仓库外

这里的几样工具都住在仓库之外：审查技能、Bash 工具的后台运行、派出去的 subagent。这个仓库改不掉它们（挂单 `Q365`）。
它们出毛病时交回来的不是一句报错，是**一份看起来正常的回执**：格式齐全、条目像样，只是审的、跑的不是你那棵树，或者只剩一截。

仓库里做得了的是防法那一半。下面每一节都是**一句判据，加上怎么核、怎么防**。

## 先核对你站在哪棵树上

**判据：你在哪棵树上，由一条命令当场答，不由提示词说了算。**

派出去的 subagent 起跑时站在主工作区，不在它的 worktree 里；提示词里写「你在 X 里干活」挪不动它
（2026-09-13 实测，第五轮队列）。站错了也不报错：`git status`、审查、门禁都照样跑得通，只是跑在别的树上。

门禁尤其如此：`cargo xtask` 是 `cargo run --quiet --package xtask --` 的别名（`.cargo/config.toml`），
门禁的仓库根从编出 xtask 的那份清单折出来（`xtask/src/main.rs` 的 `repo_root`）。
**站在主工作区敲 `cargo xtask gate`，门禁的就是 `main`**，编译产物也写进主工作区的 `target/`。

防法：

- 每条 git 命令带 `git -C <worktree 绝对路径>`；读写文件一律用绝对路径。
- **开工前、每次调技能前**核对这两条，回答要逐字对上。任何一条对不上或没有回答：停下，不要「先干着」。

  ```sh
  git -C <worktree> rev-parse --show-toplevel   # 得是 <worktree>
  git -C <worktree> branch --show-current       # 得是你的分支
  ```

- 非 git 的命令（cargo）把 `cd <worktree> &&` 写进同一条命令里，并让它把 `pwd` 与分支名印进日志的开头（见「跑门禁」）。

## 派审查

**判据：`它报的审查范围里得出现你改过的那十几个文件`**

`/code-review` 起的子 agent 继承的是起始目录（主工作区），不是你干活的 worktree。它于是报「工作区干净」
或「`git diff HEAD` 是空的」，转去审主工作区上一个提交，交回一份与你的 diff 一条都不沾的回执。
第三轮至少咬了两次（挂单 `Q222`、`Q288`）。

**派之前，自己先取一份改动清单**，不从回执里取：

```sh
git -C <worktree> diff --name-only <基点提交>            # 已提交加未提交的改动
git -C <worktree> ls-files --others --exclude-standard   # 还没 add 的新文件
```

**派的时候**：同一条消息里交给它 worktree 的绝对路径与基点提交，并写明「review 只读，工作树归实现者」。

**回执回来，拿清单逐个对**——这就是「这份回执审的是不是我这个工作区」的验法：

- 清单里的文件都得出现在它报的审查范围里。缺一两个就问它为什么没审；缺一大半就是审错了地方。
- 回执里出现「工作区干净」「diff 是空的」「HEAD 就是 main」这类句子：**审错了**，不管后面的发现看起来多像回事。
- 它引的文件与行号落在你的清单之外：同上。

**审错了怎么办**：整份作废，不按「部分有效」采信。自己派两个只读 agent 各审一轴（Standards / Spec），
提示里写死 worktree 的绝对路径与 `git -C <worktree>` 的取法，再写死禁令：不许 `checkout` / `restore` /
`reset` / `stash` / `clean`，不许改文件，不许跑 `cargo`，不许进别的 worktree。
这条补救**是必须的，不是保险**：`Q288` 那一趟重审抓出两条高。

审错的那份回执里若有真问题，那是主工作区的问题：记成挂单的「路过发现」（`Q289` 就是这么来的），
不算你这张票过了审查。

## 跑门禁

**判据：`回执里那份输出不是完整日志，不能拿它的短小当「没跑过」的证据`**

实测（挂单 `Q373`，2026-09-09）：同一趟门禁，工具回执里那份输出 **42 行 / 3.7 KB**、零个 `Running`、
零个 `Compiling`；自己写的日志 **2,233 行 / 145 KB**，全绿。据前者判定「它压根没跑过」，
白重跑了一趟、约十一分钟。

成因：Bash 工具前台一次最多等 600 秒，超了转后台，而门禁一趟常常比这久（`Q373` 那次量的是 8～11 分钟）；
转了后台之后，回执那份输出只留尾部。门禁每一步的 stdout 与 stderr 都直通出来（`xtask/src/gate.rs` 的 `run`），真跑一趟必然印出成片的 `Compiling` 与 `Running`
——**它们在你自己的日志里，不在回执里。**

### 日志落在哪儿

- **仓库外、几个 worktree 共用的一个目录**：不进树，也不放 `target/`（`cargo clean` 与拆 worktree 会连日志一起带走，
  编排的人复核时就没了）。本机第五轮队列用的是 `/Users/nicoer/dev/game-wt/logs/`，文件名 `<槽位或票>-<哪一趟>.log`。
- 票里写证据时**抄数字**：`EXIT=` 那一行、门禁的汇总表、红的是哪一条。路径只作指路——日志不进 git，数字进。

### 可照抄的办法

**起跑**：`nohup … &` 让它活过这次工具调用；日志写到自己的文件里，开头印出站在哪棵树上，最后一行印退出码，pid 当场印回来。

```sh
nohup sh -c '{ cd <worktree> && pwd && git branch --show-current && cargo xtask gate --keep-going; echo "EXIT=$?"; } > <日志> 2>&1' > /dev/null 2>&1 & echo "pid=$!"
```

`--keep-going` 让一趟看全门禁每一条；不给就在第一处红上停。几个 worktree 同时跑时按机器分资源，开关见 `cargo xtask gate --help`。

**等**：在前台分段阻塞着等，每一段都短于前台上限。

```sh
for i in $(seq 100); do tail -n 1 <日志> | grep -q '^EXIT=' && break; sleep 5; done; tail -n 1 <日志>
```

一段约 500 秒，调用时把 Bash 工具的 `timeout` 给到 `600000`（默认只等两分钟）。回来是 `EXIT=` 就去读回执，不是就再发一段。

⚠️ **`Q373` 用的那套（GNU 工具）在这台机器上照抄不得**：`setsid nohup` 加 `timeout 560 tail --pid=…`。
本机 macOS 15.7 没有 `setsid`、没有 `timeout`，`tail` 也不认 `--pid`（2026-09-13 实测）。
上面这套在本机实测过（2026-09-13），用到的只有 `nohup` `sh` `tail` `grep` `seq`。

### 你是 subagent 时

用 Bash 的 `run_in_background` 起的长跑，结束的提醒**叫不醒派出去的 subagent**（2026-09-13 实测，
第五轮队列两张票各撞一次）：它返回去等提醒，提醒来了没人接，编排的人得自己盯日志的 `EXIT=` 行、再发消息叫醒它。

防法：**subagent 不靠提醒等**，照上面分段在前台等到 `EXIT=` 再往下走。实在要先返回，
返回里写明日志的绝对路径和「看最后一行 `EXIT=`」——把等的义务明写着交到读回执的人手上。

## 读回执

**判据：结果按日志最后一行 `EXIT=` 读。没有这一行，就是被截断了或还没跑完，不是红，也不是绿。**

- **日志开头那两行**得是你的 worktree 与你的分支。对不上，就是门禁了别的树，整份作废。
- **`EXIT=0`**：再看汇总表（「── 门禁 ──」底下那几行）是不是每一条都在、都是「绿」。
- **`EXIT=` 非零**：汇总表里没列出来的那几条**没跑**，不是绿。门禁默认在第一处红上停，会印「还有 N 条没跑」。
- **没有 `EXIT=`**：别据此重跑。先看进程还在不在（`ps -p <起跑时印回来的 pid>`）、日志还在不在长。

**`test` 红了一条，不等于其余都绿。** 门禁 `test` 那一步不带 `--no-fail-fast`（`xtask/src/gate.rs` 的 `test`），
cargo 在**第一个红的测试二进制**上就停，排在后面的测试二进制一条没跑。实测（2026-09-13，第五轮队列）：
票 `no-mute-spots-opening-a-catalog/01` 那一趟停在 `romcat-core` 的 lib 上，后面的核心库集成测试、界面测试、
xtask 测试都没跑到。要知道其余的，另跑一趟 `cargo test --workspace --all-features --no-fail-fast`，
或者把改动涉及的测试目标逐个跑；写证据时说明是哪一种。

**本机 `main` 上本来就红的那几条**：默认 APFS（不分大小写）上，几条真盘测试在 `main` 上就红，与你的改动无关。
怎么处置还没裁，见挂单 `Q479`。裁之前别把哪一种绕法当规矩写进票或代码，证据里照实写「红的是 `Q479` 那几条」。

## `#[ignore]` 只挂要人主动跑、跑起来很贵的东西

**判据：`#[ignore]` 只挂要人主动跑、且跑起来很贵的东西，不挂暂时红着的测试——那种要么修，要么删。**

`#[ignore]` 的测试门禁一条都不跑（`xtask/src/gate.rs` 的 `test` 不带 `--ignored`），平常的 `cargo test` 也只把它们记成 `ignored`。
拿它挂起一条红着的测试，等于把「这里坏了」藏进一个没人会去跑的地方：门禁照绿，下一个人读到那条测试，以为那件行为有人钉着。

仓库里头一批 `#[ignore]` 是两条**量级测量**（票 `machine-checks-premises/06`，2026-09-13）：`crates/core/tests/magnitude.rs` 里的整理标题与导出。
它们**不断言耗时**，印的是「一趟多少毫秒、折算到真库是几秒、比一帧的预算差几个数量级」——那是给人读的，不是红绿。

挂之前核三条：

- **说得出为什么要人主动跑。** 头一批那两条交出来的是一份给人读的量级报告，不是红绿——门禁跑它们什么都拿不回来。
- **说得出贵在哪。** 头一批那两条要各造一份几千个变体的库、跑一遍扫描识别刮削，`-- --ignored` 一趟 6–18 秒（debug，2026-09-13 与 14 日三趟，机器越忙越久）；
  放进门禁，每一次 push 都付这笔钱。说不出贵在哪，就不该挂（这一条头一批站得不稳，见挂单 `Q533`）。
- **理由写在属性上**：`#[ignore = "…"]`，理由里带上怎么跑。量级测量放自己的测试文件，不混进主题测试文件——混进去读者会以为它们在验行为。

跑法：

```sh
cargo test -p romcat-core --test magnitude -- --ignored
```

`-- --ignored` 只跑挂着的那些，`-- --include-ignored` 连平常的一起跑。量耗时的时候别和门禁、别的 worktree 抢机器：
数会偏，量级多半不变——写证据时照实写那一趟机器忙不忙。

撞见一条暂时红着的测试想先挂起：**不挂**。修得了就修；修不了、而那件行为确实还要，就删掉测试，
在提交说明里写清它原先钉着什么，再记一条挂单。
