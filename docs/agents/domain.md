# 领域文档

工程技能探索这个仓库时，怎么消费它的领域文档。

## 动手前先读

- 根目录的 `CONTEXT.md` —— 这个项目的词表
- `docs/adr/` 里与你要动的区域相关的决策记录

**每条 ADR 读到底。** 有些 ADR 末尾带「修订」段，那是后来的调研推翻了开头的判断——只读开头会拿到已经作废的结论去干活。

## 用词表的词

输出里凡是提到领域概念——工单标题、测试名、方案里的名词——用 `CONTEXT.md` 里定的那个词。词表给每个术语列了 `_Avoid_`，那些是要绕开的同义词。

要用的概念词表里没有，这是个信号：要么你在发明这个项目不用的语言（重新想），要么是真缺口（记下来交给 `/domain-modeling`）。

## 文档与代码互顶时，文档是决定

撞见「词表／ADR 逐字说了一件事，而代码做的是另一件」——**不许放着不管，也不许当没看见。**
这不是假想：第四轮收口在长期挂账里数出**十一条有代码在催**的，其中三条正是这个形状
（词表列着一个代码断言不存在的维度、两份文档对同一件事各说一句、一份结构化的判断
被另一层降级成 parse 字符串）。

规矩：**ADR 与词表是决定，代码跟着改。**

⚠️ **但「跟着改」不等于「照着实现」。** 顶不动的时候，正确的做法是**改 ADR 或词表本身**
——把那半句删掉、或者改成今天真的成立的话。硬造一个实现去圆一句过时的文档，是把一条
矛盾换成两条。

**这条通则管的是「不许放着两句互相顶的话」，不是「文档说什么就实现什么」。**
两条路都走得通时，说清你选了哪条、为什么。

## 与 ADR 冲突就说出来

你的输出与某条 ADR 相悖时，明说：

> _与 ADR-0004（主库只读）相悖，但值得重开，因为……_
