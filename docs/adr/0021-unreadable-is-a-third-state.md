# 读不到元数据的文件是第三态，且禁止改用 getattrlistbulk 提速

实测确认库里有 **4,085 个文件（1.59%）**在 macOS 的 fskit NTFS 驱动下读不到元数据（`Operation not supported`，errno 45）。比先前估的「约 1%」更多，而且比预想更彻底：**`stat` / `lstat` / `open` / `read` 全部失败，只有 `readdir` 有效**——文件名拿得到，其余一无所知。

## 决定一：三态而非两态

扫描对每个条目产出三种结论：**未变 / 已变 / 不可读**。

不可读**既不判为已变**（否则每次扫描都重扫这 4,085 个，永远无法收敛），**也不判为已删**（否则会从库里消失，而它们在 Windows 上是正常文件）。它是一个如实记录的状态，报告里单独计数。

## 决定二：`read_dir` 不许换成 `getattrlistbulk`

`getattrlistbulk` 是 macOS 上批量取目录项元数据的接口，比逐个 `stat` 快得多，是将来给扫描提速时最自然的第一选择。

**但实测它根本不列出这批文件——23 个受影响文件里列出 0 个。**

于是这批文件会从「读不到」**变成「不存在」**，而扫描把不存在解释为已删除。一次提速改动会静默地让 4,085 个文件从库里消失。这个陷阱在代码里完全看不出来——`getattrlistbulk` 会成功返回，只是少了东西。

因此 `crates/core/src/fs/real.rs` 的 `read_dir` 实现处必须写明这条禁令与理由。

## Consequences

- `DirEntry` 的大小字段在元数据读不到时不能落到 `0`——库里有 **4,317 个真正的空文件**，两者会混淆。大小必须是「未知」而不是「零」。
- 这 4,085 个文件在 Windows 上是否正常、以及它们是否带 NTFS `Compressed` 属性，是票 28 要验证的事项之一。

## 修订：这条推广到**开场**那一屏（2026-09-10）

上面那条决定说的是**扫描**：读不到元数据的文件既不判为已变、也不判为已删，
**它是一个如实记录的状态**。这条论证与「文件」没有关系——它讲的是
**把可分辨的失败压成同一样东西，人就会走错下一步**。

**开场**那一屏在两处犯了同一个错（原挂单 `Q388` / `Q393`）：

1. **列举一个工作目录时**，那个目录**读不动**与它**里头没有库**交出来是同一样东西
   （读不动就当空的交出去）。于是屏上说「还没有库，认领一个主库开始」——
   **而正确的下一步完全不同**：去修那个目录的权限，别去建第二份库。
2. **列举每一份中立库时**，打不开的原因被压成一句话，于是**结构版本对不上**（删掉重扫就好）
   与**文件坏了**（那是另一回事）分不开。

**因此：开场的列举要产出说得出原因的状态，不是「有」与「没有」两态。**

- 对**目录**：有库 ／ 空的 ／ **读不动**。
- 对**每一份中立库**：开得了 ／ **结构版本对不上** ／ **文件坏了**。

判据与上面那条一字不改：**一个如实记录的状态，胜过一个把两件事说成一件的沉默。**
屏上要说得出是哪一种，因为人对这三种的下一步动作各不相同。
