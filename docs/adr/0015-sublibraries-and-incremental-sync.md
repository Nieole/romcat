# 主库是仓储，游玩发生在派生子库；导出是同步而非写文件

用户从不直接在 10T 主库上游玩，而是挑选一部分导出到掌机等目标设备上的子库。这重构了产品形态：工具是「一个主库 + 若干派生子库的发布管线」。

## 三个连锁后果

**格式转换的位置从主库整理移到导出管线。** 目标设备的模拟器吃什么，导出时就转成什么；主库一个字节不动。这彻底化解了 ADR-0004（主库只读）与「需要支持 rar」之间的张力，而且比转换主库更好——同一个游戏导到不同掌机可以是不同格式，主库始终保持原始形态。用户明确表示不关心 RetroArch 是否支持 rar，正是因为主库从不被直接运行。

**「选择」成为一等公民。** 原模型里只有作品、发行版、变体，没有「这批游戏」这个概念。现在需要**子库**：持久实体，带选择集、目标路径、前端格式、格式转换规则、容量上限，以及**上次导出的清单**。没有清单就没有增量。

**导出从写文件变成同步。** 三方对比再次出现，对象从元数据文件变成整个子库：主库该有的 / 清单记录的 / 目标上实际有的。

## 目标设备上的写权限

完整同步（新增 + 更新 + 删除），目标严格镜像选择集。但有一条不可动摇的约束：

**只删清单里记录过的、由工具自己导出的文件。** 用户手动拷进 SD 卡的东西、模拟器存档、金手指、截图——工具连看都不看。清单之外的一切文件对工具不存在。

- 删除前必须干跑预览列出清单。
- 目标上的意外变化（清单说有、实际没了）报告给用户而非静默补回——那可能是用户有意删的。

## 目标设备的连接方式：取卡走读卡器

用户确认只用读卡器（SD 卡挂载成普通盘），不用 MTP、不用网络、不用本地中转。这是唯一能让工具**验证目标真实状态**的方式——MTP 上 stat 极贵、无随机访问，只能盲信清单，「报告目标上的意外变化」将无法实现。

因此同步可以实现完整的三方对比，包括目标侧的实际扫描与校验，不必退化为纯清单驱动。

## 子库内一律使用相对路径

导出到子库的元数据中，ROM 与媒体路径一律相对于子库根目录。卡插到不同设备、挂载点变化、盘符变化都不受影响。绝不写入主库的绝对路径。
