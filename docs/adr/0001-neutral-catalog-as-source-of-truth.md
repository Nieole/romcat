# 以中立库为事实来源，Pegasus 文件降级为导入源/导出目标

工具要同时做三件事：ROM 刮削（需要持久化置信度、来源、待人工确认状态）、多前端元数据互转（需要一个能同时表达 Pegasus / ES-DE / LaunchBox 等格式的中立模型）、10T 级库的 GUI 浏览（需要索引查询）。这三件事 `metadata.pegasus.txt` 都表达不了，因此事实来源放在中立库（SQLite），Pegasus 文件退化为众多导入源/导出目标之一。

## Considered Options

- **Pegasus 文件为准，库只做派生缓存**：好处是不存在"两份真相"，用户随时可手改、可删库重建。但刮削的置信度/来源/待确认状态无处安放（只能塞 `x-*` 扩展键或 sidecar），且互转退化为"文件→文件"的点对点转换，N 个格式要写 N² 个转换器。
- **库为准，单向全量覆盖导出**：最简单，但用户在工具外手改的内容会被静默吞掉。用户的 Pegasus 文件是多年手工养出来的，这个代价不可接受。

## Consequences

- 导出**不是**覆盖写，而是三方合并：对比「上次导出快照 / 当前磁盘文件 / 库」，检测到外部手改时弹冲突让用户裁决。为此必须持久化每次导出的快照。
- 导入必须无损：中立模型表达不了的原始内容（未知键、`x-*` 扩展键、注释、字段顺序）要原样留存，导出时还原，否则一次往返就会蒸发用户数据。

## 修订：三方合并降级为改动检测

产品形态在后续访谈中变了（见 ADR-0015）：主库是仓储，用户从不在上面游玩，游玩发生在导出到掌机的子库；而子库的元数据由工具全权生成，用户不会跑到 SD 卡上手改 `gamelist.xml`。**字段级三方合并的唯一存在理由，是「主库的 Pegasus 文件用户还会手改」——而用户确认不会了。**

修订后的定位：

- **一次性导入用户多年手工维护的成果仍必须无损**，这条不变，也是本 ADR 最初的核心动机。
- **主库仍导出标准 Pegasus 元数据**，理由是防锁定（工具哪天不维护了用户不被困住）以及能用 Pegasus 浏览主库。
- **所有编辑收敛到工具内**。工具仍会检测外部改动并警告用户（防止手改成果被静默吞掉），但**不再实现字段级三方合并**。
- 子库侧不需要元数据合并，只需 ADR-0015 的文件级清单对比。

导入时保留未知键、`x-*` 扩展键、注释与字段顺序的要求依然成立——那是无损导入的前提，与合并无关。
