# 识别结论分置信度等级，人工裁决队列是核心工作流

库里以汉化版为主，而汉化补丁改动了字节，精确哈希与 No-Intro/Redump 对不上——识别链条里最可靠的一环对主力内容结构性失效。因此识别不产出"是/否"，而产出带置信度的候选：高置信（精确哈希、光盘内部序列号命中）自动通过；中置信（内部头与文件名互相印证）通过但标记；低置信与模型推断结论进待确认队列，由人工批量裁决后才写入中立库。

## Consequences

- GUI 的主界面是这个待确认队列，不是游戏封面墙。封面墙是次要视图。
- 队列必须支持批量裁决（按目录、按候选作品、按汉化组命名规律一次套用几百条）。只能逐条点的队列在几千条规模下等于没有，整个方案会退化成"全自动瞎填"。
- 每条识别结论都要持久化它的**依据**（命中了哪个数据库的哪条、匹配了哪个字段），否则事后无法判断一条元数据是可信的还是模型编的。

## 修订（据识别技术调研结论）

「汉化版哈希必然对不上」是错的，应修正为「对不上 No-Intro/Redump，但存在专门的汉化版哈希源」：

- TOSEC 官方命名规范定义 `[tr zh <译者>]`，libretro 的 TOSEC 镜像中有 960 条中文汉化条目（FC 722、MD 86、GB 74、SFC 48、GBA 26、GBC 4），带完整 CRC32/MD5/SHA1。
- BizHawk 附带的 GoodNES 另有 646 条 `[T+Chi]` NES 条目与 MD 172 条。
- Hasheous 提供免费、无需 API key 的哈希查询，实测汉化 NES 与 SNES ROM 均能命中。

**关键实现约束：No-Intro 按去头哈希，TOSEC 按含头原样哈希。必须同时计算两套哈希**，否则全部 TOSEC 汉化条目都会漏掉。

「结构指纹 / 分段模糊哈希」这条路没有先例支撑：ROM 领域不存在模糊哈希的既有实践，且 ssdeep 在文件扩容超过 2 倍时失效，而汉化版扩容很常见。它是原创研究而非可借鉴工程，不应放进 v1 的关键路径。

## 再修订：第一命中层是 CRC-32 + 大小，不是 SHA-1

压缩容器调研确认：ZIP / 7z / RAR 的元数据里只有 CRC-32，零解压可得；而 DAT 每条 `<rom>` 都带 `size` + `crc`。因此置信度最高的那一层用 **CRC-32 + 未压缩大小**匹配，覆盖库中绝大部分归档内容且无需解压。

SHA-1 只在必要时下沉使用——GoodNES 的 646 条 NES 汉化条目以 SHA-1 为键，但 NES ROM 体积极小，对这一类文件解压计算完全可接受。**按文件体积决定解压深度**：小文件（卡带类）可完整解压算全套哈希，大文件（光盘镜像）只读容器元数据加前部几百字节的内部标识。
