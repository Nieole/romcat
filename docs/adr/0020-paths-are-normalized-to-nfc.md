# 路径以 NFC 规范化后才能作为键

增量扫描以 `(路径, 大小, 修改时间)` 为键。实测发现**路径这一侧存在跨平台断点**——而这正是当初派人去查修改时间精度时意外撞见的，修改时间本身反而完全没问题。

**macOS 的 NTFS 驱动把文件名规范化成 NFD 后才交给 `readdir`。** 证据是「原始字节对驱动输出」：`.tar.zst` 的 tar 头里成员名是 NFC，同一个字符串经 `readdir` 出来是 NFD——12 个归档 16 处比对，**16/16 如此，反例 0**；全库 40,650 个名字里含预组合浊音假名的有 **0 个**；字节级确认返回 `E3 82 99`（U+3099 组合浊音符）。

**实测受影响 1.99% 的路径**（除日文假名外还包括拉丁重音符 U+0301），其中有 **5 个是目录名**——一个目录中招，整棵子树的路径键全变。

不做规范化的后果：盘在 macOS 与 Windows 之间来回接一次，约 5,100 个文件被判为新文件重扫一遍。而 ADR-0018 定的工作方式正是两台机器轮流碰同一块盘，所以这是主路径不是边缘情况。

## 决定

**路径在进入中立库之前一律规范化为 NFC**，比较、存储、增量判断都用规范化后的形式。

键还要再做两件事，理由与 NFC 同源：**相对扫描根**、**分隔符统一成 `/`**。存绝对路径的话，换一次挂载点或把盘从 Windows 接到 macOS，**全库**都会被判成新文件——比 NFC 要防的那 5,100 个还糟。三件事合起来才构成一个跨平台稳定的键。

## Consequences

- 中立库里存的路径与 `readdir` 直接给出的字节可能不同。**读盘时要用系统给的原始形式，入库与比较时用 NFC 形式**——两者不能混用。
- **导出到前端时写哪种形式，需要单独验证**：前端与目标文件系统对规范化的敏感度不一，本次未测。这条不阻塞增量扫描，但在票 16、17 落地导出时必须回答。
- 规范化只解决**表示形式**的差异，不解决大小写等其他等价问题。Windows 侧的实际形式待验证（见票 28）。

## 一条方法论

这次结论靠的是「**找一个不经驱动的原始字节参照**」：归档内部存的成员名、回收站 `$I` 文件里存的 FILETIME。同样的手法也排除了时区偏差的嫌疑（回收站 FILETIME 与 fskit 报出的 mtime **12/12 吻合，差 0.4–31.6 毫秒，0 例 ±8 小时**）。凡是怀疑「驱动做了什么手脚」，都该先找这样一个参照，而不是拿两个都经过驱动的值互比。

## 修订：子库的目标路径两份都存；查找的分解敏感性实测

票 20 第一次真的往目标设备上写文件，两件事因此有了答案。

**子库的目标路径在 `sublibrary` 表上存两列**（挂账 D82 的工头裁决）：`target` 是 NFC 的那一份（当键、进报告），`target_raw` 是系统交出来的原始那一份（读盘走它）。只存 NFC 一份的话，目标目录名是分解形式、又挂在**分解敏感**的文件系统上时，`canonicalize` 会失败然后被报成「目标不在位」——而那是这条链路上最不该说的谎：卡明明插着。原方案的论证依赖「APFS 与 NTFS 都不分解敏感」，但**真正的目标是 SD 卡（exFAT / FAT32），那一侧的规范化行为没人查过**，而 ADR-0018 定的工作流里卡才是最终落点。

**macOS 的 fskit NTFS 驱动，查找这一侧不分解敏感。** 实测：库里 200,000 个文件键中有 383 个的 NFC 与 NFD 形式不同，逐个用两种形式去 `stat`，**383/383 两种都开得了**。也就是说驱动只在 `readdir` 的**输出**上做了分解（本文开头那一段），查找时两种形式都认。

这条实测不构成「可以混用」的许可，只是说明主库那一侧眼下走不到那个坑。因此仍然保留一道兜底：`fs::real_path` 把一个 NFC 的键还原成盘上真实存在的那条路径——**先原样试一次**（98% 的路径与不分解敏感的文件系统都一次就中，不花额外系统调用），**打不开才逐段列目录按 NFC 折过去认**。

**导出到前端写哪种形式，这里答一半。** 子库里工具**自己起名**的那些文件（媒体、元数据）一律按 NFC 的键写下去——名字是我们选的，选 NFC 就没有第二种形式。而回头去**读**目标上的文件（核对、删除、覆盖）一律走 `fs::real_path`：写下去的名字被文件系统存成什么形式不由我们说了算（HFS+ 就会存成 NFD）。另一半——把元数据交给别的前端时它怎么解释这些路径——仍然待验。

## 修订：键的第一段是**根名**——主库变成一组根

上面写的「相对扫描根、分隔符统一成 `/`、再规范化成 NFC」三件事一件都没变，但**前面
多了一段**：主库不再是一个目录，是**一组根**（`CONTEXT.md` 的**根**词条），于是中立库
的键是「**根名** + `/` + 相对那个根的路径」（`path::library_key`）。

**为什么非加不可。** 用户手上两块盘（一块 10 TB 无元数据、一块约 3 TB 有元数据）要统一
管理。只按相对路径当键的话，两块盘上同名的 `FC/魂斗罗.zip` 是**同一条记录**——一条静默
覆盖另一条，而中立库是事实来源（ADR-0001）。这不是「少几个文件」，是事实来源在说谎。

**为什么进键里而不是另起一列。** 中立库里有二十来张表以「条目的键」或「变体的键」当
主键或外键，**沉淀库**的**路径锚**是 `(主库名, 变体的键)` 那一对。键拆成两列的话这些
全要改，连不可再生的沉淀库都要动结构。而「键是一串不透明的文本」这件事除了「取平台
目录」与「取文件名」之外没人依赖——把根名放进第一段，改的只有 `crate::path` 里拆键的
那几个函数。

**NFC 这一条照旧管到根名头上。** 根名是用户敲进来的，而同一个名字在 macOS 与 Windows
上敲出来可能一个 NFD 一个 NFC；不折一下，「元数据库」这个根在两台机器上就是两个根，
全库重扫一遍。`path::root_name` 因此去两头空白、挡掉 `/` 与 `\` 与控制字符、再折成 NFC。
拼接**不会破坏 NFC**：中间那个 `/` 不参与任何组合，两侧各自已经是 NFC。

**这一次的代价落在两处，都写明白了：**

- **中立库结构版本 5 → 6**，旧库打不开，删库重扫。中立库整份可再生，这是它当初就
  付过账的便宜买卖。
- **沉淀库里的路径锚全部失效**：`variant_key` 存的是旧形状，从此撞不上。那些行
  **原样留着**，一条不删不改（`verdict` 的模块文档写清了为什么不能猜）。
  **内容锚一条都不受影响**——它钉的是那份字节，与文件躺在哪块盘上无关。

**导出到前端写的仍是不带根名的那一份。** `file:` 是给前端看的路径，相对元数据文件所在
目录解析；子库里的落点同理（前端认平台靠的是顶层那一级目录，ADR-0013）。机器读的那一半
（`x-romcat-variant`）**带着根名**：它要精确对回中立库里那个变体，而两块盘上同名的东西
只靠相对路径分不开。
