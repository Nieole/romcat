# 平台目录是强先验而非权威，Platform 与 Collection 保持正交

用户的资源已按平台分好目录，因此平台是扫描的**输入**而非输出：成型规则按目录直接分派，不需要先从扩展名和魔数猜平台。目录名到平台的映射由工具推测、用户确认一次即可。

但目录声明必须能被文件内容推翻——目录说 GBA、文件头说 NDS 是真实会发生的（下错、放错、压缩包混装）。这类冲突不是错误而是**库体检最该报告的产出之一**。

## Consequences

- 库体检的定位随之改变：不再是「猜平台」，而是「验证目录声明与文件实际内容是否一致」加上分布统计。
- **Platform 与 Collection 必须保持正交**。在用户当前的库里「目录 = 平台 = Pegasus 的 collection」三者恰好重合，但模型里绝不能把它们捏成一个——否则「我通关过的」「适合双人玩的」这类跨平台合集将永远无法表达。

## 修订：目录→平台映射是范围边界，未映射的目录不进识别管线

真实主库的顶层不是整齐的平台目录。实地扫描前的目录列举显示，顶层混杂着四类东西：平台目录（`FC`、`GB`、`gba`、`3ds`、`街机`）、按作品或系列组织的目录（`废都物语`、`荒野兵器系列`、`歌颂之丘`）、与 ROM 无关的目录（`存档`、`插件`、`模拟器`、`杂志`、`安卓`、`MacOS`），以及散落在顶层的裸归档与补丁包。

用户的决定：**工具只管已经按平台分好类的那部分，未分类的内容由用户手动处理。**

因此目录→平台映射不只是命名便利，它是**范围边界**：

- 用户确认一次哪些顶层目录对应哪个平台。**未映射的目录整体不进识别与刮削管线。**
- **库体检仍然报告全部内容**，含未映射的部分——那正是用户据以手动整理的依据。报告的覆盖面与识别的覆盖面是两件事。
- 「目录是强先验而非权威」这个结论比原文更成立，但理由变了：原本担心的是偶发放错，实际情况是大部分顶层目录根本不声明平台。

这一条同时结掉了挂账 D5（平台目录名要不要现在就映射成规范平台）：**要做，而且它是票 05 与票 07 的前置**，不是可延后的便利功能。
