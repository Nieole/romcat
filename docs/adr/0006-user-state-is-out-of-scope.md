# 工具完全不管理用户状态

收藏、游玩次数、游玩时长、通关状态这类数据是用户在前端里玩出来的历史，覆盖掉就真的没了；而各前端的存放位置极其分散（Pegasus 在 `favorites.txt` 与 `stats.db`，ES 在 gamelist.xml 内，LaunchBox 在库文件里），多设备并用时还存在无解的合并语义。因此工具既不读也不写用户状态，全部交给前端自己管。

## Consequences

- 换前端或重建库时，多年积累的收藏会丢失。这是明确接受的代价。
- **「不碰」在 ES gamelist.xml 上不是省略而是搬运**：`favorite` / `playcount` / `lastplayed` 长在同一个文件里，导出时若省略这些元素等于把它们清零。必须从导入快照里逐条原样搬过去。这再次说明三方合并与快照是必需的，不是可选优化。

## 修订：这条线管的是**前端里那份**用户状态；romcat 自己的**收藏**在线外

上面开头第一个词是「收藏」，而票 `gui-redesign/06` 给 romcat 加了一颗星。两者**同名不同物**，这一段把界线画在纸上，免得下一个人照开头那句把新加的这颗星删掉。

**这条 ADR 真正在讲的是「不碰别人家的文件」。** 三条理由通篇都指着前端那一侧：数据长在 `favorites.txt` / `stats.db` / `gamelist.xml` / LaunchBox 的库文件里，各家一个地方；那是用户**在前端里玩出来的历史**（游玩次数、时长、通关状态，收藏与它们同住一处）；多设备并用时合并语义无解。结论也照旧成立：**既不读也不写**，导出时逐条原样搬运（`adapter::gamelist`、`adapter::pegasus` 那两处至今一个字没动，报告里「用户状态 N 处」那一行就是搬运真的发生了的证据）。

**romcat 自己那颗星不在这三条理由的射程里：**

- 它长在**沉淀库**里（`crates/core/src/collection.rs`），不是任何前端的文件；主库照旧一个字节都不写（ADR-0004）。
- 它的键是**内容锚**（CRC-32 加大小），不是某台设备上的一条路径——所以两台机器上同一份内容天然是同一条，**这里没有那个无解的合并语义**。
- 它不是「玩出来的历史」：游玩次数与通关状态由前端在运行时累加，romcat 生不出这种数据；而「我要把这一批带到掌机上去」是**用户对着这个库做的一次挑选**，与**裁决**、**人工纠正**同一类，与它们同住一处。

**因此这条 ADR 的适用范围收窄成：前端里那份用户状态不在管理范围内。** 开头那句「收藏……这类数据」指的是 `favorites.txt` 里那一份。`CONTEXT.md` 的**收藏**词条已经把这条界线写死了：「**它不是用户状态**」。

**Consequences 里那句「换前端或重建库时，多年积累的收藏会丢失」照旧成立**，说的是前端那一份——romcat 不去救它，也不去动它。而 romcat 自己这一份反过来：**删掉中立库重扫也不丢**，那正是它住沉淀库的理由。

**两者之间眼下没有任何通路，这是故意的。** 「把 romcat 的收藏写进 Pegasus 的 `favorites.txt`」是一件独立的事——它要回答的是「哪一份说了算、怎么合并」，而那正是这条 ADR 当初判定无解的那个问题。要做的话另开一票、另立一条 ADR，不许顺手做。
