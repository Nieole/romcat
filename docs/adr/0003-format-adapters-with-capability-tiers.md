# 每个前端格式是一个适配器，并显式声明能力档位

需要支持的前端格式在访谈中迅速膨胀到七个以上（Pegasus、ES/ES-DE gamelist、RetroArch .lpl、LaunchBox、Playnite，以及若干安卓端前端），且方向是双向。把它们全部做到无损往返会让工程重心整个偏离需求 1（汉化版识别）。因此格式支持做成插件式适配器，每个适配器显式声明自己的能力档位：只读 / 只写 / 双向 / 无损往返。

## Consequences

- v1 只保证 Pegasus 与 ES gamelist.xml 达到「无损往返」档；其余格式一律先上「只写」档。只写成本极低，却当场满足「多前端多设备并用」。
- 「支持哪些格式」不再是版本级决策，而是增量工作。升档由实际使用驱动。
- 能力档位对用户可见：导出前 GUI 要能明说「这个格式会丢掉你的通关记录」，而不是让用户事后发现。
- 中立模型必须按所有格式字段的**并集**设计，即使 v1 只有两个适配器用得上——否则后续加适配器会反复重构模型。

## 修订（据格式调研结论）

「无损往返」不可能靠格式本身达成，必须靠旁路快照：

- **Pegasus 自己就是有损的**：`rating` 无 `%` 会被静默丢弃，`players` 的 `1-4` 存成 `4`（下界永久丢失），`release` 的 `1985` 读回来是 `1985-01-01`。
- **Attract-Mode 的转义规则不对称**，含 `"` 但不含 `;` 的值物理上无法往返。
- **RetroArch 缩略图的字符净化是多对一**，不可逆。

因此「无损往返」重新定义为：**导入时保存原文件的完整快照，导出时以快照为基线做三方合并**，中立模型表达不了或格式会吞掉的部分从快照还原。做不到这一点的格式，档位就只能标到「双向」。
