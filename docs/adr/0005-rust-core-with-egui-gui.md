# Rust 核心 + egui 原生 GUI

核心能力（二进制头部解析、并发哈希、10T 目录遍历）是 Rust 的主场，且核心必须是独立的库 + CLI，因为 10T 规模的扫描迟早要挂后台或扔到别的机器上跑，只能靠点按钮驱动的程序不可接受。GUI 选 egui：单一二进制、无 WebView 依赖、部署最简单、渲染性能好。

## Considered Options

- **Tauri**（曾被推荐）：中文输入法走系统原生通路无风险，复杂表格用 Web 技术写成熟。被否决是接受了包体与运行时依赖上的取舍。

## Consequences

- **中文输入法是这个选型的头号风险**，而工具的主界面（待确认队列）恰恰需要大量中文输入。egui 的 IME 支持依赖 winit，各平台表现不一。已派专项调研核实三平台现状，若确认不可用需要就地换 GUI 层——核心是独立库，换壳的代价被限制在 GUI 一层。
- **egui 内置字体不含 CJK 字形**，必须显式加载中文字体，会显著增大二进制体积，需要评估按需从系统字体加载的方案。
- 十万行表格要靠 `egui_extras::TableBuilder` 的虚拟化，多列排序、列宽、多选、行内编辑大概率要自己写。

## 修订（据 egui 可行性调研结论）

三个风险都不构成硬伤，选型维持不变。但以下约束必须进设计：

- **egui 版本下限锁 0.35**。中文输入最致命的两个 bug（回车上屏在多行输入里多插换行、组字时退格误删已有文字）2026-03-24 才修复，随 0.35.0 发布。一切基于 0.34 及更早版本的中文输入评价均已过时。
- **必须打包字体子集，不要读系统字体**。egui 内置字体不只缺汉字，中文标点、假名、罗马数字 Ⅲ、带圈数字 ① 全缺。实测 Noto Sans SC 裁剪结果：GB2312 子集 2.5 MB，GBK+Big5 子集 7.4 MB，完整 16.9 MB。系统字体不可行——苹方位于哈希命名的路径下不可硬编码，且实测苹方缺 `♪`、冬青黑缺 `♪` 与 `Ⓡ`，各机器覆盖不一致。
- **macOS 退出前必须调 `set_ime_allowed(false)`**，否则组字中关窗会 abort。
- **中文输入放详情面板，不放表格单元格**。表格虚拟化会让正在组字的那一行滚出视口时 widget 消失。
- **排序下推到 SQLite**。`egui_extras` 完全没有排序能力（源码中 `sort` 零出现），但这与「绝不把全库载入内存」的既定原则一致——排序本就该是 `ORDER BY` 加分页。多选需自写，估计 800–1500 行。

### 已知的遗留缺陷

- Windows 上 IME 默认仍走 legacy 路径；搜狗候选窗定位有一个开了三年的 winit issue，与修复者的实测结论冲突——**只能实机验证**。
- macOS 字符检视器插不进 `★` `♪` `Ⅲ`（三年未修），而这些符号在游戏标题中真实存在。仅影响手动输入这些字符，不影响显示与刮削。

### 若实机验证失败

降级目标是 **Slint**（真内联预编辑、官方承诺行数实际无上限、其搜狗定位 issue 已关闭、另有 Qt 后端作第二通路）。**不要换 iced**——`iced_winit` 走的是同一条 winit 通路，且额外背着一个 Linux 拼音连打三字直接 panic 的未修 bug。

## 再修订：主力平台是 Windows，风险排序改变

用户管理资源库的主力机是 Windows，外接硬盘为 NTFS。macOS 只是次要环境。

- **头号风险变成 Windows 上的 IME**：winit 在 Windows 上默认走 legacy 路径（源码注释称因 winit 给韩语 IME 报错误光标位置），且搜狗候选窗定位有一个开了三年、与修复者实测结论冲突的 winit issue。而 Windows 上最常见的中文输入法正是搜狗。此前记录的「macOS 字符检视器插不进 ★ ♪ Ⅲ」降级为边缘问题。
- **`egui_mcp` 无法验证 IME**。它走 `egui_inspection` 协议在应用层注入事件，而输入法位于操作系统与应用之间，注入的文本根本不经过 IME。它能验证的是字体渲染（截图检查 `★ ♪ Ⅲ ① ，。《》` 是否为豆腐块）与十万行表格性能，这两项占三个风险中的两个。**IME 必须在 Windows 真机上人工验证，没有替代方案。**

## Windows 平台约束

**MAX_PATH 260 字符限制**。10T 库、深层目录、中文文件名极易超限。必须使用 `\\?\` 前缀或在应用 manifest 中启用长路径支持，否则扫描会在库中最深的目录上以难以定位的方式失败。

## 修订：「排序下推」是**库浏览**那一屏的规矩，**待确认队列**不适用

上面写的是「排序下推到 SQLite」，并把它归到「绝不把全库载入内存」这条既定原则下。
票 24 落地时那一句要分成两句：它对**变体表**成立，对**待确认队列**不成立，而后者是主界面。

队列在票 24 里**整份留在内存里**（`triage::Queue`），换选择器只是把
`Filter::keeps_item` 重跑一遍，一次都不读库。三个理由：

- **队列不是库。** 库是 46,444 个变体、还要连上候选与标题；队列是其中拿不定主意的
  **16,656 条**，一条 `triage::Item` 几百字节，整份不到十兆。真机实测列一次 **34 ms**。
- **分组本来就要走完全部条目。** ADR-0002 说批量裁决是这件事成不成立的分界，而
  「一条 `--name [ACG汉化组]` 覆盖 129 条」这句话只能由走一遍全部条目数出来
  （三个轴、真机 3,391 组记号）。既然必须走完，留着就是白拿的。
- **人的动作不一样。** 库浏览是「翻到第九万行」，那是 `LIMIT`/`OFFSET` 的活；队列是
  「换个选择器再看一眼」，一分钟十几次。每次重跑一遍 `survey` 就是每次 1.3 秒的卡顿，
  那样的队列没人用得下去。

真正下推的那一半没变：**内容判据**（每个变体两次查库）只为选中的那些算，而不是列一眼
就整份算出来（`Queue::plan` / `Queue::detail`）。变体表那一屏照旧只留 512 行。

顺带把「中文输入放详情面板」推到底：**队列那一屏连搜索框都在面板里**，顶栏与表格里
一个 `TextEdit` 都没有。Windows 的输入法还没实机验过（票 23），把会碰到输入法的控件
全收进同一块不虚拟化的面板，是眼下能把风险面缩到最小的做法。

## 再修订：「核心必须是独立的库 + CLI」不等于「第一步必须在命令行」

开头那句「只能靠点按钮驱动的程序不可接受」说的是**命令行必须存在**——37 分钟的扫描要挂后台、要在另一台机器上跑（ADR-0018）。它从来没说过流程的**第一步**得在命令行，但实现把两件事合成了一件：界面开不了第一份库（`Site::open` 在 `catalog.exists()` 那一步就挡下），主干七步里识别、折标题、导出三步在界面上根本没有落点。

**ADR-0023 收窄了命令行的定位**：界面自足，命令行是后台与跨机入口。核心是独立库这一条不变，两个壳共用同一个核心、同一份**现场**、同一套路径锚。

## 修订：「原料还没备齐」那几句拒绝**留在界面层**

ADR-0005 那条红线是**领域判断不在界面层**。工序段落地时同一个形状撞了两次
（挂单 `Q423`、`Q437`），于是把边界写下来，免得第三次还是即兴：

- **界面层说得出口的是「原料还没备齐」**：库里那个键在不在、那份弹药取回来没有。
  眼下两处——识别那一支「还没有 DAT 库，去库屏上面那一段取」，
  导出那一支「还没选过导出的格式与目录，先在工序段底下那一行选一次」。
  **它们不是判断，是查一眼有没有**；而拒绝的那句话要指向**屏上的哪一处**才有用，
  而屏上的位置正是核心库不该知道的东西。
- **真正的判断照旧在核心里**：「有没有这个前端格式」是 `ExportSetup::check` /
  `ExportSetup::adapter`，界面只把 `Display` 转出来。
- **拒绝写在排活那一个入口里，不禁按钮。** `Section::start` 是排一趟活的唯一入口
  （票 `09` 的捷径走的也是它）。禁按钮等于把同一条守卫写两份，而两份迟早分叉；
  点了要**说话**，不是默默不动——各配一条测试钉着。
- 判据一句话：**拒绝的理由要是「盘上/库里缺一样东西」，留在界面层；要是「这东西对不对、算不算」，进核心库。**
