# 自动识别只保证做到发行版级，变体标识靠裁决沉淀

GBA 与 NDS 是中文玩家存量最大的两个平台，却是汉化版数据覆盖最差的（TOSEC 的 GBA 中文条目仅 26 条，NDS 无 DAT，RetroArch 数据库中文条目仅 13 条）。但缺口不在「这是什么游戏」——GBA 头里的 game code、NDS 头里的 gamecode 汉化补丁通常不改，发行版级识别是可行的；缺口只在「这是谁汉化的第几版」。而在作品级收敛的前提下，汉化组与版本对前端展示几乎没有影响，只影响库里挑哪个文件作首选启动。因此自动识别只保证做到发行版级。

## Consequences

- 汉化组与版本靠文件名启发式提取，并在裁决时由人工补全。
- **每条裁决沉淀成 `SHA-1 → 发行版 + 汉化组 + 版本` 的本地库**，可导出分享。裁决一次永久受益：重装、换机、日后拷进来的同一文件直接精确命中。这份数据正好补 TOSEC 缺失的那部分。
- 结构指纹 / 分段模糊哈希这条原创路线明确不做（见 ADR-0002 的修订）。

## 修订：沉淀库这一版按 **CRC-32 加大小**钉，不按 SHA-1

上面写的是「每条裁决沉淀成 `SHA-1 → 发行版 + 汉化组 + 版本`」。票 08 落地时**没有按
SHA-1 钉**，锚是 **CRC-32 加未压缩大小**，`sha1` 那一列建好了但一条都不算。

理由是成本不对称，而 ADR-0002 的再修订已经把这条道理说过一遍（「按文件体积决定解压深度」）：

- **CRC-32 加大小是白拿的。** 它是第一命中层的口径：**透明容器**里零解压就在容器头里，
  裸文件上一趟识别算过之后存在中立库的 `content_hash` 里。于是裁决**零成本落下、当场生效**。
- **SHA-1 要把内容整份读一遍**，容器里的还要先解压。真机队列里体积 ≤64 MiB 的有 9,622 条，
  加起来 25.3 GiB——而裁决是一件用户会反复做几十次的事。

代价说清楚：**导出的那份数据对不上以 SHA-1 为键的外部库**（GoodNES 的 646 条 NES 汉化
条目正是那样收的），别人拿去只能按 CRC-32 对。本机自用与「换机、重装、日后拷进来的
同一文件直接命中」不受影响——那几件事 CRC-32 加大小一样做得到。

这条**不是推翻，是推迟**：表里那一列与导出格式里那个字段都已经在，补上只是「算不算」
的问题。什么时候算、由哪条命令出这笔钱，记在挂账 D98 上。

## 修订：「确认没有发行版」是一条**明说**的裁决记录

上面说变体标识靠裁决沉淀，但没说「它压根没有发行版」这件事怎么记。票 07 一度靠
**「作品有、发行版空」这个形状**去推它——而那个形状同时也是「裁决定了作品、识别认出了
发行版」的样子，两者混着读，后一种会被误判成 homebrew 跳过（原挂账 D48）。

票 08 起它是沉淀库里一档**明说**的裁决（`verdict::Decision::NoRelease`），识别在撞库之前
读掉它；`identify::scope` 里那条靠形状推断的判据同时删掉。**判据只认明说的那一条。**
