# 开发在 macOS、验证在 Windows，跨平台是第一天的约束而非后期适配

用户在 Windows 上管理资源库（外接硬盘为 NTFS），开发会话运行在 macOS。选定的工作方式是两边都跑：先在 macOS 上把扫描器调通（快迭代），再在 Windows 上跑一遍验证平台差异。

NTFS 在 macOS 上默认只读，而库体检恰好只需要读——这个限制不构成障碍，反而顺带保证了第一轮迭代绝不可能写坏用户的库。

## Consequences

- **不允许任何 macOS 专属捷径**。路径处理、文件系统探测、文件名编码从第一行代码起就必须跨平台。事后适配的代价远高于一开始就写对。
- **Windows 侧必须显式验证的差异**：`MAX_PATH` 260 限制（须用 `\\?\` 前缀或 manifest 长路径）、路径分隔符、大小写不敏感但保留大小写的语义、文件锁定语义（打开中的文件不能删除或改名）。
- **所有写操作只能在 Windows 上执行**（子库同步、格式转换），因为 macOS 侧对 NTFS 无写权限。这与 ADR-0004（主库只读）恰好互相加强。
- 前置工作项：外接硬盘需接到 macOS 一次；Windows 侧需准备 Rust 工具链用于第二轮验证；egui 的 IME 冒烟测试排在 Windows 侧人工完成（`egui_mcp` 无法验证 IME，见 ADR-0005）。
