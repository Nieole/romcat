# 路径与只读接缝（`path` + `fs`）

**职责**：两件容易被当成琐事、实际撑住整个中立库的事——把任何平台的路径折成**中立库的键**，以及把主库的接触面收成一份**没有写方法的 trait**。

**边界**：不认领域概念。这里不知道什么是变体、发行版、子库；它只懂路径与字节。谁要碰主库就得拿 `LibraryFs`，这是 `core` 里唯一的读盘入口（`MemFs` 是它的内存实现，扫描那一路的测试因此不需要磁盘）。

## 路径

- **键 = 根名 + 相对那个根的路径**，分隔符统一成 `/`，再规范化成 **NFC**（`adr-0020`）。读盘用系统给的原始形态，入库与比较用键，**两者不混用**——混用的症状是同一个文件在库里出现两次、或者同名不同形认不出。拆键走 `split_root`。
- 第一段是**根名**，因为主库是**一组根**：加一个根不动已有键，挪一个根只改它自己那一支（`core-catalog`）。
- **Windows 长路径**：`MAX_PATH` 是 260，而深层中文文件名极易超限，所以系统 API 调用前加 `\\?\` 前缀；报告里展示的仍是原路径。跨平台是第一天的约束（`adr-0018`），扫描器里不许出现平台专属捷径。
- 路径规范化要**先化开**（尾斜杠、`.`、`..`、相对路径、符号链接），再剥 Windows 的 `\\?\` 前缀、再折成 NFC——工作目录折名字时踩过的坑，同一个目录换个写法就会另开一份库。

## 只读接缝

`LibraryFs` 只有 `canonicalize` / `read_dir` / `read_head` / `read_tail` / `open`。**没有写的办法**，因此「不改主库」不是纪律而是类型事实（`adr-0004`）。要读一份文件的一段就用 `read_head` / `read_tail`，别为了看几个魔数把整份 4 GiB 镜像读进来。

写的那一侧没有对应 trait：写只发生在同步执行与导出，且落在目标设备与元数据文件上（`core-sync`、`core-adapter`）。

## 已知地雷

- 键与原始路径**混用**这件事已经被违反过四次。凡是要拿路径当键、当比较对象、当落点，先问它是哪一族。
- 工作目录、断点、媒体池一律**不落主库**；判定「这条路径落进主库了」需要先从中立库查出根，查不出根时守卫退到字节级底线：只放行新建，目标已存在就拒绝（`adr-0004` 修订段）。
