# 能力档案与转格式（`capability` + `convert`）

**职责**：答两问——目标设备吃得下什么、目标存储放得下什么——并按答出来的配方把一份内容转成另一种形态，从主库读、往目标写。

**边界**：不挑谁进子库（`core-sublibrary`），不管落到哪条路径（`core-sync` 执行）。**只产生新文件**：读主库走 `LibraryFs`，那个 trait 根本没有写的办法（`adr-0004`）。

## 一份档案 = 一张平台矩阵 × 一个文件系统

两半缺一不可。只管格式的话，一份 5 GiB 的 PS2 镜像会被判成「原样搬」，然后在 FAT32 的卡上传到一半失败——卡上留下半份文件、清单里留下一条谎。同一个 RetroArch，卡是 exFAT 还是 FAT32 完全是另一件事，所以两个坐标各列一遍、再拼成几份具名档案。

内置预置档案可手动覆盖，档案本身是 TOML（数据不是代码）。

## 转格式的三条

- **边转边流式写目标**，默认**不落第三份**：转换很贵，缓存要再占一份等同空间，本机只剩几十 GiB 时那不是优化是灾难。出口是目标上一个临时文件，转完落盘再改名到位。
- **判的是每张碟的主文件**：多碟变体合完之后，各张碟算不算吃得下要逐碟判（`core-shape`）。
- **转换把两份不同的容器解成同名内容**时会撞车——那算「放不进目标」，不算覆盖（`core-sync`）。

## 为什么转换在导出管线里而不在整理主库

`adr-0015` 把转换的位置从「整理主库」挪到了导出管线，为的是让「主库保持原始形态」成为构造上的事实：同一个游戏导到不同掌机可以是不同形态，而主库那份永远是它本来的样子。
